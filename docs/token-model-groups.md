# 同一个 Key 的多模型分组配置

创建或编辑普通 Key 时，开启“按模型配置多个分组”，选择一个或多个可用分组，再选择需要限制的模型。每个模型可以继承 Key 的分组，或单独指定其中的一部分。调用者继续使用同一个 Key 和原来的 `model` 参数，不需要添加分组参数或创建多个 Key。

- 分组按选择顺序尝试；每个模型的独立列表也按其选择顺序尝试。自动路由和失败重试只在显式选择的范围内进行，不追加后台全局自动分组。
- 模型限制留空时允许这些分组内的全部可用模型；选择模型后，仅允许这些模型。清除某个模型的分组选择表示继承 Key 的分组。
- 修改分组导致已有模型规则变空时，需要重新指定分组或清除该规则后才能保存，避免静默扩大范围。
- 每次请求都重新核对用户分组权限；权限被收回或分组停用后，不会自动切到未授权分组。渠道限制、客户端限制、并发、重试预算和已输出内容的保护继续生效。
- 所有模型共用同一 Key 的余额/额度或套餐。倍率按实际使用的分组计算，仍叠加现有用户专属倍率、模型价格和时间倍率。列表显示动态倍率，实际分组和消费以使用日志为准。列表原有分组筛选继续按首选分组筛选。

## 测试目录

测试窗口可选择具体分组。选定后只显示该 Key 在该组有权使用、存在启用渠道且符合模型/渠道限制的模型，实际测试也固定在该组。真实模型测试仍正常计费，失败按原规则退款；视频仍仅检查配置。

未指定测试组时，多组 Key 使用其完整配置范围；旧固定组 Key 默认只列出首选组模型，即使开启故障自动切组也不合并其他组。旧 `auto` Key 默认保留自动组范围，可以在测试窗口选定具体组。旧 Key 的普通 API 调用与自动故障回退行为不变。

## API 与兼容

`POST /api/token/` 和 `PUT /api/token/` 增加 `routing_config` 字符串字段，内容为 JSON；空字符串表示沿用旧单组/auto 逻辑。例如：

```json
{
  "name": "团队统一 Key",
  "group": "standard",
  "model_limits_enabled": true,
  "model_limits": "model-a,model-b",
  "routing_config": "{\"groups\":[\"standard\",\"premium\"],\"model_groups\":{\"model-a\":[\"standard\"],\"model-b\":[\"premium\"]}}"
}
```

示例仅展示路由字段，其余额度、有效期字段按原接口提交。`group` 必须等于 `groups` 第一项；所有分组必须是用户有权限的真实分组，不能填写 `auto`。独立模型分组必须属于 Key 的分组；启用模型白名单时，规则里的模型也必须属于白名单。

旧客户端 PUT 省略 `routing_config` 会保留已有配置；显式传空字符串才清除。只改状态不改路由。旧 Key 不回写，可售 Key 保持已有只读限制，不开放本配置。新列为可空 TEXT，兼容 SQLite、MySQL、PostgreSQL，Redis 沿用字符串缓存格式。

`GET /api/token/models?token_id=ID&detail=true&group=GROUP` 返回该组目录和可选的 `groups`；每个模型包含其匹配分组和端点类型。`POST /api/token/test/:id` 可提交 `{"model":"model-a","group":"standard"}`。目录查询和测试都检查 Key 归属与模型、分组权限。

开始使用新配置后，不能直接降级到不认识 `routing_config` 的旧程序：旧程序会忽略新范围。需要回退时先核对这些 Key 的权限语义并通过受保护发布入口操作，不能用旧版本验证通过来代替此核对。
