# K3 缓存与思考用量字段验收

## 适用范围

本地兼容仅用于 Moonshot / OpenAI兼容渠道的 `kimi-k3`、`k3` 原生Chat响应，不改变调用参数、模型选择或其他模型的协议。截图显示“未返回字段”只能证明测试器没有取得数值；不能据此断定缓存未命中、思考关闭或网关丢字段。

## 字段与优先级

| 信息 | 首选路径 | 缺少首选字段时支持的真实来源 |
|---|---|---|
| 缓存读取 | `usage.prompt_tokens_details.cached_tokens` | `usage.input_tokens_details.cached_tokens`、`usage.cached_tokens`、`usage.prompt_cache_hit_tokens`、单choice的嵌套/平铺缓存字段、`usage.cache_read_tokens` |
| 思考用量 | `usage.completion_tokens_details.reasoning_tokens` | `usage.output_tokens_details.reasoning_tokens`、`usage.reasoning_tokens`、单choice的嵌套/平铺思考字段 |

只有上游已报告非负整数，才补齐缺失的标准嵌套位置及 `usage.cached_tokens` / `usage.reasoning_tokens` 兼容别名。后者为兼容既有客户端，不是要求所有模型都必须返回的标准字段。

- 标准字段明确0优先于正数别名。现有冲突原文保留，不静默改写为一致；客户端应按首选路径取值并记录冲突。
- 缺失或null是未知，不能填0或1伪装成未命中/命中。负数、字符串、分数、溢出数字或超过其明确输入/输出总数的候选值不用于补齐。
- 缓存用量是输入用量的一部分，思考用量是输出用量的一部分，别名不能再次加进总数。内部结算只使用归一后的单一计数；兼容修复可能纠正之前漏读的缓存折扣，不调整历史余额。
- SSE在真实usage块上补齐；后续结束/元数据块不覆盖对应的用量来源。强制格式化保留原usage，避免字段丢失或额外生成无依据的0。
- 客户请求 `stream_options.include_usage=false` 时仍遵守隐藏usage约定，不能为了验收强行暴露。
- 不能从reasoning文本的字符数、响应速度、`effort=high/max` 或输入相似度计算出“真实”思考量与缓存量。没有计数来源时保持未知。
- `cache_read_tokens` 为最低优先级后备字段；实测同渠道首次为0、重复命中时与标准缓存字段及输入总数同为5720。`cache_write_tokens` 不映射为缓存读取量，不凭该字段推定创建缓存的TTL或价格。
- 单choice来源只用于请求不是`n>1`、当前只有一个choice且index为0或省略的情况。不能把多choice流中某一块恰好只有一个choice，当作全响应用量。

### 冲突字段的结算一致性

- 流式和非流式结算都重新采用与来源诊断相同的计数优先级，清除通用解析器曾复制的低优先级别名。标准计数为null或非法时，不能一条路径按别名给予缓存折扣、另一条路径按未知处理。
- 内部未知计数仍用0参与既有结算，但不把0补进对外JSON/SSE，不把管理员的unknown/invalid改成reported。
- K3非流式在估算前复用流式已有的总量归一：非零`input_tokens`/`output_tokens`沿用既有取值优先级；不改变共享归一函数或其他模型。已有原始总量字段仍保留，不伪造供应商一致性。
- 新鲜缓存/思考计数不得超过任一明确给出的对应总量。遇到负数总量，两种模式均按无效上游用量返回错误，不让负数别名进入结算。

## 流式尾块保留

供应商可以先发含细项的usage，再发仅含相同总量的usage快照。此前后块会覆盖前块的缓存/思考量；本地现在只在**对应输入/输出总量明确相同**时保留前块已报告的计数。

- 缓存按输入总量绑定，思考按输出总量绑定；两项独立处理，不将usage快照相加。
- 当前块有明确0、null、非法值，或对应总量改变/缺失，均不沿用旧计数。
- 同一块同时提供`prompt_tokens`和`input_tokens`（或`completion_tokens`和`output_tokens`）时，二者必须是相等的非负整数才能作为快照依据；冲突、null、非法值或零/正数不一致都禁止恢复。此要求同时适用于来源块和后续块，后续回到旧总量也不能让已失效的快照复活。
- 响应ID或返回模型发生变化时清理快照；重试切换渠道时清理本次诊断。状态保存在单次handler内，不跨请求或用户共享。
- 此机制不缓存全文、不等usage才发送正文，不更改用户的思考档位、模型、路由、输出预算或超时。
- 无法证明总量一致的任意增量用量协议不在本规则内。未报告的计数依然不生成。

## 管理员来源诊断

消费日志原始数据的 `other.admin_info.kimi_usage_evidence` 保存归一前可识别的字段来源，用于部署后的请求级排查：

```json
{
  "cache": {
    "status": "reported",
    "source": "usage.cache_read_tokens",
    "value": 0
  },
  "reasoning": {
    "status": "missing"
  }
}
```

- `reported`：找到合法真实计数；value可以为0，并不等于命中。
- `missing`：未找到可安全使用的已知来源；不能据此断言响应中不存在任何供应商自定义计数。
- `unknown`：权威计数字段明确为null。
- `invalid`：权威字段格式不合法、为负数或超出明确的对应总量。
- `restored_from_prior_chunk=true`：值来自同一响应先前相同总量的usage块；source仍指向最初真实来源。

诊断只记录固定状态/字段路径/计数，不记录请求或响应正文、思考文本、用户标识或密钥，不参与扣费计算。普通用户与令牌日志接口沿用既有权限清理，不返回admin_info。没有新增诊断页面或自动供应商切换。

对于`missing`，下一步仍需要按实际供应商契约核对其原始响应，不能从模型输出字符数估计“真实reasoning_tokens”，也不能为了客户截图变绿而添加假的计数。

2026-09-29晚间的[供应商原始响应对照](KIMI_USAGE_UPSTREAM_DIAGNOSIS_2026-09-29.md)已确认1468的两次high/max直连请求也缺少思考计数；1466直连及经过元衡的定向请求均报告真实思考/缓存用量。这个新证据限定到实际样例，不将此前未知的全部历史记录改写成已归因。

## 测试器正确断言

1. 按上表查找数值，不能只找平铺字段；先判断字段是否存在，再判断值是否合法。
2. 缓存命中要 `cached_tokens > 0`。字段存在且等于0代表报告未命中，不代表命中。
3. 字段全部缺失要标记“未知/证据不足”。若合同要求供应商必须提供计数，可判“用量字段契约未满足”，但不能写“缓存未命中”。
4. 思考开启与思考Token计量分别断言：有reasoning内容不保证有reasoning_tokens，计数缺失不证明没有思考。
5. 冷请求、预热请求和暖请求分开；重试后可能更换渠道，必须记录实际链路，不把不同供应商的缓存拼成同一个会话命中率。
6. 流式汇总保留真实usage事件和字段来源，不把元数据尾块当成完整usage，更不能把累计usage逐块相加。

本站不包含截图所示测试器的源码，因此本轮不能直接修它的断言。需客户提供脱敏原始JSON/SSE、请求ID、渠道、stream选项及测试器版本，才能判断该次缺字段发生在供应商、元衡或测试器哪一层。

## 本地验证边界

本地夹具覆盖平铺/嵌套/单choice、强制格式化、未知/零/冲突、非法数值、usage隐藏及尾部元数据。隔离SQLite控制器验证相同上游数字按不同字段形状返回时，钱包、令牌、消费日志金额一致，不重复计算缓存与思考。

新增回归先复现“相同总量尾块把缓存80变0”和“单choice思考18漏读”，再验证尾块保留、总量/响应ID变化、n>1隔离、管理员元数据快照与用户日志权限。计费回归在含/不含尾部细项时均使用同一真实计数，且首段正文/思考/工具输出不等待后续usage。

冲突补充回归覆盖两种渠道、JSON/SSE、强制格式化、标准null/零/负数/超界计数与别名冲突；隔离结算覆盖14种用量形状的流式/非流式路径。原null冲突样例两种模式均扣120内部quota，正常缓存80仍扣48；这只是固定测试倍率下的结果，不是生产价格或历史补偿结论。

离线回归本身不是缓存TTL、真实命中率或K3推理档位的线上验收。随后授权进行的14条实际请求见[用户体验实测](KIMI_USER_EXPERIENCE_2026-09-29.md)：线上缓存可命中，但部分请求缺少计数；补丁的实际usage切片回放不等于已部署验证。未改变官方KVV断言或生产配置。
