# 服务状态与支持反馈

遇到问题先判断是网页、账户、模型调用还是特定客户端配置。不同层的问题需要不同证据；“不能用”通常不足以定位。

## 查看当前状态

主站公告用于发布平台更新与服务提醒。控制台中若显示服务可用性或监控数据，可作为排查线索；没有监控数据不等于所有模型不可用，单个监控点正常也不保证每个模型和分组都正常。

模型可用性以当前模型广场、令牌权限和实际请求结果共同判断。可以先使用只读的 `/v1/models` 验证基本认证，再决定是否进行会产生费用的最小生成测试。

## 一份有效的问题报告

| 信息 | 示例 |
| --- | --- |
| 时间和时区 | 请求发生的准确时间与所在时区 |
| 入口 | 网页路径、客户端名称和版本，或 API 端点 |
| 模型与分组 | 实际模型 ID 与令牌分组 |
| 请求标识 | `X-Oneapi-Request-Id`，若响应包含 |
| 错误 | HTTP 状态、完整但脱敏的错误正文 |
| 复现范围 | 每次发生还是偶发，最小请求是否成功 |
| 预期与实际 | 想完成什么，实际在哪一步停止 |

不要发送完整 API Key、网页登录 Cookie、密码、支付凭据秘密字段或无关客户内容。必要的请求结构可以用占位符替换敏感值。

## 联系方式

可通过站内文档的[常见报错](/docs/troubleshooting)先排查；仍未解决时联系 [nanashiwang@gmail.com](mailto:nanashiwang@gmail.com)。企业容量与迁移需求请说明业务规模，详见[企业接入](/docs/guides/enterprise)。

支付未到账时提供订单号、支付时间和页面状态；不要重复支付同一订单来尝试补到账。模型扣费争议提供请求 ID 和日志记录，不把支付金额与模型 token 用量混为一谈。

## 反馈后的核实

配置保存成功、任务已提交或修复已发布，都需要实际效果验证。重新验证受影响流程，并记录结果。服务恢复后再逐步恢复并发，避免积压请求一次性冲击上游。
