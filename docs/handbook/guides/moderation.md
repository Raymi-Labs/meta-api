# 内容审核接口

网关提供 `/v1/moderations` 路由，是否可用取决于账户范围内是否有支持审核协议的模型和渠道。它与平台自身的请求风控不同，也不是所有模型请求都会自动附送的审核结果。

## 调用示例

从模型广场确认支持审核的模型 ID，再把 `MODEL_ID` 替换为该值。密钥从环境变量读取。

```bash
curl --fail-with-body https://meta-api.vip/v1/moderations \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"MODEL_ID","input":"Text to evaluate"}'
```

| 字段                                                 | 用途                                     |
| ---------------------------------------------------- | ---------------------------------------- |
| `model`                                              | 审核模型标识，不应填入普通聊天模型       |
| `input`                                              | 待评估的文本或该模型明确支持的输入结构   |
| `results`                                            | 响应中的评估结果集合                     |
| `results[].flagged`                                  | 该结果是否触发模型审核规则，若协议提供   |
| `results[].categories` / `results[].category_scores` | 该结果的分类及分数，字段与分类随模型变化 |

不要把分数直接解释为客观违法概率，也不要把未触发判定当成平台使用条款的豁免。

## 应用如何使用结果

先定义业务规则：哪些内容可以自动通过，哪些需要复核，审核服务不可用时如何提示。保存必要的判定版本与操作记录，避免记录多余的敏感原文。

处理响应时先确认 HTTP 请求成功且没有错误对象，再检查 `results` 是否存在以及所需判定字段是否有效。单条输入通常读取第一个结果；批量输入应按模型协议对应每项结果，不能只检查第一项后放行全部内容。缺失结果、无法解析或连接超时应进入“审核未完成”流程，不应当作未触发规则。

对高影响决策应保留人工复核和申诉路径。审核模型会有漏判和误判，语言、上下文、格式与截断都可能改变输出。

## 失败处理与平台限制

认证、权限和限流处理与其他 API 相同。模型不支持该协议时，应选择有效审核模型或使用应用既有流程，不要把错误响应当作“审核通过”。

平台仍会按照自身服务条款与上游规则处理请求。使用规范、账户限制或安全风控的申诉应走[支持与反馈](/docs/guides/status-support)，不能通过改写调用路径来绕过。
