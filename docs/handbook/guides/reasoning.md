# 推理参数与模型能力

推理模型会在输出答案前进行额外计算。强度越高不一定越适合所有任务，也可能增加等待时间和成本。本站不会保证所有模型都接受相同的思考参数。

## 参数从模型与协议出发

| 协议 | 需要核实的配置 |
| --- | --- |
| Chat Completions | 模型是否接受 `reasoning_effort`、输出 token 限制以及温度 |
| Responses | 模型支持的 `reasoning` 对象、输出限制和文本格式 |
| Messages | `thinking` 配置、预算与 `max_tokens` 的关系 |
| Gemini | `generationConfig` 中当前模型支持的思考配置 |

不要同时发送多个厂商的思考字段，也不要假定 `low`、`medium`、`high` 等值适用于所有模型。某些模型不接受温度、采样或旧的 token 限制字段，错误正文会指出具体不兼容项。

## 从最小请求渐进开启

先用模型对应协议完成普通文本调用，再加入一个推理参数并比较正确性、延迟与使用量。记录模型 ID、参数、输入长度和请求 ID，方便区分模型差异与配置问题。

客户端的“深度思考”按钮可能会修改模型名、使用扩展字段或采用厂商 SDK。应检查其实际请求，不只看按钮文字。模型名称后缀也不是通用协议：只有平台明确列出的模型 ID 或明确支持的适配规则才可使用，不能自行附加 `-thinking` 或其他标记。

## 输出与费用

推理内容可能以独立字段、专用事件或仅统计 usage 的形式出现，不保证返回完整内部思考过程。应用应分别处理最终文本、工具调用和允许公开的推理摘要，不把缺少思考文本当成模型故障。

输出预算可能同时受上下文、模型和推理预算影响。到达长度限制不代表任务完成；检查停止原因。费用核对参见[计费说明](/docs/account/billing)。

## 遇到参数错误

保存错误正文，删除被明确拒绝的可选字段后重新验证。不要为了兼容一个上游而在所有模型中全局删除推理、工具或结构化输出参数。协议样例见[Chat Completions](/docs/reference/chat-completions)、[Responses](/docs/reference/responses)与[Messages](/docs/reference/messages)。
