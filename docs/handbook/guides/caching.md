# 提示词缓存与费用核对

提示词缓存用于重复上下文的复用。能否命中、保存多久、哪些内容参与缓存以及如何计费，取决于模型和上游；它不等同于平台把完整回答永久保存后直接返回。

## 三种常见情形

| 情形         | 调用侧关注点                                        |
| ------------ | --------------------------------------------------- |
| 自动前缀缓存 | 保持稳定系统提示词与公共前缀，把变化内容放在后面    |
| 显式缓存标记 | 仅在模型支持时按原生协议设置 `cache_control` 等字段 |
| 显式缓存资源 | 不要假设网关支持厂商的缓存创建、删除和计时管理接口  |

Chat Completions、Messages 与 Gemini 对缓存的表达不同。不要把某个协议的字段机械复制到另一个协议；本站未提供的缓存管理服务见[兼容范围](/docs/guides/compatibility)。

## 提高复用机会

1. 保持公共前缀的内容与顺序稳定，包括工具定义和系统消息。
2. 让用户输入、时间戳和随机信息出现在稳定前缀之后。
3. 保持模型与调用路径尽量一致；渠道切换、模型版本变化或缓存过期都可能降低命中。
4. 不为命中缓存而发送不必要的敏感数据或多余上下文。

即便两次请求看起来相同，也不能保证命中。上游的最小长度、有效期、容量和组织边界可能影响结果。

## 如何查看与计费

在响应 `usage` 中检查模型实际返回的缓存相关字段，并在[使用日志](/console/log)对照输入、输出、缓存命中或缓存写入说明。不同协议可能使用 `cached_tokens`、`cache_read_input_tokens` 或其他字段。

| 常见返回格式     | 核对位置                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| Chat Completions | `usage.prompt_tokens_details.cached_tokens`                            |
| Responses        | `usage.input_tokens_details.cached_tokens`                             |
| Messages         | `usage.cache_read_input_tokens` 与 `usage.cache_creation_input_tokens` |

字段未返回时不能自行填成“已命中”。有些协议的输入总量已经包含缓存，有些把非缓存输入与缓存读取、写入分别返回；不要重复相加或重复扣减。跨协议适配后尤其应以本站日志的计费分项核对，不只按客户端请求的协议猜测口径。

缓存命中通常仍有输入成本，缓存写入也可能单独计费。不要把所有输入 token 都按缓存价计算；也不要把推理 token 或输出 token 当成缓存命中。具体价格以模型广场与请求结算为准。

## 缓存异常的排查

对比请求的模型、系统提示词、工具顺序、前缀长度、分组、时间间隔与响应 usage。客户端额外注入的时间或会话信息可能改变前缀。如果只有某个客户端表现不同，先检查它实际发送的内容。

向支持反馈时提供脱敏的前缀结构、请求 ID、时间和用量字段即可，不要上传真实私密长文或完整密钥。
