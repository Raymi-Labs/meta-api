# HTTP 错误与请求诊断

诊断需要同时看 HTTP 状态、响应正文、客户端异常和平台日志。状态码只表示错误类别，不能单独判定是谁拒绝了请求。

## 常见状态码

| 状态 | 常见原因 | 建议动作 |
| --- | --- | --- |
| 400 | 参数格式、上下文长度、模型协议不匹配 | 保存错误正文，简化到最小请求后逐项恢复字段 |
| 401 | 密钥无效、缺失或认证格式不正确 | 检查令牌和当前请求实际发出的认证头 |
| 403 | 账户、模型、IP 或渠道权限限制 | 对照令牌和分组设置；不要换身份规避限制 |
| 404 | 地址拼错、模型或资源不存在 | 检查重复的 `/v1`、任务 ID 和接口路径 |
| 413 | 请求体超过链路限制 | 缩小图片、音频或上下文，避免反复提交相同大请求 |
| 429 | 用户、令牌、模型或上游限流 | 读取正文，减小并发，遵循重试提示 |
| 500–503 | 平台或上游异常、暂无可用渠道 | 记录请求 ID，短暂退避后有限重试 |
| 502 / 504 | 网关连接或响应超时 | 核对超时设置、网络和上游状态 |
| 524 | 中间代理等待源站超时 | 比较首字节与整体耗时，尝试受支持的流式请求并联系支持 |

同一种业务错误在不同协议中可能有不同包装。不要只匹配英文错误字符串来做授权或扣费判断。

## 收集最小证据

在 curl 中用 `-D` 保存响应头；不要启用会输出密钥的调试日志并直接公开。

```bash
curl --silent --show-error --fail-with-body \
  -D response-headers.txt \
  https://meta-api.vip/v1/models \
  -H "Authorization: Bearer $API_KEY"
```

重点记录 `X-Oneapi-Request-Id`、时间与时区、接口路径、模型、所选分组、状态码和已脱敏错误正文。流式请求还需要记录最后一个完整事件与是否收到终止事件。

## 分层排查

1. 在同一网络下测试最小请求；成功后再恢复工具、图片和附加参数。
2. 对照客户端 Base URL，避免把 `docs.meta-api.vip` 当成 API 域名。
3. 对照[令牌设置](/docs/account/api-keys)，确认未过期、有足够额度且模型可用。
4. 在[使用日志](/console/log)查找对应时间与请求 ID。
5. 若仅特定客户端失败，比较它实际发出的端点、请求头和字段。

## 哪些情况不要自动重试

认证失败、额度不足、参数不支持和未实现接口需要先修复配置。连接断开不代表上游没有处理；已返回部分文本、已创建视频任务或支付订单时，优先查询状态，避免重复生成或支付。

HTTP 200 的流仍可能在中途失败。应用必须检测错误事件、异常断流和缺失终止事件，不能在收到首块后立即显示“完成”。更多例子见[常见报错排查](/docs/troubleshooting)。
