# 历史：Pulse 付费消费来源证明 v1（已停用）

本文记录的逐消费付费来源证明曾用于 Pulse 消费贡献与产券。Meta Pulse v0.2.88 已退役该权益路径，Meta API 不再向消费日志写入 `Other.pulse_funding`，不得再用此证明生成 Pulse 贡献、等级或抽奖券。历史日志中的字段仅供审计，不表示有效权益。

文中描述的 `PulseFundingLedger`、`PulseWalletReservation`、`PulsePaidQuota` 与资金来源归因仍被 Meta API 的钱包预扣/结算/退款和现金核算使用，不得按本功能停用而删除。它们现在只服务 API 内部财务与钱包一致性，不由 Pulse 消费。

Pulse 只对有正向付费来源证明的消费产生贡献与券。`quota > 0`、`transferable_quota`、用户曾充值以及充值日志本身，都不能证明某次消费使用了付费额度。

## 支持范围

本版支持上线后 Stripe、Creem、易支付已验签成功回调产生的钱包入账，以及之后通过普通同步 `BillingSession` 完成结算的钱包消费。使用 new-api 已实际入账的整数 quota，不新增浮点金额账。

历史余额、管理员改额或手动补单、普通兑换码、用户钱包码、签到、邀请赠送和 Pulse 奖励不增加付费资格。它们仍按原有余额规则使用，但其消费不能据此产券。

订阅、独立套餐令牌、异步任务、Realtime、强制预扣图像请求以及旧结算路径暂不提供证明。相关消费、补扣和退款日志标记 `unknown`，由 Pulse 转入待核查。不得将上线前日志回填为“付费”。

## 本地原子核算

- `users.pulse_paid_quota` 保存尚可归因的付费余额，初始为 0，`pulse_funding_epoch` 阻止归因失效后在途退款重新恢复旧资格。两个字段都不通过 User JSON 输出。
- 支付订单成功、钱包入账、付费资格入账和 `PulseFundingLedger` 在同一事务完成。重复成功回调不重复入账。
- 同步钱包请求使用服务器生成的 `request_id` 创建 `PulseWalletReservation`，锁定用户行，在同一事务中预扣钱包和付费资格，优先使用有证据的付费部分。最终结算使用绝对目标额度，重复调用不会再扣。
- 预扣大于实际消费时先退未知部分，再按原预扣归因退付费部分；请求失败只退该预扣凭证的余额。已终结的凭证禁止变更金额或静默退款。
- 转码、人工改额、手续费、旧扣款或无法匹配原预扣的退款保守清空付费资格并记录失效原因。此策略可能少发券，不能误将未知余额当成付费。
- 钱包余额增减立即写入数据库；不再将 `users.quota` 加减延迟到批量更新。令牌额度、统计等既有批量更新仍保留。理由是延迟扣款可能在付费资格被消费后才到达数据库，无法提供一致来源证明。
- 支付权益追回还会设置独立的 `pulse_reward_hold`，停止相关账户新奖励到账，正常模型使用按原有余额规则处理。正常 Pulse 撤奖不设置该冻结。解除必须由运维核对支付与已发奖励并留审计，不能由用户资料修改覆盖。

这些操作都发生在 new-api 自己的数据库内，不调用 Pulse 服务，不给 relay 增加 Pulse 网络依赖。数据库或进程失败留下的未终结预扣须依原 request_id 核查；不能凭“没有消费日志”直接退款。

## 消费日志契约

日志写入器保留 `Other.pulse_funding` 键并覆盖调用者自行传入的值。正常用户日志视图隐藏该内部字段。

```json
{
  "pulse_funding": {
    "version": 1,
    "status": "verified",
    "paid_quota": 75,
    "non_paid_quota": 0,
    "unknown_quota": 25,
    "proof_ref": "wallet:不可变结算凭证ID"
  }
}
```

三个 quota 都是非负整数，合计等于该消费日志的 quota。`verified` 只说明 `paid_quota` 部分有证明，不能把混合消费中的 `unknown_quota` 计入贡献。只有成功结算、匹配日志用户、请求 ID 和额度的内部凭证可生成此字段。

没有证明时写 `version=1,status=unknown,paid_quota=0,non_paid_quota=0,unknown_quota=日志quota,reason=funding_source_not_attributed`。退款类型日志本版仍为 unknown；支持的同步预扣退款发生在消费日志产生之前。异步消费与之后退款均为 unknown，不能先发券再等待后续退款。

Pulse 消费方必须同时验证字段范围、版本、总额和 proof_ref，且对 proof_ref 做永久唯一去重；同一证明被写入多条日志不能产生多份贡献。缺失、未知、不一致或不支持版本均不自动产券。

## 部署与验收

不得混跑本版与不维护来源资格的旧 new-api 实例。切换前停止旧实例接新请求，排空在途请求及旧 wallet quota 批量更新，然后完成数据库迁移并一次切换所有实例。否则旧实例的余额写入可能绕过资格失效。

新表由既有模型迁移注册。禁止从历史 `quota` 或 `transferable_quota` 初始化付费资格。验收应覆盖真实支付重复回调、付费加赠送混合消费、并发预扣、部分退款、整笔退款、付款追回、转码、奖励消费不再生券，以及 DB 已结算但令牌调整失败时不误退钱包。

只在 Pulse 侧的契约校验、证明去重、预算限制、收款接收端上限和到账核对同时上线后开放自动抽奖。代码测试通过不等于生产支付和真实到账验收完成。

new-api 接收端的发奖开关、三项额度上限、发奖/撤销密钥、消费日志保护及论坛 SSO，可在「系统设置 → 配置 Meta Pulse 对接」配置，具体字段及轮换方法见 [META_PULSE.md](META_PULSE.md)。页面只保存修改的字段，已保存字段优先，未设置字段继续回退到部署环境变量；密钥输入留空保留，明确清除才删除。处理保存请求的实例立即生效，其他实例按 `SYNC_FREQUENCY` 同步，默认 60 秒。

这些页面设置不能替代上述全量版本升级、数据库迁移及在途请求排空要求。保持消费日志保护开启，以免停止向 Pulse 提供消费事实。Pulse 与社区插件的独立密钥、奖池、预算和开放开关仍须分别设置；不要因为 new-api 页面已保存，就认为抽奖或实际到账已完成验收。
