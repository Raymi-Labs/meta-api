# 企业归档：本地实现与验收说明

日期：2026-11-16。实现最初以`759bf144c`（v1.32.5）为基线，之后已整合伙伴最新`main`（`5c554ddaa`，v1.34.3）上的企业申请审核、渠道模型发现和定价更新。归档与伙伴新增的申请审核页、原子企业开通事务和路由同时保留；归档列表加载不会在申请审核/待对账页签触发多余请求。本次没有处理线上企业数据或发布应用。

## 目标与整体框架

企业生命周期扩展为：

```text
使用中 ←→ 已冻结 → 已归档
                     └─ 只读历史，不能恢复
```

冻结用于暂停服务；归档用于资金和在途任务都结束之后退出企业生命周期。历史消费、调账流水、审计和企业/成员归属ID继续保留。归档不会删除普通账号，也不会自动退款或核销。

实现复用现有企业管理、Root权限、钱包调账和历史接口；没有另外建立企业钱包、路由或价格体系。普通用户资金和调用规则保留。

## 管理员从哪里操作

入口：`/console/enterprise-admin`，平台「企业管理」。

1. 在企业行的「更多」中冻结企业。冻结后，新的企业令牌调用被拒；已受理任务仍继续结算。
2. 超级管理员（Root）在冻结企业的「更多 → 归档企业」打开预检。
3. 如果有剩余资金或欠额，按实际业务走退款、入账或现有「调账」流程，并填写真实原因。调账可在「金额 / 原始额度」间切换，原始额度直接使用整数，不再被两位小数截断。
4. 刷新预检；条件满足后输入完整企业名称和归档原因，点击「归档企业」。确认区明确告知不可恢复。
5. 归档企业从默认列表移到「已归档」页签。平台管理员可通过「历史记录」查询用量、资金流水、操作记录和历史成员。

普通平台管理员、企业所有者、企业管理员和普通成员都不能执行Root归档。前端隐藏归档操作，后端也独立校验权限。历史记录由平台管理入口访问，已释放的成员关系不继续提供企业后台权限。

## 归档条件

| 检查项 | 放行条件 | 不满足时 |
| --- | --- | --- |
| 企业状态 | 已冻结 | 先冻结；不能直接从使用中归档 |
| 账务守恒 | 净入账 = 未分配 + 成员可用 + 预留 + 消费 | 阻止归档，先核账 |
| 企业净余额 | 未分配 + 全部成员可用 + 全部预留 = 0 | 正余额与负余额都必须结清，包括1个原始单位 |
| 成员预留 | 每个成员的预留均为0 | 不能依靠正负相抵通过 |
| 请求记录 | 没有reserved/review或未知未终结状态 | 零金额预留也会阻止 |
| 视频/音乐任务 | 成功或失败、初次记账已确认、没有待结算标记 | 完成进度不等于完成账务 |
| Midjourney | 已确认受理/拒绝、任务终态、初次和最终结算都确认 | 结果未知、超时、未确认结算继续阻止 |
| 确认 | 企业名称完全一致、原因非空 | 不写入任何归档改动 |

预检是当时快照。实际提交在数据库事务中重新检查，因此预检后新增一笔调账或任务仍会被拦住。缺表/查询失败不会按“没有任务”放行。

### 微额收尾示例

历史验收记录中的 `未分配=-299、成员可用=0、预留=0、消费=299、净入账=0` 虽然账本平衡，但净余额是负299，不能归档。

如果平台明确决定承担这笔测试消费，应由Root通过已有调账入口增加299个原始单位，原因写清测试消费核销。之后消费仍是299，净入账成为299，净余额为0，才能归档。实现没有自动执行该操作，也没有把历史消费改成退款。该例来自先前的本地验收记录，不代表本轮重新读取了线上状态。

## 归档事务做什么

按企业行 → 全部成员ID升序锁定，复核资金与任务后，在一个事务内：

- 把成员正/负可用额度通过已有归并流水转回企业未分配；只做企业内部转移，不改变净资产或已消费金额。
- 撤销待接受邀请、失效待审批申请、停用企业令牌。
- 释放所有成员的`active_user_id`；当前有效成员变为已退出，已离职/停用成员保留原状态和离开时间。
- 给所有成员代次写归档标记，防止旧成员的迟到回调再次改账。
- 写企业归档时间、操作者、原因和不可修改的归档审计。

任何一步失败全部回滚。重复提交归档返回已有结果，不重复归并或写归档审计。

归档后，解冻、企业编辑、入账、调账、邀请、预算修改和新的企业计费写入均被拒绝。Owner的历史数字ID保留，但已归档企业不再阻止该账号注销或加入另一家企业；仍存在未归档企业Owner关系时，原保护继续生效。

归档企业不再占用计费分组引用。历史列表只保留当时分组名称，不显示后来修改的倍率作为历史价格。使用中和冻结企业继续保护其分组，普通用户分组未改。

## 对抗性审查中补齐的边界

| 边界 | 处理 |
| --- | --- |
| 归档与迟到请求/回调并发 | 归档锁定所有成员代次；请求和结算复用成员锁，读取归档标记后拒绝写入 |
| 上游已受理，任务记录迟到落库 | 企业Task插入也取得成员锁；在途预留和任务任一未结束都阻止归档 |
| 陈旧的令牌编辑覆盖归档停用 | 企业令牌更新取得同一成员锁 |
| 退款结束后仍有违规费补扣 | 企业违规费先持久化，再释放原预留；个人调用顺序不变 |
| Midjourney本地额度准入失败 | 仅在尚未发送且没有预留记录时明确结束意图；不从超时、未知响应或零价推断未发送 |
| 预检之后状态变化 | 提交事务重新计算，不信任浏览器预检结果 |
| 归档后恢复旧任务 | 沿用任务终态CAS，不能从已成功/失败改回进行中 |
| 列表迟到响应 | 请求序号隔离搜索、分页和归档筛选，旧列表不能覆盖新视图 |
| 预检请求失败 | 清空可提交状态，提供重试；提交失败刷新预检并保留确认输入 |
| 短屏确认操作不可见 | 弹窗正文滚动，危险后果与确认按钮保留；提交中禁止关闭和重复提交 |

### 验证边界

本机未配置可丢弃的MySQL/PostgreSQL实例，相关子测试明确跳过。本轮没有用旧CI通过记录代替新schema和事务的三库验证，也没有连接生产数据库。旧版本不认识归档状态和成员封闭字段，已有归档数据后回退版本需核对状态兼容，不能用旧版解冻接口恢复。Redis多实例缓存失效和真实生产schema仍未现场演练；企业调用会直接读取主库成员关系，缓存清理不是唯一阻断条件。

没有发布、线上企业归档、真实退款/核销、收费模型请求或邀请邮件投递。默认构建的SEO预渲染因本机默认Chromium路径不存在而跳过，不影响后台产物编译；需要正式发布时由原发布流程使用构建环境浏览器。
