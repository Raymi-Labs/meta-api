## 1. 整体框架

```text
个人账号登录
  ├─ 个人令牌 → 原个人资金来源
  └─ 企业成员关系 → 企业模型与角色权限
       ├─ 企业后台：成员 / 额度 / 审批 / 用量 / 设置
       ├─ 企业令牌 → TokenAuth → 调用入口许可 → EnterpriseFunding
       │               → 持久预留 → 本地/真实上游 → 结算或退款
       └─ 平台后台：开通 / 冻结 / 入账 / 调账 / 待对账处理

本次优化：
邀请授权代次 + 前端账号隔离 + 一次性结果保留
+ 空白名单明确确认 + 用量口径一致 + 本地调用账务验收
```

继续使用伙伴的企业独立钱包、实额分配、一个账号一家企业、令牌付款方不可变、有界首笔预留、欠额阻止新请求等设计。不把企业管理员提升为平台管理员，不恢复已撤回的独立路由/企业售价体系。

## 3. 本次加入和修复的细节

### 3.1 邀请不能绕过额度与模型权限

**原问题：**管理员直接给自己分配额度被拒，但可邀请自己的邮箱、退出、再接受邀请，得到自行填写的初始额度，并把原模型限制重置成继承。

**本次处理：**

- 创建邀请拒绝邀请本人邮箱；接受时按账号ID再次拒绝自授，不只依赖邮箱。
- 邀请记录新增 `inviter_member_id`，绑定签发人的具体成员关系/代次。
- 接受邀请的事务中重新检查签发人仍是该企业有效管理员/Owner，其账号未停用；邀请管理员角色仍要求签发人当前是Owner。
- 退出、停用、角色变更及所有权转移撤销相应签发人的待接受邀请。之后恢复角色也不复活旧邀请。
- 保留原有邮箱一致、邀请一次性消费、企业状态、唯一有效成员关系及预算守恒检查。
- 当前注册的邀请接口仅供企业管理身份使用；不根据“签发人没有成员关系”推断其为平台管理员，也不新增平台代邀入口。

**兼容影响：**旧版未接受邀请缺少签发成员代次，升级后需重新发送；已加入成员、企业钱包、现有令牌和历史账单不受影响。数据库只增加带默认值的列和索引，不删除或重写历史资金数据。SQLite已验证；MySQL/PostgreSQL迁移仍需实测。

### 3.2 企业身份缓存不串账号

- 切换账号时立即清空旧企业名称、额度和角色数据。
- 旧请求在退出/切号后返回，不得重新填入旧身份。
- 同账号后台刷新保留已加载内容，避免页面、抽屉和邀请结果反复卸载。
- 读取身份失败明确显示错误与重试，不把网络错误假装成“没有加入企业”。
- 企业后台按企业ID和成员ID隔离页面状态；成员变化不复用上一成员表单。

### 3.3 邀请的完整交互

- 成功后保留一次性邀请链接，用户点击“完成”后才刷新统计。
- 邮件未发送时仍可复制链接；后端只保存摘要，所以前端不得提前丢弃返回结果。
- 浏览器验收发现当前Semi组件在显式 `footer={undefined}` 时没有默认提交按钮，现显式提供“取消 / 发送邀请”。
- 提交使用同步锁，避免连续点击发出多个邀请请求；发送中关闭操作被阻止。
- 自动同账号身份刷新后，结果弹窗与链接仍保留。

### 3.4 模型权限支持“全部禁止”

- 企业及成员设置允许保存 `model_mode=custom`、`models=[]`。
- 保存前显示“禁止全部模型？”和后果确认，不能把空集合改成继承。
- 用户取消则不发保存请求；确认后保存空白名单，保留已有账单。
- 继承、指定非空、指定空集是三种不同语义；原生权限仍由后端决定。

### 3.5 用量和异步结果一致

- “全部状态”发送 `status=all`，列表、汇总和CSV共用相同参数，退款记录不会被遗漏。
- 成员、审批、设置、用量等数据读取使用请求序号；迟到旧请求不得覆盖最新筛选/页面结果，过期请求不结束新请求的loading状态。
- 后端默认省略status时排除退款的旧契约保持，避免影响其他调用者。

### 3.6 多语言与窄屏

- 新增三组错误/后果文案，覆盖17种控制台语言，保留既有重复键和文件结构，不顺便重排无关文案。
- 逐语言渲染390px深色用量页，发现俄语、德语等长文案令顶部余额超出屏幕。
- 顶栏在窄屏允许分行，完整保留返回入口与未分配金额；17种语言复验页面宽度均为390px，无整页横向溢出。
- 表格与导航保留自身横向滚动，不通过隐藏内容假装适配。
- 本轮没有逐页逐语言验收整个应用；覆盖的是企业共用顶栏和用量页，及中文邀请/设置关键流程。

## 4. 第一批调用的完整本地验收

新增 `router/enterprise_handoff_test.go`，使用真实API路由、TokenAuth、选渠与计费，唯一替身是回环HTTP上游和内存SQLite。

验证顺序：

1. 平台创建企业、入账；Owner邀请员工并分配额度。
2. 员工通过真实令牌接口创建企业令牌。
3. 企业令牌发起聊天请求，得到合成模型结果并结算。
4. Owner通过接口回收剩余额度，模拟额度耗尽。
5. 连续三次额度耗尽被拒，未到达上游，令牌按既有规则停用。
6. 员工申请额度，Owner批准；账务守恒。
7. 补额度后令牌仍停用，不自动解除停用。
8. 员工通过令牌状态接口手动恢复，再次调用成功。
9. 对比企业预留、消费、总览及账本，个人钱包不变，在途余额清零。

**没有修改自动停用规则。** 现有产品文档明确：连续三次耗尽停用，补额度后手动启用。自动恢复会混淆手动封禁和耗尽保护，需要另行设计停用原因与恢复策略，不能直接在审批成功时批量启用。

### 用户验收顺序

1. 更新至本次合并版本，Root登录：控制台 → 企业管理 → 启用企业功能。
2. 开通一间测试企业并指定现有测试账号为所有者；Root录入测试额度及凭证。
