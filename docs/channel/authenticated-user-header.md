# 可信用户身份 Header

渠道管理员可在既有「请求头覆盖」中使用完整值占位符 `{authenticated_user_id}`，向明确受信任的上游传递本次请求所属用户的 ID。它来自认证中间件写入的上下文，不来自客户端 Header、请求体、令牌名称或渠道名称。

示例（仅配置到已确认可信的接收端）：

```json
{
  "x-vm2api-tenant": "{authenticated_user_id}",
  "x-session-id": "{client_header:x-session-id}",
  "session-id": "{client_header:session-id}",
  "x-thread-id": "{client_header:x-thread-id}",
  "x-codex-parent-thread-id": "{client_header:x-codex-parent-thread-id}"
}
```

## 行为边界

- 只接受上下文中的正整数用户 ID；缺失、非正数或错误类型时拒绝构造上游请求，不回退客户端身份。
- 占位符必须占满配置值，允许首尾空白；不支持拼接前后缀。客户端传入的会话值不做二次占位符展开。
- 显式 Header 覆盖优先于通配和正则转发，按 HTTP 名称不区分大小写合并；构造 HTTP 请求时清除同名旧值，避免客户端伪造值或适配器非标准大小写残留。
- 普通请求缺少会话头时保持缺失，不根据用户、令牌或渠道自动生成共享会话。后台渠道测试使用其已有测试用户身份，并继续跳过浏览器会话头透传；后台测试不等于用户跨渠道会话验收。
- 未配置此占位符的渠道不自动添加身份头；不会更改模型、分组、密钥、计费、重试或数据库结构。
- 用户 ID 是可关联标识，应只向必要的可信上游发送。接收端仍需校验可信中转入口，不能因为有这个 Header 就信任任意公网请求；应用实例之间共享用户 ID 命名空间时需由接收端明确站点隔离。

## 发布与回退

1. 基于当前生产代码构建新版本，先通过受保护的 `newapi-update` 发布；不要用旧候选镜像覆盖后续修复。
2. 确认实际接收流量的所有实例均支持新占位符后，才通过管理接口合并渠道 Header 配置。旧程序可能原样发送模板字符串。
3. 模型列表需要调整时，先检查上游声明及实际能力，再复用渠道更新接口刷新能力索引与运行时缓存；不运行已退役的临时 SQL 发布脚本。
4. 公网验收需核对无效凭据拒绝、流式成功终态、Chat/工具、跨渠道会话，以及不同用户同名会话和伪造身份的隔离。账号选择、实际等待组和缓存效果以接收端证据为准，不能从渠道名推断。
5. 回退不支持占位符的程序前，先恢复相关渠道的 Header 配置并刷新缓存，再走 `newapi-rollback`。仅恢复本次配置，不用整库回滚覆盖新计费和日志。

代码合并与镜像构建不自动修改生产渠道，也不表示真实缓存收益或七天观察已通过。
