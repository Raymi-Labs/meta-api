# VM2API 渠道实时容量（试点）

适用于组织内部已有的单 Key Claude VM 渠道。默认关闭，不更改其他渠道的调度、会话字段或计费规则；没有数据库迁移。此补丁不包含生产部署。

## 配置

1. 确认 VM2API 提供 `GET /v1/channel/capacity?model=...`，schema_version 为 1，使用该渠道现有调用 Key 鉴权。接口基线为 [VM2API 补丁](https://github.com/hotsu32/vm2api/commit/8dae99a19ce96f08e9f685f8c7628891eb1d0f4c)；不能对不支持该接口的渠道开启本功能。
2. 开启已有的渠道并发控制。多实例必须共用同一 Redis；不使用 Redis 时只支持单实例。
3. 管理员编辑 Claude 渠道，在额外设置打开「VM 实时容量」。同一个 Base URL + 上游 Key 只能配置一个启用渠道，不支持多 Key 轮换。复制已启用的 VM 渠道会被拒绝，避免重复放大额度。
4. 保留渠道静态并发安全上限；选择等待或分流策略。首轮仅启用已约定的 VM 渠道，不全站开启。

对应 `channel.setting` 的局部示例（与现有 JSON 合并，不替换其他配置）：

```json
{
  "max_concurrency": 4,
  "upstream_capacity": {
    "enabled": true,
    "overflow_policy": "wait",
    "max_wait_ms": 30000
  }
}
```

- `wait`：优先等待当前 VM 渠道；默认 30000ms，可设置 1–120000ms，0 表示默认值。预算从选渠开始计算，不在容量重试时重置，客户端截止时间更早时服从客户端。
- `reroute`：当前渠道满载时尝试权限范围内的其他渠道，不额外做 VM 亲和等待。没有其他渠道时仍受原有全局有界等待保护，不保证立即成功。
- 静态 `max_concurrency: 0` 仍是继承全局默认；VM 返回动态容量 0 则禁止新派发，不能解释成无限并发。

## 调度与故障口径

中转准入上限为 `min(静态安全上限, effective_admission_limit)`。`available_now` 只表示上游此刻有无名额，已经扣除上游占用，不能再次减中转在途数，也不能当成渠道总上限。所有模型共用原有按渠道计数的 Lease，动态容量下降不切断已有请求。

按实际映射后的模型查询容量，需求触发刷新，不后台扫所有模型。快照最多有效 1 秒；同 Key 各模型汇总至少间隔 150ms 查询。读取超时为 750ms，响应上限 32KiB，不跟随重定向。共享快照和刷新锁使用现有 Redis，Redis 故障、接口失败、过期或未知状态均暂停准入；`partial` 只使用其中已知的保守容量。

仅对启用渠道的 HTTP 429/503 且结构化错误码为以下值时，按「执行前容量拒绝」处理：`channel_capacity_busy`、`account_pool_exhausted`、`channel_capacity_unavailable`、`api_key_concurrency_limit`。释放本轮 Lease，共享暂停 1–5 秒（Retry-After 在此范围内限幅），然后按预算和策略处理；不进入普通 429 长冷却、自动停用和模型熔断。未知错误仍走原规则。容量拒绝重试还受现有 RetryTimes 约束；0 不做额外重试。

只有尚未交付业务内容或已有 Claude ping-only 安全证据时允许重放，已经输出正文后不拼接或重试回答。保留原有请求体、session/cache 字段和账务流程。排队不持有执行 Lease；取消退出并释放等待计数。

这不是上游预留协议：快照间隙、其他调用 Key 与会话绑定都可能引起竞争拒绝。队列沿用有界轮询，不保证 FIFO，人数限制仍为实例本地。新功能不能单独保证用户首字更快或缓存命中提高，需要部署后的真实样本验证。

## 观测与回退

管理员现有 `/api/channel_concurrency/stats` 包含空闲 VM 渠道、静态上限、保守动态上限和 `vm_capacity` 状态。该接口只读缓存，不因打开管理页而查询 VM。默认查看渠道配置的第一个模型，可用 `?model=客户端模型名` 指定，再应用模型映射；不是跨模型容量总和。

零容量显示为 0；未知、过期、忙、读取失败显示未知，绝不显示默认 100。需求触发缓存可能在空闲时过期，因此空闲渠道显示未知是正常的。已有等待人数、超时、取消与等待时长是全局聚合指标，不能据此单独推断 VM 或用户首字时间。尝试错误保留原有诊断记录。

启用顺序：先验证并发布两端兼容代码（部署需单独授权），确认 VM 容量接口和实际模型，再对指定渠道启用。反向代理、客户端非流式超时应大于等待预算加模型处理时间；队列期间不承诺 SSE 心跳。不要对真实账号做 20 并发压测。

回退先关闭该渠道 `upstream_capacity.enabled` 并设置合适的静态安全上限，再回退应用；关闭后恢复旧调度行为，运行时缓存自然过期。不要仅关闭全局并发开关而保留 VM 容量开关：这会安全拒绝该渠道，而非绕过准入。

## 已验证与未验证

隔离测试验证了容量 4 下 20 个竞争调用的 Lease 不超过 4且最终释放、零容量后恢复、取消与总截止时间、Redis 共享缓存/故障关闭、实际模型映射、非法和过期响应、管理员零/未知状态不触发探测。完整非流式 Relay 测试通过真实 HTTP 适配、首次容量 429 后成功、一次计费、无长冷却/停用/Lease 泄漏。前端 helper、全部语言资源、Vite 构建及新增组件桌面/手机渲染已检查。

未验证生产流量改善、VM Rust 补丁的实际部署输出、两独立进程联调、真实 Claude 账号、MySQL/PostgreSQL 运行、完整管理表单端到端保存，以及新增策略的完整流式 Relay 矩阵。测试不代表已经上线。
