# 调用失败日志

用户可在使用日志的“调用失败”筛选中查看自己的失败请求，展开后可复制排查信息。字段包含请求 ID、模型、接口路径、HTTP 状态码、失败状态码、错误码、总耗时、处理建议及可用的 Retry-After。

- 一次请求只按最终结果记录失败。渠道重试最终成功时不新增失败行；最终失败时最近 5 次渠道尝试作为管理员诊断保存。
- HTTP 200 并不代表流式请求成功。响应开始后的显式流内错误仍会记录为调用失败，HTTP 状态与错误状态分开展示。
- 记录已识别用户且非已禁用令牌的鉴权拒绝、限流、渠道分配失败、参数及额度校验失败、上游错误和任务提交接口失败。无法识别用户的无效密钥请求不归入任何用户日志。
- 不读取或复制请求正文，也不缓冲模型响应。用户接口只返回公开的排查字段；渠道信息、上游诊断和尝试详情仅管理员可见。
- 失败行不充当账单，也不凭 usage 缺失推断免费。费用以相同 Request ID 下的消费或退款记录为准。
- 异步任务提交成功后的运行结果继续在任务日志查看；已有消费日志中的流式异常标记继续保留。本功能不将无明确错误的 HTTP 200 或零 usage 自动视为失败。

## 已禁用令牌与身份信息

令牌已手动或自动禁用时，客户端继续发送请求仍收到 HTTP 401 和原拒绝提示，但不再新增使用日志。服务端访问/错误日志仍可按 Request ID 排查。连续三次额度不足中触发禁用的那次失败仍记录；已通过鉴权的在途请求按实际结果记录，不因随后禁用而隐藏。过期、耗尽、IP 限制和上游鉴权错误仍保留，已有可信额度拒绝在日志中显示为“账户或令牌额度不足”。

早期失败缺少用户名时按已识别用户 ID 补齐；历史空用户名在管理员列表显示用户 ID。管理员复制排查信息包含用户名、用户 ID、令牌名称和令牌 ID，普通用户复制范围保持公开排查字段。均不复制密钥、IP 或管理员内部诊断。鉴权阶段尚未解析模型的请求仍保留空模型，不额外读取请求体猜测。

此规则仅影响升级后的新请求，不删除或回填历史日志，也不改变令牌状态、费用或自动禁用计数。

## 开关与升级

管理设置 → 运营设置 → 日志设置 → “启用调用失败日志记录”。默认开启；未保存面板设置时使用 `ERROR_LOG_ENABLED`（默认 `true`），已有显式 `false` 配置继续有效。

升级不会补造历史失败日志。旧错误日志可能来自单次渠道尝试，无法推断当时整个请求是否最终失败；其内部诊断仅管理员可见。

用户查询接口为 `/api/log/self?type=5`，支持现有时间范围、模型、令牌名称和 `request_id` 筛选，始终按登录用户隔离。错误行沿用既有日志保留和清理策略，不计入消费金额统计。

## HTTP 请求 ID 与上游 ID

客户端应从 HTTP 响应头 `X-Oneapi-Request-Id` 读取本站请求 ID，再用于日志的 `request_id` 筛选。该 ID 在同一次请求的渠道重试间保持一致；上游返回同名头时也不会覆盖本站 ID。响应 JSON 中的 `id`（例如 `resp_...` / `msg_...`）仍属于模型响应对象，不作为本站日志查询键。

管理员可在消费/失败日志 API 返回的 `other.admin_info.upstream_request_ids` 中查看共用 HTTP 出站入口最近五个实际响应的 `channel_id`、`request_id` 和 `request_id_header`。优先识别上游的 `X-Oneapi-Request-Id`，再识别已有供应商请求 ID 头；只保存长度不超过 256 字节且无控制字符的值。该列表不是最终响应 ID：后续连接失败或响应没有 ID 时不会补造条目。原有失败尝试诊断也识别该上游头。普通用户接口继续删除 `admin_info`。

独立 SDK、WebSocket 的上游请求 ID 不承诺由此入口采集。升级不回填历史缺失的上游 ID，也不改变历史日志的本站 ID；发布后的 HTTP 契约需要部署新版本才生效。

## 客户端连接中断诊断

新日志用「客户端连接中断」描述 `client_canceled`，不认定用户主动停止。管理员展开失败日志可查看 `other.admin_info.cancellation`：

- `duration_ms`：从失败日志中间件进入到服务端观察到取消的毫秒数，区别于包含后续收尾的 `latency_ms`。未安装观察器时回退为总耗时。
- `upstream_response_started`：当前 HTTP 尝试是否实际读取过正文（true / false）；未覆盖的传输为 null，不能把未知当作未返回。
- `phase`：`waiting_headers`（等待上游响应头）、`waiting_body`（响应头已到但正文未到）、`receiving_body`（已开始读取正文）、`unknown`（阶段未观测）。重试开始重置当前尝试，断开后的迟到数据不会覆盖快照。

共用 HTTP 出站入口覆盖流式与非流式。正文包含上游心跳、错误响应，不能据此认定已收到模型有效输出或已交付客户端；SDK/WebSocket 独立出站、进入共用出站前的排队与历史日志没有阶段证据时保持未知。取消回调有调度误差。45 秒或几秒断开均不能单独证明超时或主动停止，仍需结合客户端配置与日志。

管理员字段沿用既有权限隔离，不进入普通用户 API 或复制排查报告。无数据库迁移，不回填历史，不改变取消的重试、健康统计和费用语义。

## 响应头等待超时与一次切换

Chat Completions 和独立 Messages 请求第一次等待上游响应头超时时，如果失败重试次数大于0、客户端仍连接且尚未交付正文，网关可换一个同授权范围内的渠道，最多两个上游尝试。受控保活成功不算正文；写失败、指定渠道、透传/渠道参数覆盖/上游会话/容器/MCP/服务端工具、Responses和任务接口不使用这个例外。第二次失败即结束，不因跨分组计数重置而追加尝试。原60秒响应头等待不变，最坏总等待可能增加一次；超时不证明供应商未处理原请求。

保活已经发出时，HTTP状态只能保持200。最终成功不向客户端暴露第一路超时，管理员消费日志保留失败尝试；最终失败继续发送流内错误并记录失败状态504。客户端必须解析流内error，不能只以HTTP200或结束标记判断成功。未发出响应时可以正常返回HTTP504。不要把历史日志的HTTP200改写成504。

## 视频、文件和接口能力错误

渠道选择会提前排除已知本地转换限制：Chat Completions 的 `video_url` 不进入 Claude Messages 转换（包含映射到 Claude 的 Vertex、非 Nova 的 AWS）；Responses 不进入尚未实现该转换的 Anthropic、AWS、Vertex 适配器。按原模型、分组和令牌渠道权限选择其余候选，保留优先级；指定渠道不兼容直接拒绝，不改选。没有兼容候选时在调用与预扣费前返回 HTTP 400：

| 错误码 / 日志分类 | 含义 | 处理方式 |
| --- | --- | --- |
| `unsupported_video_input` / `unsupported_video` | 当前适配器不能处理视频输入，或上游明确拒绝视频 MIME | 使用支持视频的模型、接口和提交格式；不要把 MP4 当成任何接口都支持的普通文件 |
| `unsupported_endpoint` | 本地渠道未实现当前接口转换 | 使用可用接口或支持当前协议的渠道 |
| `unsupported_file`（日志分类） | 上游明确拒绝文件数据或格式，具体 MIME 未必已知 | 核对支持类型、编码和上传方式；不据此认定是 MP4 |
| `context_length`（日志分类） | 明确的上下文长度超限 | 缩短历史或减少附件 |
| `upstream_stream_break` | 上游明确报告流中断 | 保留请求 ID 和已收到内容，排查上游线路 |

展示用模型模态不作为路由承诺；未知上游能力仍由上游校验。已有透传模式保持原语义，不自动下载、抽帧、丢弃附件或修改视频格式。企业计费组同样遵循这些限制。历史失败日志不回填，不增加格式错误重试。

自研 SSE 脚本须按完整事件解析（空行分隔，不能假定一次网络读取就是一个事件），并分别处理：

- Chat Completions：JSON 的 `error` 对象是失败；后续 `[DONE]` 不能覆盖已经记录的失败。
- Responses：`event: error` / `type: error`、`response.failed` 均为失败；`response.incomplete` 也不能视作完整成功。网关在响应头发出后的最终本地错误使用顶层 `type/code/message/param` 的 `error` 事件，不追加 `[DONE]` 或 `response.completed`；上游错误已转发时不重复写。
- Claude Messages：`event: error` 是失败；只有正常 `message_stop` 才代表完整结束。
- EOF 前没有对应正常终态时，记录为未完整返回；保留部分输出，禁止自动重放已经输出内容或执行工具的请求。记录本站请求 ID、HTTP 状态及流内错误码，不记录密钥或附件正文。

上述脚本约定需在调用方实现；服务器更新不等于已修改外部脚本。
