# Agent Note: 企业工作空间、成员额度与申请审批

Status: implemented

## Problem

企业需要统一购买和管理模型调用额度，由企业管理员给员工分配额度及可用模型；员工独立登录、创建自己的令牌，余额不足时申请追加。原有的用户钱包、令牌和平台管理员权限不能表达企业归属、企业内部授权和审批。

目标客户是外部合作企业，平台内部团队作为首家灰度企业。本笔记记录首期闭环的实现；视频、体验区等第二批调用类型尚未接入，完成前不对外部企业开放。

## Decision

[交接后的安全与闭环优化](../bug-fix/2026-11-13-enterprise-local-closeout.md)补齐邀请签发成员代次和权限撤销、前端账号隔离、空模型语义及账单筛选；旧版未接受邀请需重发，已加入成员和账本不变。第二批调用仍未完成，详见[交接进度](../../../../docs/reviews/2026-11-13-enterprise-optimization-and-handoff.md)。

### 范围与开关

企业工作空间复用现有登录、令牌管理、模型目录、路由、计价和结算框架。企业持有独立钱包；成员额度是企业内部的预算划拨，不进入个人钱包。企业管理员是企业内部角色，不写入 `User.Role`，不获得平台管理员权限。

整个功能由 `common.EnterpriseEnabled`（选项 `EnterpriseEnabled`，默认关闭，`/api/status` 以 `enterprise_enabled` 暴露）控制。关闭时 `EnterpriseEnabled()` 中间件拒绝全部企业接口，企业令牌不可用，日志不补付款方。旧用户、令牌、钱包、套餐的解释不变。

用户 Group 继续承担可用分组/倍率职责，不兼作租户标识。每家企业配置一个计费用户组 `BillingGroup`，企业令牌鉴权后以该组覆盖请求上下文里的用户组，同一企业成员价格一致，合同价落在该组的专属倍率上；员工个人 Group 不改。

### 身份与角色

一个账号可同时有个人空间和企业成员身份；`EnterpriseMember.ActiveUserId` 的唯一索引保证一个账号只有一个有效成员关系，即首期一个账号只能加入一家企业。界面不做空间切换：企业成员创建令牌时选择付款方（企业或个人），`Token.EnterpriseId` 与 `MembershipId` 创建后不可更改；令牌列表和使用日志每行标出付款方并可按其筛选。个人令牌不会因加入企业而迁移。

| 角色 | 权限 |
| --- | --- |
| 平台管理员 | 开通、编辑、冻结/解冻企业，查看企业数据；入账、调账、处理待对账预留仅限超级管理员 |
| 所有者 Owner | 管理员任免、所有权转移，以及管理员的全部权限；企业始终保留一名有效 Owner |
| 管理员 Admin | 邀请及停用普通成员、分配回收额度、设置成员模型、审批申请、查看企业用量与操作记录、修改企业设置；只能管理普通成员 |
| 员工 Member | 查看本人企业额度与消费、管理本人企业令牌、发起和撤销本人待审批申请、退出企业 |

所有者也受自身成员预算与模型策略限制。管理员不能给自己加额度、审批本人申请或放宽本人模型范围，这些由 Owner 操作。企业只能由平台开通，开通时指定 Owner 和计费用户组。分配与审批不设单笔金额上限，总额受未分配余额约束。

邀请绑定邮箱，库中只存令牌摘要，7 天有效，一次性消费。成员关系以登录后接受邀请的用户 ID 为准，账号邮箱与邀请邮箱一致只作为接受时的校验。邀请可带初始额度：未接受不占预算，接受时在同一事务内从未分配余额划拨；余额不足时成员照常加入、额度为 0，并邮件通知邀请人。停用成员时其启用中的企业令牌一并停用、待审批申请失效，可用额度（无论正负）并入未分配；在途请求仍按原企业结算，结算后的残余由后台任务归并。重新加入建立新的成员代次 `Generation`，旧令牌不复活。成员离开不删除历史账单。

### 企业余额与成员额度

预付费、实额划拨：分给员工的额度立即从企业未分配余额划出。金额沿用内部整数 quota，不用浮点记账。

记 U 为未分配余额，A_i 为成员可用额度，R_i 为成员在途预留，S 为企业累计净消费，则净入账金额 = U + ΣA_i + ΣR_i + S。

- 入账：只走对公转账，超级管理员在平台“企业管理”页录入金额与转账凭证号，同一企业内凭证号唯一，重复录入被拒绝。企业入账不产生邀请返佣。
- 调账：超级管理员填写原因后增减 U，不设下限，可以把 U 调成负数；U 为负时不能分配，下次入账先抵。
- 分配与回收：U 与 A_i 之间划拨，回收仅限 A_i 为正的部分；不计入消费。
- 请求：按现有预估预留，A_i 不足本次预留则拒绝；结算按真实用量多退少补，超出预留的部分直接计入 A_i 并允许其为负，为负后拒绝新请求，后续分配先抵欠额。
- 成员的全部企业令牌共用 A_i；令牌可另设更小的上限，上限与已用量记在 `EnterpriseTokenBudget`，与成员预算在同一事务内检查。企业令牌不使用令牌表的剩余额度字段。
- 内容安全违规费从触发成员的 A_i 扣除并记流水，不扣个人钱包。
- 个人钱包、个人套餐、可售令牌额度都不作为企业令牌的备用资金；企业余额不足不扣员工个人的钱，个人消费也不扣企业钱包。
- 不提供月度清零、自动结转、成员间转账、提现和自助充值。

### 模型与调用范围

实际模型范围 = 平台开放范围 ∩ 企业设置 ∩ 成员设置 ∩ 令牌限制，由 `ApplyModelPolicy` 在服务端计算。企业与成员各有“跟随上层”和“指定清单”两种模式：跟随时平台新增模型自动可用，指定清单后不再自动加入；清单为空表示全部禁止。

企业令牌默认拒绝：`enterpriseTokenRoutes` 是放行白名单，覆盖文本、生图、语音、向量与重排以及模型列表；其余路由返回“暂不支持企业额度”。按用户 ID 扣个人钱包的兜底分支遇到企业来源同样报错。路由枚举测试断言每条 relay 路由要么在白名单、要么拒绝企业令牌，新增路由默认不放行。

`ValidateEnterpriseToken` 每次请求读主库核对开关、成员状态和企业状态，停用成员或冻结企业对新请求立即生效；停用成员时主动删除其令牌的 Redis 缓存。已受理的请求按原企业完成结算。

### 申请与审批

员工在“我的额度”页填写金额和用途发起申请。状态为 pending → approved / rejected / cancelled / expired；同一成员同时只有一个待审批申请，7 天过期。批准金额可以少于申请金额。批准在同一事务内核对审批权限、申请状态、成员有效性和 U，再完成状态变更与划拨；U 不足时申请保持待审批并返回原因，多人同时审批只有一个成功。企业冻结或成员停用使待审批申请失效，解冻不恢复。

通知只走邮件：邀请、邀请初始额度不足、新申请、审批结果、成员与企业的低余额提醒。邮件失败不影响业务结果。审批页和侧栏显示待办数量，没有站内消息。

额度用尽的请求返回 403 和“企业额度不足”文案，并区分“其他请求仍占用额度”的情况；没有单独的错误码。与个人令牌相同，连续三次因额度用尽失败的企业令牌会被自动停用，请求过大或额度被占用不计入；停用后要由成员手动重新启用，补充额度不会自动恢复。

### 页面

- 管理员：独立的企业工作台 `/enterprise/console`，自带顶栏和侧栏，五页为总览、成员、审批、用量、设置。
- 员工：留在原控制台，侧栏“企业”分组下的“我的额度” `/console/enterprise`；令牌与使用日志沿用原页面并标注付款方；顶栏同时显示企业额度。
- 平台：`/console/enterprise-admin` “企业管理”，含企业列表（开通、编辑、入账、调账、冻结/解冻）和待对账预留。
- 邀请接受页 `/enterprise/invite`：未登录可预览，登录或注册后回到该页加入。
- 公开介绍页 `/enterprise` 对企业成员显示“进入工作台”：所有者和管理员进企业工作台，员工进“我的额度”。

企业管理员可看成员消费金额、模型、时间和令牌名称，可撤销成员的企业令牌，不能读取明文 Key、个人账单或请求内容。用量按企业时区展示，导出上限 10000 条。

### 数据与接口

新增表：`Enterprise`、`EnterpriseMember`、`EnterpriseInvitation`、`EnterpriseAuditEvent`（只追加）、`EnterpriseLedger`、`EnterpriseReservation`、`EnterpriseTokenBudget`、`EnterpriseQuotaRequest`。`Token` 增加 `EnterpriseId` 和 `MembershipId`。日志表不增加企业列：付款方与企业名在读取时按令牌归属补上，账单以主库企业流水为准。

接口分三组，均在 `router/enterprise-router.go`：

- `/api/enterprise`：邀请预览与接受（限流）、本人企业信息、退出、本人申请。
- `/api/enterprises/:id`：企业管理，要求登录且是该企业的管理员或所有者；每次按对象 ID 访问都带企业条件，越权对象统一返回“企业不存在或无权访问”。
- `/api/enterprise/admin`：平台侧，要求平台管理员；入账、调账、处理待对账预留要求超级管理员。

### 计费可靠性

`EnterpriseFunding` 是独立的资金来源，每个企业请求都按请求标识建立持久预留，重试共用同一预留，结算与退款不重复生效。成员预算、令牌上限的检查与更新在同一事务内完成，以行锁和条件更新防止并发超分配。

后台任务每 5 分钟运行一次：超过 6 小时（`ENTERPRISE_RESERVATION_STALE_SECONDS`，最小 600）未终结的预留转为待对账并通知平台，不自动退款；由超级管理员在“企业管理”页填写原因后按金额结算或全部退回。同一任务归并已停用成员的残余额度。

## Existing capabilities and impact

- 公开介绍页 `/enterprise` 保留原内容，只多一个仅成员可见的按钮。
- 个人钱包的预留与结算规则不变；企业成员预算沿用同一规则，账本独立。
- 令牌分组、模型限制、自动回退仍按原逻辑运行，企业策略只做收窄。
- 额度不足提醒和连续失败自动停用增加了企业来源；上游现金账本接受企业来源。

## Alternatives considered

- 管理员给普通用户钱包直接充值：现有功能复用最多，但资金混入个人资产，离职回收、企业隔离、共享审批与审计都无法准确表达，因此不采用。
- 企业共用管理员账号和一枚令牌：接入最快，但员工无独立身份、权限与责任归属，不能支持本需求。
- 企业钱包加成员消费上限、允许总上限超过钱包：适合弹性预算且资金利用率高，但某员工可能提前用尽其他人的预算。首期采用实额划拨；后续可作为明确的共享预算模式。
- 独立企业版部署和代码分支：隔离直观，适合私有化交付，但会重复维护计费与权限。采用同应用组织隔离。
- 企业严格准入预留（初稿）：无可信计费上界即拒绝，超出部分待平台人工对账，超支控制最严。但多数客户端不传输出上限，成员有额度也会被拒，且每笔超出都需人工调账；2026-11-12 产品决定改为沿用个人钱包规则。
- 超出部分由企业不可分配的安全垫自动补扣、成员预算不为负：成员额度更直观，但多一套安全垫配置和补扣流水；产品选择与个人钱包一致的规则。
- 顶栏空间切换（初稿）：切到企业后整个控制台只显示企业数据，边界直观。但控制台要维护两套视图，成员容易找不到另一空间的令牌；2026-11-12 产品决定改为创建令牌时选付款方。
- 企业功能全部放进现有控制台侧栏：改动最少，但企业管理员多为非技术角色，五个管理页会夹在不相干的菜单之间。全部独立一套则令牌和日志要做两遍。选择管理员独立后台、员工留在控制台。
- 只开放同步文本协议（初稿）：交付范围最小，但外部企业需要生图、视频等全部能力；改为全部类型分两批开放，未改造的入口先拒绝。
- 自助创建企业并在线充值：获客路径最短，但每家企业的价格要单独配置，在线订单还要处理付款人与企业的归属；首期由平台开通、对公转账入账。
- 管理员审批设单笔上限、超出由 Owner 审批：多一层控制，但可批总额本来就不超过未分配余额，首期不设。
- 平台新增模型默认不对企业开放、由管理员显式加入（初稿）：企业不会在不知情时用上高价模型，但每次上新都要逐家勾选；成员预算已经限制支出，2026-11-12 产品决定默认自动开放，需要管控的企业改用指定清单。
- 额度用尽返回专用错误码 `enterprise_quota_exhausted`（初稿）：客户端可按码识别。实现沿用个人钱包的 403 加文案，没有新增错误码；需要程序识别时再加。

## Consequences

- 第二批调用类型未接入：网页体验区、视频与音乐等异步任务、Midjourney、实时语音对企业令牌一律返回“暂不支持企业额度”。完成前不对外部企业开放。
- 不支持：一个账号加入多家企业、自助创建企业、在线充值、企业发票归属、周期预算、按能力或速率的策略、站内消息、部门与项目、SSO、多级审批、后付费。
- 成员预算可短暂为负；全企业额度耗尽或平台调账后企业未分配余额也可能为负，由下次入账抵扣。界面在调账会扣成负数时用红色预览和红色确认按钮提示，不拦截。
- 实额划拨下闲置预算不会自动回到企业，管理员需主动回收。
- 预算接近用尽时，预估较大的请求可能因单次预留不足被拒，文案与“额度不足”区分。
- 连续三次额度用尽的企业令牌会被停用，补充额度后需成员手动启用。
- 对公入账依赖人工核对，录错金额只能走调账并留痕。
- 待对账预留不会自动退款，需要超级管理员逐笔处理；处理前该笔金额一直占用成员额度。
- 企业价格取决于计费用户组的倍率配置；绕过请求上下文直接读用户分组的调用点没有逐一核对。
