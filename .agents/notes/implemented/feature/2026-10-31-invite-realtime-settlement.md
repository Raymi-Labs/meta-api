# Agent Note: 邀请充值返佣及时到账与持久补偿

Status: implemented

## Problem

用户希望充值成功后返佣尽快可划转及按原规则申请提现。现有支付事务提交后才尽力入台账，失败只记录日志；主节点次日零点发放，启动不补跑，单笔异常中止全批；钱包及返佣弹窗不自动刷新。

## Existing capabilities and impact

已核对功能地图、钱包/设置/管理员邀请关系 → self权限接口 → model/user.go聚合 → InviteCommissionLedger，及Stripe、易支付等统一充值、Creem、管理员补单、套餐支付与权益撤销入口。原有台账唯一键、两级快照、条件状态更新、每日上限和追回逻辑可复用。活跃笔记检索“返佣|InviteCommission|T+1”：邀请推广笔记仅部分重叠（链接与点击保持）；日志计数同步笔记无关。没有已有结算归属笔记。

## Decision

复用pending台账作为持久待办，与成功支付/额度发放同事务写入，实际发放独立事务执行。事务提交后通过可合并的本机信号唤醒worker；各实例启动即补跑并每30秒扫描当天及以前的到期待办。数据库条件更新兜底多实例防重，不依赖内存信号持久性。单笔故障记录重试次数、到期时间并指数退避（30秒至30分钟），不阻断其他记录。

新台账保存金额快照版本，后续价格变化不改写已确定的返佣；历史pending保留原金额核验路径，既有已结算/跳过记录不重发，不按当前邀请关系全量追补无台账的历史订单。功能关闭继续暂停发放。每日额度仍按原支付本地业务日，两级合并按受益人计上限；失败重试可能晚于后续订单占用剩余额度，不承诺支付时间严格FIFO。

结算和支付撤销共用TopUp源记录锁；套餐撤销在锁住SubscriptionOrder后先锁支付镜像，避免pending状态竞争遗漏追回。新列默认值兼容现有数据及三种数据库，普通和快速迁移继续复用已有模型迁移。

钱包及明细在可见时每15秒刷新、恢复可见时刷新，保留当前分页、请求代次和身份隔离；后台请求不清空旧数据，不扩大二级关系可见范围。管理员汇总沿用同一settled台账，无另建口径。

## Alternatives considered

- 只缩短午夜任务间隔：最少代码，但仍有昨天日期过滤、入池丢失、单笔阻塞及前端陈旧问题。
- 支付事务内发放所有返佣：即时但扩展资金行锁与失败耦合；仅原子保存待办，发放留给worker。
- 引入Redis队列/新outbox表：可做分布式唤醒，但当前已有持久pending状态；复用台账避免双重任务状态和额外基础设施。

`go test ./model ./service ./controller ./router ./common` 全部通过。专项 `go test -race ./model ./service -run 'TestInviteRealtime|TestInviteCommissionRecovery' -count=1` 在隔离SQLite、MySQL 8.0和PostgreSQL 16上通过：含8个并发结算worker、每日上限、12轮充值/套餐交替撤销竞争、增量迁移保留旧行、支付待办写失败回滚及重复回调、金额快照、错误隔离与退避、今日收益立即划转/申请提现。worker测试覆盖启动、唤醒、补偿与退出，不使用真实时间等待。

Chrome 156的1440/390px页面验收通过：钱包与明细联动刷新，分页保持，隐藏暂停/回到页面恢复，失败保留旧数据并提示，弹窗关闭注销轮询，无支付写请求。修复原明细弹窗固定860px导致的手机溢出；新文案覆盖17语言。可见刷新单元测试和改动源码ESLint通过；全前端构建、语言资源检查及Chrome预渲染通过。尚未执行生产部署或真实支付/提现。

## Consequences

新列amount_version/retry_count/next_retry_at及status+next_retry_at复合索引由既有普通/快速迁移入口创建。待办数据库写入失败会让本地支付完成事务失败并等待支付通知重试，避免成功但永久漏返；外部收款不随数据库事务回滚。关闭功能暂停发放，已入台账的有效快照不受后来比例设为0影响；非法新配置仍按现有规则不产生返佣。

旧pending自动参与启动补偿，保留原支付业务日，旧已结算/跳过不重发；无台账历史订单不自动按现配置追补。多个实例与失败退避会影响达到日限额时的订单分配顺序，不保证支付时间严格FIFO。旧版本可保留新增列回退，但会恢复日批并重新按旧价格规则核算新pending，回退前应检查待办。

及时发放使收益更早可用，撤销后可能需要按原规则从已划转的钱包追回；原提现审核、金额门槛及权益回退保留。每个实例30秒兜底查询、可见页面15秒刷新增加少量数据库/HTTP负载。上亿级历史台账或大量实例时应再评估独立worker分片，而非预先引入消息基础设施。生产上线独立执行受保护迁移预检，本轮不部署生产。
