# Agent Note: 模型 Uptime 使用测试补充空闲时段

Status: implemented

## Problem

模型详情 Uptime 只使用真实请求成功率。低流量模型的小时段缺少样本，即使渠道测试正常也无法展示。测试日志使用管理员的分组，不能据此归属实际供应分组。

## Decision

扩展现有健康小时快照，分别记录真实调用与渠道测试，不新增日志扫描或定时探测。渠道测试实际发起请求且通过原响应校验后才记成功，远端失败记失败；本地预检、配置校验不采样。按当前渠道的精确模型能力归属分组，auto、未配置模型不纳入，不把一个测试模型推广到渠道全部模型。

查询先跨进程合并同分组/模型/小时。没有有效真实请求的桶，测试合并为一个补充样本：任一通过为成功，仅有失败为失败，无调用无测试为未知。已有真实调用不受测试影响。Uptime=(真实成功数+成功补充桶数)/(真实请求数+补充桶数)，不声称为时间在线率。真实请求 success_rate、用量、延迟、缓存与账单不变。

模型广场、详情 Uptime、小时条与对比图使用一致口径；请求健康入口维持原统计。仅测试的时段按结果着色并标记来源，不以30次真实请求门槛掩盖测试证据；含真实请求且不足30次仍灰色。保留当前权限、24/72小时窗口、七天清理与五秒幂等快照。

## Alternatives considered

- 将每次测试直接当用户请求：简单但测试频率、多渠道数量会改变成功率并污染用量；不采用。
- 测试通过覆盖已有真实失败：能更快转绿，但会掩盖用户实际故障；只补无有效调用的桶。
- 回读历史测试消费日志：无需新增采集，但分组不可靠且缺少完整失败记录；不回填。

## Consequences

小时桶内的任一次成功仅表示该时段测通过，并非整小时持续在线；未测试的上游不能推断状态。旧版本没有测试证据，新增数据仅从升级后开始。生产部署独立于发布。
