# Agent Note: 推广者实名、有效消费判定与风控

Status: implemented

## Problem

有效消费、同主体多账号、返佣回充及人工处置需要共享可审计状态；实名明文不可进入普通接口与日志。

## Decision

有效消费使用单笔一元、注册七天、真实用量三选二。新用户未满足时记 pending_time/pending_usage，在注册七天时重判；仍不足则跳过。每日资格补偿处理已满七天且有用量、没有新支付回调的用户。

已划转邀请额度与已排除基数分别累计，支付事务锁用户并扣减未排除额，明细展示排除基数。这是累计额近似，不判断站外资金真实流向。

实名由人工审核。姓名证件加密、主体 HMAC 去重，普通接口只返回脱敏值；原文只允许 Root 在填写原因后查看并记审计。是否要求实名才能发放由配置决定，默认 false。持久化加密密钥是启用前置条件。

浏览器保存随机设备标识并只上传到已登录用户接口，服务端仅存 HMAC；它是可清除的辅助信号，并非不可伪造的硬件指纹。当前可用付款主体为可信服务端 StripeCustomer；没有付款主体的渠道不伪造关联证据。同主体第二账号生成 skipped 台账，并复用支付风控事务 upsert 建单，已有支付处置不被覆盖。

按照用户 2026-11-19 确认，集中注册只记录风险、由管理员冻结。辅助检测使用 IPv4 /24、IPv6 /64、三日注册窗口和同额订单；没有自动冻结人数阈值，扫描上限一千条，不宣称完整反作弊识别。

改绑限注册三十天内一次，由新上级确认；关系写入共用全局锁，拒绝环和上游深度大于三，既有台账不迁移。清退下级进入公共池；撤销只恢复仍未改绑且不会成环的关系。处置撤销只恢复本动作持有的字段，保留后续晋级和永久切断状态。管理员不能处置同级或更高权限账号。

## Alternatives considered

- **接入第三方实名核验接口** — 自动化程度高、可防伪造证件；但需要额外供应商合同、费用与个人信息出境评估，且规则只要求“完成实名认证”，先用人工审核满足合规，接口留作后续替换实现。
- **用注册 IP 代替设备指纹做关联** — 无需前端改动，已有 `register_ip` 索引；但同一出口 IP 下的正常用户（校园网、企业网）会被误伤，单独使用误判率过高，改为只在“集中注册”组合规则中参考 IP 段。
- **有效消费只在支付时判定一次** — 实现简单；但规则允许“注册满 7 日 + 有调用”这类事后满足的组合，只判一次会让新用户的首笔小额充值永远无法生效，改为可到期重判。
- **明文存储实名信息并靠数据库权限保护** — 查询方便；但仓库与备份泄露时直接暴露身份信息，且项目已有按用途派生密钥的加密工具，选择加密存储加 HMAC 去重。


## Consequences

完整实现使新周期功能可由管理员启用，默认不影响旧入池路径。SQLite、MySQL 与 PostgreSQL 共用 GORM；跨库回归覆盖唯一索引迁移、并发回调、并发结算和退款交叉。浏览器验证桌面/移动入口、空态和分页；自动化检查记录见 [验收记录](../../../../docs/reviews/2026-11-19-invite-tier.md)。

生产启用仍需要备份和迁移预检；本次版本发布不等于生产部署。实名与设备数据须使用持久化密钥，丢失密钥无法解密原有记录；辅助信号和人工审核不能替代实名核验供应商。
