# Agent Note: 新公告发布时同步邮件

Status: implemented

## Problem

平台已有公开公告和控制台公告列表，但用户未打开网站时无法及时获知迁移维护等消息。现有 SMTP 用于验证码和个人额度通知，公告设置保存仅更新 JSON，缺少群发进度和跨重启防重复状态。

## Existing capabilities and impact

- `SettingsAnnouncements` 在本地编辑列表，点击“保存设置”才通过超级管理员 `PUT /api/option/` 写入 `console_setting.announcements`。公开铃铛、控制台和 `/api/status` 继续读取此列表，不另建公告源。
- `common.SendEmailTracked` 已区分 SMTP 接受、明确失败和 DATA 结果未知；复用其单次发送，群发队列自行控制重试。
- 当前用户邮箱、启用状态和软删除字段是收件资格来源。管理员个人通知地址不替代用户绑定邮箱；收件人逐封发送，不公开邮箱列表。
- 活跃笔记检索：[公开铃铛](./2026-10-25-public-notification-bell.md)部分重叠，仍持有展示和已读行为；[额度不足提醒](./2026-10-24-quota-blocked-notifications.md)部分重叠，复用发送结果边界但不共用业务限额；首页、企业导航、公开语言及 PITR 运维邮件笔记与公告发布不重叠。没有可直接更新的公告群发决策。

## Decision

在现有公告设置增加默认勾选的“发布新公告时同步邮件”。它随本次保存提交 `email_sync`，旧 API 调用省略时保持仅保存公告。只在最终保存成功后发布，添加弹窗仍为草稿操作。保存失败保留草稿；保存期间禁用公告开关；父级仪表盘设置刷新用递增序号只接纳最新响应，并跳过现有 GET 请求去重，保证保存后的刷新不会复用旧快照。卸载使未完成刷新失效。

公告保存与邮件任务、收件快照、已见公告标识同事务写入。所有保存均登记标识，只有本次真正新增且选择同步的公告进入队列；编辑、排序、删除、重复保存、删除后重新添加相同公告不重复发送。新公告使用 UUID，HTTP 内网使用 getRandomValues 回退；旧数字 ID 和无 ID 历史兼容，保留原编辑器对缺失、零值和空字符串 ID 的序号补齐，补齐后编辑历史正文也不触发群发。SMTP 未配置且确需创建新任务时整个保存失败，用户可取消同步后仅保存。单次最多同步 10 条新公告，限制批量事务规模，网站原有 100 条上限不变。

有效、启用、未删除用户的邮箱在发布时去重快照，发送前再次核对账号资格和邮箱。持久队列采用 GORM 跨库表和 CAS 认领，2 分钟租约超时转结果未知，不自动重发；暂时失败最多尝试 3 次，间隔 1/2 分钟。数据库共用发送槽将多实例合计限制为每秒最多认领 1 条，实际速度还受 SMTP 响应影响，不在保存请求内等待整个群发。超级管理员分页查看每项公告的待发、处理中、已提交、失败、未知及跳过数量，不通过接口返回邮箱。带收件快照的数据库操作禁用 SQL 日志；发布超过 90 天且无待发/处理中的任务及快照定期清理，防重身份摘要永久保留。

日期沿用原公告展示元数据，不增加定时发布功能；保存新公告即触发邮件。正文和收件人使用发布时快照，后续编辑、删除不撤回队列。邮件正文转义后台内容并保留 Markdown 原文文本，SMTP 接受仅称“已提交邮件服务器”，不承诺收件箱送达。

## Alternatives considered

- 全局开关自动监听任何公告 JSON 变化：可以覆盖旧调用方，但难区分历史编辑、迁移及显式发布，容易将旧公告重发。选择发布表单明确同步意图，旧调用保持兼容。
- 保存成功后直接启动内存 goroutine 群发：无需新增表，但进程重启无法追踪进度，重复请求及多实例也无法防重。选择持久任务和原子发布。
- 复用个人额度通知队列：已有追踪与重试，但业务频控、资源恢复和个人媒介偏好不适用于平台公开公告，因此只复用 SMTP 基础层。

## Testing

- `TestAnnouncementEmailDatabaseMatrix` 在 SQLite、MySQL 8（utf8mb4_unicode_ci）和 PostgreSQL 15 隔离数据库通过：新表迁移、SMTP 未配置和任务插入故障的原子回滚、历史/编辑/重复/删后重加防重、收件资格与去重、并发认领、全局限速、租约恢复及清理后仍防重。独立回归覆盖零值/空 ID 历史编辑、10 条同步上限和有界重试。
- service 测试覆盖实际队列处理、发送前资格变化、未知不重放、后台续发及 HTML 转义；复用 `TestQuotaNoticeSMTPOutcome` 的本地 SMTP 接受、拒绝和 DATA 回执丢失测试。新 model/service 测试通过 `-race`。
- controller 通过实际会话中间件验证未登录、普通用户、普通管理员的读写拒绝，超级管理员正向保存返回任务数、旧调用缺省不发、分页和数据库失败；响应不含收件地址。
- `web/scripts/announcement-email.test.mjs` 的 5 项测试覆盖 HTTP UUID 回退、旧 ID、显式同步与失败保留、草稿刷新保护和历史分页。`announcement-email.browser.mjs` 在真实项目页面验证桌面及 390px 暗色、添加/保存/取消同步、SMTP 保存失败、分页/刷新失败恢复、手机横向状态列；额外扣住旧 GET 并倒序返回，确认保存后的新列表不被覆盖。
- Go 全量测试、本地版本构建、17 语言资源检查、ESLint、主站与文档站正式构建及 Chrome 预渲染通过；发布工具 13 项测试与笔记结构检查通过。CI 产物与生产部署另行核对。

## Consequences

SMTP 无法提供严格恰好一次或最终投递保证；未知记录需要运营方核实，首版没有人工重发入口。数据库持久队列提高重启和重试的可追踪性，但收件快照与永久防重摘要占用空间；发送节奏会使大批量公告需要时间，积压增长时应结合实际 SMTP 限额评估速率。发布版本与生产部署分离，本次一次性维护邮件按用户授权独立发送并保留私有回执，不写入功能代码或公开收件数据。
