# Agent Note: 单次发票申请最低人民币 20 元

Status: implemented

## Problem

发票申请目前只校验交易有效性及合计上限，用户要求每次申请金额合计至少人民币 20 元。平台订单与人工银行转账走同一创建入口，必须使用已有开票金额口径，避免只在页面限制后被 API 绕过。

## Decision

复用 TopupHistoryModal → 登录用户 POST /api/user/invoices → model.CreateInvoiceRequest。后端在收集有效交易并以 decimal 累加人民币金额后、创建快照和扣手续费前拒绝不足 20 元的申请；20 元及以上继续原流程。前端显示最低金额并禁用不足额提交，提交处理也防御校验。门槛针对整次申请，不针对单笔交易；订单取数据库已有人民币开票金额，不采信客户端总额，不含手续费，不按钱包显示币种换算。旧申请审核与重发不追溯限制，无 schema 或配置迁移。

活跃笔记检索：原生发票 PDF、钱包体验及经典钱包布局部分重叠，分别保留附件与入口设计；全站语言部分重叠，沿用 17 语言。通知铃铛、发布复用和音色管理仅文本命中，与申请门槛无关。没有现有最低金额决定可原地更新。

## Alternatives considered

- 仅前端限制改动更少，但直接请求接口可绕过，不能保证提交规则。
- 每笔订单至少 20 元便于逐行校验，但会阻止多笔小额订单合并，不符合合计门槛。
- 管理设置可调门槛更灵活，但当前需求明确为固定 20 元，不增加配置入口与传播契约。

## Testing

`go test ./model ./controller -run Invoice -count=1` 通过，覆盖两类来源的 19.99、20、20.01、多笔不足额与多笔合并达标；不足额不创建快照、不占用订单、不扣手续费。订单归属、付款状态、CNY presentment 优先与旧审批/重发回归通过。钱包购买的 Money 为零，单独申请被拒绝，与足额人民币订单合并可继续申请，额度不计入门槛。

`cd web && bun scripts/invoice-minimum.browser.mjs` 挂载真实申请组件，合成 API 验证金额提示、禁用、增减选择、六位金额与浮点合计、切换来源、手工转账增删，以及 390px 手机提交失败保留表单后重试。前端完整构建、17 语言资源检查、Chrome 预渲染及 Go 编译通过。未操作真实客户发票或生产数据库；本轮无需迁移或数据库专属查询，数据库回归使用 SQLite。

## Consequences

合计门槛由统一后端创建入口保证，前端即时提示，旧客户端直接提交也收到明确拒绝信息。前端浮点合计按现有数据库六位小数精度处理边界，后端保留 decimal 精确比较。旧申请审批不追溯门槛；钱包额度单独不代表人民币金额。不增加管理员配置入口；如未来需要改门槛，需要同步前后端常量与提示。正式发布与生产部署分开验收。
