# Agent Note: 额度不足后持续调用的分级提醒

Status: implemented

## Problem

用户在余额不足以预扣下一次请求时，客户端仍可能持续重试。现有低余额通知在消费结算后触发，最终返回额度不足的请求不会走通知流程；提高已有通知频率不能补齐这个入口。

2026-10-24 的匿名生产样本在北京时间 03:45:36 至 08:38:50 有 584 次 insufficient_user_quota，单分钟峰值 154 次；04:08:30 最后一次成功消费后又有 297 次失败。样本余额大于零但小于请求预扣额，因此通知不能把所有拒绝都写成“余额已用尽”。历史日志确认部分低余额提醒被频控拒绝，但没有邮件成功回执，不能证明其余邮件已经送达。

本篇实现了用户确认的分级提醒，日上限使用滚动 24 小时。发布验证与生产部署分别记录，开发验收不向生产客户发送测试通知。

## Existing capabilities and impact

- [个人通知设置](../../../../web/src/components/settings/personal/cards/NotificationSettings.jsx)经 `PUT /api/user/setting` → [UpdateUserSetting](../../../../controller/user.go) → `User.Setting` 保存方式、阈值和通知地址。复用 email/webhook/bark/gotify 与绑定邮箱回退，用户选择其他方式时不额外强制发邮件。
- [SettleBilling](../../../../service/billing.go) → [额度提醒](../../../../service/quota.go) → [NotifyUser](../../../../service/user_notify.go) 已有发送链路。钱包与订阅提醒共用 `quota_exceed`；[现有频控](../../../../service/notify-limit.go)在发送前消耗次数，本功能沿用独立频控，不依赖旧通知窗口；相邻上游适配单独修复其原子计数。
- [NewBillingSession](../../../../service/billing_session.go)负责钱包、订阅、令牌预扣及资金来源回退。只有最终失败才应计入受阻事件，不能在钱包不足但订阅成功时提醒充值。
- [TokenAuth](../../../../middleware/auth.go)调用 [ValidateUserToken](../../../../model/token.go)，额度耗尽可能提前返回 401，不能仅监听 403；预扣令牌失败也可能包含数据库错误，不能仅凭错误码认定额度用尽。
- [最终结果观察](../../../../middleware/request_failure_log.go)和[失败标记](../../../../service/request_failure_log.go)可以提供统一入口；发送资格不得依赖 `ErrorLogEnabled`，也不能把模型列表查询、上游 403 或重试中的失败算成额度受阻。
- 活跃笔记检索：与[失败诊断](../../implemented/bug-fix/2026-10-17-relay-failure-diagnostics.md)、[上游能力切换](../../implemented/bug-fix/2026-10-12-upstream-capability-failover.md)部分相邻，沿用单次请求最终结果、回退成功不计失败的边界，不替代两篇决定。其余命中的支付、日志计数、模型页面、视频提案和运维邮件笔记不持有用户额度提醒决策；未发现可原地扩展的同主题笔记。

## Decision

### 触发与频率

增加独立通知类型 `quota_blocked`，与已有 `quota_exceed` 分开计数，复用通知方式和收件地址。首版固定以下默认值，在个人通知设置增加“额度不足导致调用失败时提醒”开关，默认开启并明确显示频率说明。

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 首次确认持续受阻 | 同一资金资源最近 5 分钟至少 3 个不同 Request ID 的明确本地额度拒绝，且最早与最晚拒绝间隔至少 60 秒 | 发送一次受阻通知；一个短暂并发尖峰结束后不单独补发 |
| 首次追提醒 | 首封受阻通知成功提交后至少 30 分钟，最近 10 分钟仍有至少 3 次新增额度拒绝，最近一次在 5 分钟内 | 发送一次累计失败汇总 |
| 后续追提醒 | 距上次成功提交至少 6 小时，仍满足上述近期活动条件 | 再发送一次汇总 |
| 总量上限 | 同一用户跨模型、令牌、协议合并计算 | 受阻通知滚动 24 小时最多 4 次；低余额通知沿用原规则，不占用这 4 次 |
| 无继续调用 | 不满足近期活动条件 | 停止追提醒，不因余额低而定时循环发邮件 |

若首次发送失败，重试沿用同一通知事件，不生成新的“首次通知”。达到频控上限时保留累计次数和下一次允许时间，下一次满足活动条件后再汇总；不补发窗口内的每一条历史提醒。初始参数是产品取舍，实施后通过通知量、持续失败量和退订情况再评估。

### 原因、合并与恢复

- 在本地计费拒绝点提供结构化事实：用户、令牌 ID、资金资源类型、拒绝原因、请求 ID、时间、可用额度与所需预扣额；未知数值省略。不从自由文本猜金额，不从上游响应或客户端 Header 获取用户身份。
- 钱包不足按用户钱包合并；令牌额度按具体令牌，订阅额度按具体订阅/适用范围记录。对外按用户合并一封，展示受影响令牌/模型数量及有界明细，避免多个令牌分别刷屏。
- 只处理服务端确认的本地额度不足，包括“仍有余额但不足以预扣”。资金来源回退成功、临时数据库错误、上游账户不足、模型无权限和普通鉴权失败不触发。
- 对鉴权前置的令牌耗尽，须先确认密钥命中合法令牌、用户启用及适用访问限制；未完成通知身份和权限校验时不发送，不改变原 API 状态码或额度判断。
- 充值、套餐续费、周期重置或提高令牌额度后先重新核对对应资源。以该资源在最后一次拒绝后成功结算、且连续 10 分钟无同类拒绝作为自动解除条件；其他令牌/资金来源成功、免费请求成功不解除。不能因一次小请求成功而不断重置通知次数。
- 无调用时不主动宣布恢复；48 小时无额度拒绝可结束旧事件。所有解除/新事件均不重置用户滚动 24 小时发送上限。

### 文案与可追溯性

标题示例：“API 调用因额度不足持续失败，请检查客户端自动重试”。正文包括观察时间段、拒绝次数、仍有余额但不足预扣的具体情况、受影响令牌/模型摘要、最后一个本站 Request ID，以及充值/调整令牌额度/等待套餐重置的相应入口。明确建议处理额度前暂停自动重试。

金额注明是某次失败时的快照，预扣额不等于实际费用。不展示令牌 Key、上游渠道身份或请求正文；名称等用户输入按发送媒介转义。部分调用仍成功时写“部分请求受阻”，不宣称整个账号停用。

每次通知保留事件 ID、用户、原因、汇总区间、触发次数、收件地址掩码、当前状态、累计尝试次数与最近失败原因；不把每次尝试另存为独立历史行。状态区分待发送、处理中、已提交 SMTP/通知服务、明确失败、结果未知、频控抑制和无可用地址；SMTP 接受不得标为已送达。普通用户在自己的通知设置下查看记录，管理员按用户查看，沿用原登录/管理员权限。

### 实现与可靠性边界

- 从请求最终结果观察处把可信拒绝快照交给专用服务，退出请求后处理；不在 API 请求内等待 SMTP，不扫描全量历史消费日志。成功结算也提供对应资源的恢复事实。现有 `RequestFailureLog` 的日志开关与额度提醒独立。
- 高频窗口使用 Redis 原子计数/时间桶，限制保留时间和维度数量。候选通知、发送时间、每日额度和审计使用小型持久记录及待发送队列，通过 GORM 唯一约束、事务与条件更新认领，跨实例和重启不重复放大发送。没有 Redis 时使用数据库原子聚合回退，不降级成每个进程独立发送。
- 原有 `NotifyUser` 返回 nil 也可能是缺少地址而跳过，且发送前已占用次数，不能直接当作成功依据。抽取已有各媒介发送实现，增加有类型的发送结果；新通知使用自身原子频控，保留其他通知的行为。数据库以待发送占位约束并发上限，发送成功后结算发送额度，明确失败释放并进入有界重试。
- 每个通知事件最多重试两次，建议在 1 分钟、5 分钟后进行；每次重试重新检查收件偏好、资源恢复和活动条件。无地址、用户停用或主动关闭通知时明确跳过。SMTP 最终确认丢失等结果不明情形标为 unknown，并保守占用频控额度，不立即重发；SMTP 不提供严格恰好一次投递保证。
- Redis/数据库异常时优先保证请求原有处理，通知服务记录内部错误，不绕过发送上限。后台工作有队列上限、查询索引与明确保留期；发送审计保留 90 天，清理只影响该通知记录，不删除消费/退款日志。
- 涉及新持久字段时仅做兼容性新增迁移，SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 均验证。生产部署仍走受保护发布入口，提案提交不代表上线。

## Alternatives considered

- **提高当前低余额通知次数**：改动最小，但无消费结算的额度拒绝仍不会触发；继续消耗原 `quota_exceed` 预算也无法区分即将不足与已经受阻。
- **每次额度拒绝都发，或每分钟固定发**：最快暴露错误，但样本达到每分钟 154 次，会制造邮件洪峰；持续时间越长干扰越大。选择短时确认、分级延长和滚动日上限。
- **第一次拒绝立即发送一次，之后永不再提醒**：实现简单且不打扰，但偶发并发预占会误提醒，用户错过首封后持续重试仍无人感知。选择至少跨 60 秒确认并按后续活动追提醒。
- **定时查询所有失败日志**：可少改请求代码，但通知会依赖错误日志开关、日志保留和数据库扫描；错误码也不足以区分真实额度不足与预扣数据库故障。选择可信事实与轻量聚合，历史日志只用于诊断。
- **只使用内存/Redis 保存发送次数**：成本更低，但重启、驱逐或多实例降级会重置通知节奏，也没有可靠发送审计。只将短期聚合放入 Redis，发送资格与结果持久化。

## Implementation and verification

- [可信拒绝](../../../../types/quota_rejection.go)由本地钱包预扣、令牌/周期额度、订阅判断提供，保留原有错误文案、HTTP 状态和 errors.Is 链。最终请求观察器与错误日志开关独立；鉴权前置拒绝另核对用户、到期、IP、分组、模型与指定渠道权限。恢复仅由正额度结算且最终成功提供。
- [后台服务](../../../../service/quota_notice.go)使用 2048 条有界信号队列、2 个信号消费者和 2 个发送消费者；调度每 15 秒最多检查 100 个账户，发送每批最多 20 条。信号超过 5 分钟或队列满时丢弃并记内部计数，不影响原请求；因此进程退出前尚未持久化的信号可能丢失，后续持续调用会重新达到门槛。
- [持久状态机](../../../../model/quota_notice.go)按用户写锁串行化：pending/sending 预占名额，明确失败释放，submitted/unknown 按实际提交或恢复确认时刻保守计数。发送租约 2 分钟，超时恢复为 unknown；SMTP/HTTP 单次网络发送有 30 秒期限（SMTP 另有拨号时限）。发送失败最多同事件重试 2 次，间隔 1/5 分钟。跳过后 30 分钟再查，连续 3 次明确失败后冷却 6 小时。
- 每账户最多 64 个资源，每资源最多保存 64 个令牌/模型标识；总 JSON 另限 56 KiB（兼容 MySQL TEXT 字节上限），超限先缩减标识集合再丢弃最旧资源；通知说明“至少”涵盖的数量，展示最新 5 项。Redis 每资源最多 10000 个 Request ID、20 分钟 TTL；序列有缺口或不可用时回退 SQL 信号，信号保留 20 分钟。信号和终态审计每轮分批清理 1000 条；48 小时闲置资源清空，账户保留空状态。无全量消费日志扫描。
- `TestQuotaNoticeDatabaseMatrix` 在 SQLite、MySQL 8.0.46（utf8mb4/utf8mb4_unicode_ci，与生产核对一致）和 PostgreSQL 15 的隔离库通过：首次门槛、30 分钟/6 小时、跨午夜滚动上限与精确过期、154 次/分钟突发、并发认领、重复 Request ID、租约恢复、恢复不清空日限额、有界重试、其他资源成功和无活动停发。迁移使用 GORM 新增表/索引，没有引擎专有 DDL。
- `TestQuotaNoticeFinalOutcome` 覆盖三协议最终结果、上游错误、数据库错误、免费/查询、回退成功和日志关闭；`TestQuotaNoticeAuthoritativeBillingSources` 使用实际预扣入口核对钱包、令牌、周期包、订阅拒绝及钱包回退订阅成功。鉴权限制与发送前关闭设置单独回归。
- 本地 SMTP 服务注入 DATA 接受、明确 550 拒绝、最终确认丢失；HTTP 本地服务覆盖接受、503 和连接中断。Redis 7 实例及 miniredis 覆盖窗口、缺失/乱序/清空/不可用回退；未发送真实客户邮件，也未证明外部收件箱送达。
- 用户/管理员接口用真实会话鉴权中间件验证本人隔离、越权拒绝、未登录、管理员查询、分页、数据库失败，以及关闭开关后旧客户端省略字段的保留行为。
- `web/scripts/quota-notice-browser.test.mjs` 在真实项目壳配合隔离 API fixtures 验证个人开关保存/刷新、分页、错误恢复、名称转义、普通用户只请求本人记录、管理员编辑侧栏、390px 暗色和桌面。七语言同步；后端相关包、竞态、前端构建与 `make verify-notes` 在提交前执行。

## Consequences

[新公告邮件同步](./2026-10-26-announcement-email-sync.md)复用相同 SMTP 单次结果边界，独立管理公开公告收件快照与群发队列，不占用本功能的个人额度提醒频控。

短时确认会使首封提醒延后至少一分钟；停止重试的用户可能只看到已有错误响应。单个大请求的预扣额也可能远高于实际费用，需要准确文案，不能自动代用户更改预算或充值。

持久队列和多实例认领增加实现维护成本；短期聚合在 Redis 丢失时可延后触发，但持久发送额度必须继续防重。SMTP 接受后的最终投递仍需邮件服务事件或收件证据验证。

首版默认开启会扩大已有通知功能的触达范围，个人页提供说明与关闭入口；当前频率使用隔离服务验证。上线后若出现队列丢弃、发送积压或单用户超过维度上限，应先检查负载和活动样本，再调整容量或频率；不能通过清空持久限额解决。
