# Agent Note: 分组模型断路集中通知

Status: implemented

## Problem

生产检查发现企业专属组的 Grok 两条线路均停用，同一模型每小时出现 748 次选渠失败。现有单渠道禁用通知和多 Key 账号池通知不能说明某个分组模型已完全没有线路。单令牌限制、未知模型和余额不足又不能作为整组故障证据。

## Decision

仅在鉴权、模型权限和请求范围核对后，最终无法选渠的请求上收集有界分组模型信号；指定渠道、渠道白名单及已取消请求不收集。后台批量按完整分组模型范围核对 abilities 和渠道状态、待禁用和多 Key 持久化禁用/待禁用；只有确有配置且持久化状态下所有线路不可选才进入告警。进程局部/Redis 临时冷却、用户级熔断和客户端过滤不能证明跨实例全组断路，不纳入本批告警证据。自动组/首选组回退最终成功不计入断路。

使用小型 GORM 状态表存储每个分组模型的已观察失败次数、有限令牌 ID 样本、首次/末次时间、通知租约和恢复状态。以 CAS 更新支持多实例，不依赖 Redis 持久性；通知仍复用现有 root 用户投递目标和 Redis/内存频控。同步请求只进行有界内存聚合，后台合并写入并核对。首次通知后只有已观察失败计数增长才追提醒，同一持续故障至少隔 30 分钟，明确投递失败 5 分钟后重试，结果未知按已提交处理以避免立即重复；恢复仅称“路由恢复可选”，不宣称真实模型调用已经成功。不执行付费探测，不启用停用渠道或修改令牌回退。

## Existing capability review

- distributor 已区分模型未配置与渠道全空，并在已授权范围内进行有序回退；复用最终无可用渠道入口。
- 单渠道与多 Key 池通知继续负责各自状态；新增消息集中描述组/模型，不替代原通知。
- [额度不足提醒](../../implemented/feature/2026-10-24-quota-blocked-notifications.md)部分重叠：复用可追踪投递、频控与有界异步思路，不复用私人账务表或扩展其对象含义。
- [首选分组回退](../../implemented/feature/2026-10-24-preferred-group-fallback.md)部分重叠：保留权限和计费，不因告警增加重试或自动切组。
- [分组健康统计](../../implemented/bug-fix/2026-10-22-group-health-outcome-accounting.md)保持独立统计口径；通知中的计数仅为已观察到的断路信号，不声称全站完整请求数。

## Alternatives considered

- 每次失败同步查库和发通知实现简单，但增加转发延迟并导致通知风暴；使用有界内存聚合和后台状态机。
- 只用进程内 map 无迁移，但多实例重复通知、重启后恢复状态丢失；使用数据库 CAS 状态并沿用现有通知频控。
- 启用备用组或自动恢复所有渠道可能恢复部分请求，但会改变费用、权限或继续调用欠费上游，不属于告警职责。

## Testing

- SQLite、真实隔离 MySQL 8.0.46（utf8mb4_unicode_ci）和 PostgreSQL 15 状态机与路由查询矩阵通过，包含 GORM 迁移、并发累计、租约唯一、发送失败重试、租约过期恢复、恢复中发送与再次断路、过期清理。
- 可控时钟模拟批内前序投递耗时三分钟，后续通知仍获得完整两分钟租约，另一实例无法立即重复领取；通知间隔从实际投递完成时间计算。
- 新增失败快照计数验证空闲不追提醒、持续失败至少间隔 30 分钟、投递中新增失败保留；恢复待发时配置移除退役，重新不可选/查询不明延后，十条陈旧恢复记录不会阻塞后续告警。
- 真实 Distribute 集成覆盖全组断路、成功回退、auto 全空、渠道白名单、未知模型及模型权限；请求范围补充指定渠道、取消、匿名和首选组；后台验证配置正常/未知不误报、停用/待禁用/多 Key 持久化禁用，以及节点本地冷却不作为共享故障证据。
- 后台通知替身覆盖 748 次聚合、失败后重试、持久化配置恢复通知；并发聚合、1024 个内存分组模型上限、8 个令牌样本、HTML 转义与模型别名合并已验证。三包定向 race 验证通过。
- 未发送真实管理员通知，未执行真实模型探测，未部署生产。页面和权限 API 不变，无新增前端页面。

## Consequences

同步路径只收集已鉴权的最终无可用渠道信号，最多保留 1024 个组/模型、每个 8 个令牌 ID 样本；每次自动范围最多记录 32 个组。后台每 10 秒合并，单路由查询最多 1024 条能力；按实际配置模型合并归一化别名，状态表仅存配置范围内的已观察事件并保留七天，每轮限量清理 500 条。恢复每轮检查最多 100 条，通知最多 10 条，跨进程通过数据库 CAS 及两分钟租约协调；每条通知在实际领取时取当前时钟，投递完成后重新取时计算频控，不复用批次开始时间，避免前序慢投递令后续租约领取即过期。恢复待发的不可确认记录会延后，避免队列饥饿。

聚合满、进程退出或数据库失败时会丢失尚未持久化信号，数量明确标记“已观察”；状态表不是账务账本。投递结果未知按已提交节流；进程恰在投递后、写回前退出可能在租约到期后重复通知，不能声称 exactly-once。通知保留 root 用户现有邮箱/Webhook/Bark/Gotify 配置和 Redis/内存通知频控；未配置目标、限流或明确失败会延后重试，不阻断请求。

告警只证明数据库中渠道、能力和 Key 的持久化状态全部不可选，不覆盖节点局部/Redis 临时冷却、用户熔断、客户端限制、正在发生的上游故障或全部请求统计。恢复只说明持久化路由配置恢复可选，各节点临时冷却仍可能存在，不代表上游成功。此功能不执行付费探测，不自动更改渠道状态、令牌回退、分组权限或费用。
