# Agent Note: 源站与跳板 SSH 自动封禁

Status: implemented

## Problem

用户要求在 New API 源站与 Flawless 跳板安装并启动 Fail2ban。源站近期有大量密码失败；仅密钥登录的跳板仍有无效用户及 root 认证前扫描。两台均未运行自动封禁服务。普通登录来源已与用户核对，保护必须继续允许合法密钥连接。

## Decision

复用发行版 Fail2ban、sshd filter、systemd journal 和 nftables multiport action，仅针对 TCP 22。10分钟内6次失败封1小时，重复触发逐步延长、最长24小时，封禁历史保留7天。使用 aggressive 模式覆盖仅密钥服务器上的认证前扫描；不将公网动态VPN出口长期加入白名单。

采用[两个小型配置片段及运维说明](../../../../scripts/server-security/README.md)，在两台主机分别验证。保留既有 SSH 认证方式、应用、数据库、反代和防火墙规则。Fail2ban 自己的链/集合与既有数据库防火墙隔离。配置检查、真实自动封禁、解封、服务重启后的恢复及业务端口验证构成验收，不以仅服务启动代替。

## Existing capability and note audit

功能地图已有服务器流量监控，不能代替登录防护。活跃笔记按 fail2ban、爆破、SSH、ssh 检索：反代迁移笔记仅部分涉及管理访问；公开监控笔记涉及SSH跳转，均保留原决定；Kimi测试笔记仅为临时会话清理，属于无关命中。没有既有自动封禁归属，新增本篇。

## Alternatives considered

- 使用 normal 模式：对偶发认证前断开更宽容，但跳板已禁用密码，主要攻击表现为反复无效用户/root认证前失败；采用aggressive并保留6次/10分钟容错。
- 同时按源站HTTP日志封禁：能覆盖网页扫描，但源站记录的网络对端常为自有跳板/CDN，且登录失败也可能返回HTTP 200；未经真实客户端IP及登录结果校验不启用网页jail。
- 同时关闭源站密码登录：可消除密码猜测入口，但用户本轮明确要求Fail2ban，已确认部分合法工具仍用密码；保留认证方式，将密钥迁移作为独立变更。

## Testing

两台服务enabled/active，唯一sshd jail参数一致。源站包版本1.0.2-3ubuntu0.1、跳板1.1.0-9，均通过fail2ban-client配置验证，实际扫描日志已触发自动封禁。

使用临时network namespace、veth和198.18.255.0/30网段进行本机独立来源验收。基线22/80/443均连通；4次真实SSH失败连接产生足够失败事件后自动封禁，22无法连接而80/443保持连通。封禁期间重启Fail2ban，数据库恢复规则并继续阻断；逐IP解封恢复连接。两台均通过，测试地址活动封禁、接口、namespace及路由已清理，验收日志/历史按保留期处理。

源站39条、跳板64条成功公钥日志全部被filter忽略，0条记为失败。两台全新密钥连接成功，SSH有效配置与变更前哈希一致，源站数据库保护规则保留；部署片段与仓库哈希一致。源站本地和源站到跳板的HTTPS状态/鉴权分别200/401。本机电脑指定IP探测存在间歇TLS连接超时，记录在运维说明，不把异地成功当作本机网络稳定性证明。

## Consequences

自动封禁减少反复SSH扫描，仍依赖主机日志，不能代替强凭据、应用鉴权或服务商DDoS防护。共用出口的合法用户连续失败也可能被临时封禁，运维说明提供逐IP解封方式。一次连接可能产生多条失败事件，6条事件不等于6次连接。

现场复用Ubuntu 24.04与26.04各自软件包维护的SSH日志匹配，避免自行复制过时filter；新版本升级后仍须验证实际日志。源站原有密码登录保留，密钥迁移和关闭密码认证为独立工作。本轮为服务器运维配置和文档更新，不发布应用版本。
