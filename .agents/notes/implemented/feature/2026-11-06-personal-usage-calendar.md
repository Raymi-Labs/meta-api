# Agent Note: 个人调用日历复用留存结算记录

Status: implemented

## Problem

用户希望在元衡增加近365天调用热力日历、最长连续使用、日均/周均与总数。当前概览以留存结算日志统一口径，旧quota_data按异步小时写入，不能无说明作为完整年度真实请求。

## Decision

后续[个人总览](2026-11-06-personal-overview.md)接管页面归属：日历从数据看板移到个人总览并默认展开，数据口径/缓存/失败边界不变。以下保留首版位置决定以便追溯。

在概览统计卡片后加入“我的调用日历”，独立于原30天筛选，点击展开才查询；仅登录用户本人，管理员也不扩大范围。近365个本地自然日（含今天），timezone使用浏览器IANA时区，服务端校验，日期跨DST用AddDate。每笔消费结算记录计一次，task_id补差不计，退款/错误不计，与概览requests语义一致；不称全部HTTP请求或成功率。日均=区间总数/365、周均=日均×7，今天未结束；最长连续天数仅针对窗口内留存记录。明确日志清理/停记可能导致不完整，不将无留存冒充全年未调用。

复用日志表user_id索引与结算元数据，只投影时间/other，Go分日兼容三库；查询8秒、25万条上限、进程级并发2、账户/时区/日期隔离缓存5分钟（最多64项），不创建轮询或后台计数任务。超时/超限/坏JSON明确报失败，不显示部分总数。对于超限大账号后续可扩展持久日聚合，本次不放开原30天接口限制或启动全年回填。响应仅365个日期和次数，不含个人文本、令牌、渠道。

## Alternatives considered

- 直接扩原接口到365天：会扫描全部用量细节并建模型小时桶，影响现有概览性能与限制。
- quota_data年度汇总：轻量但数据采集开关/异步丢失/补差口径与现统计不一致，不作为同口径请求数。
- 新增日汇总表和实时写入：适合大规模但涉及结算幂等、回填与保留期迁移，本轮采用显式按需、有界失败的首版，超限不静默降级。

活跃笔记：概览体验与统一结算指标部分重叠，复用其请求口径、身份切换与失败不伪装零；公开用量参考不用于个人日历。

## Verification

模型及控制器两个包完整Go回归通过；定向测试覆盖账户隔离、无身份401、无效时区400、忽略客户端user_id/username、私有不可缓存HTTP响应、跨年/闰年/DST365日、区间边界、task_id/退款排除、连续天数与均值、空记录、坏JSON/超限/取消失败、缓存切片不共享与时区隔离。无数据库/schema/写入改动，SQLite fixture验证，不声称生产负载或其他数据库实机验收。

前端日历纯函数3项回归、36项完整主站界面/正文语言检查与生图资源覆盖通过；主站Vite构建通过。真实Chrome测试展开前0调用，展开后365日网格、键盘选择、390px横滑与无页面溢出、深色、失败不保留旧数、空态、账号切换重挂载清空；截图用合成数据，不是线上个人统计。前端关闭API通用GET去重，避免跨账号重挂载时借用旧请求；退出取消并用序号丢弃旧响应。初次单测直接导入组件触发浏览器localStorage依赖，拆出纯日期/数据校验helper后测试通过。


笔记校验248篇与归档封印通过，diff检查通过；最终定向Go回归通过。本轮测试、浏览器、预览与构建进程均结束，遗留进程为零。

## Consequences

基于留存消费记录而非永久审计，不能承诺历史全量。固定扫描上限对大账户会明确暂不可用，需要后续日汇总支持；不在失败时回退旧quota_data。增加只读接口无DB/schema/计费写入，合并不等于部署。
