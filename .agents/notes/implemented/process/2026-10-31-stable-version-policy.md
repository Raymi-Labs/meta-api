# Agent Note: Meta API 后续采用正式版本号

Status: implemented

## Problem

用户要求后续维护使用正式版本号。公司迁移时沿用的 v1.0.0-compat.N 序列将所有日常发布归为预发布，也无法从版本号区分修复、新功能和不兼容变更。

## Decision

本篇“不兼容变更自动递增主版本”的决定已由 [产品里程碑版本规则](2026-10-31-product-version-milestones.md)取代。保留以下原决定及其验证记录；停止新增 compat、首次正式版基线、历史产物保护和工作流复用继续有效。

后续常规应用发布使用 v主版本.次版本.修订号；首次正式发布以 v1.0.0 为基线，发布前核对远端标签，已有版本不重用。修复递增修订号，向后兼容新增功能递增次版本号，不兼容变更递增主版本号。预发布仅在明确需要测试版时使用 alpha/beta/rc 后缀。

现有 Linux Release 根据连字符后缀区分正式/预发布，镜像和附件名称使用完整标签，无需重写工作流。生产更新工具读取镜像版本字符串，latest 路径解析不可变摘要，显式目标仍限定 SHA/摘要，不新增直接传版本标签的用法。本次只落实未来维护规则，保留当前 VERSION、历史 compat 标签、Release 和产物，不因命名约定单独重发应用。CHANGELOG.compat.md 暂作为累计更新记录继续使用，避免改变既有脚本路径。

## Existing notes audit

- [公司仓库迁移](../../implemented/process/2026-10-27-company-repository.md)：部分取代其中继续 compat 序列的决定；仓库归属、历史保留、Actions 和生产边界继续有效。
- [Linux 优先发布](../../implemented/process/2026-10-21-linux-first-release.md)：部分重叠，复用构建矩阵和附件保留约定，不修改发布行为。
- 检索到的页面版本记录、生产恢复、数据库备份笔记不负责版本命名，判为无关。

## Alternatives considered

- 继续 compat 流水号最省改动，但不能满足正式版命名要求，且所有常规发布仍显示为预发布。
- 立即给相同应用重新打正式标签可马上出现正式 Release，但用户要求的是后续维护规则，本轮没有应用功能更新，保留下一次实际发布作为切换点。
- 新建更新记录文件能去掉 compat 文件名，但需要同步历史补包与发布脚本，当前保留路径并明确正式条目同样写入该文件即可。

## Verification

以离线 gh 替身执行实际 Release 工作流的发布步骤，v1.0.0、v1.0.1、v1.1.0、v2.0.0 均不携带 --prerelease，v1.0.0-rc.1 与 v1.0.0-compat.140 继续携带，所有路径保留 --verify-tag。没有调用真实发布接口。既有13项发布附件/可选平台回归、发布策略检查通过；代码核对确认 SHA/摘要更新路径不解析或比较 compat 数字。

AGENTS、公司说明、发布说明和功能地图同步新规则，旧公司迁移决定保留并标出部分取代。当前 VERSION 保持 v1.0.0-compat.140；未创建或修改标签。只修改维护文档，不涉及应用代码、数据库、前端构建输入或生产操作。

## Consequences

命名不能替代兼容性验收；首个正式版包含已有应用能力及其已知限制。多个并行维护任务须在发布前同步主分支并核对远端标签，避免版本碰撞。本次提交合并可能触发现有 main 镜像构建，不能称为新应用 Release 或生产部署。
