# Agent Note: 完整恢复包清单与可验证日志离机归档

Status: implemented

## Problem

源站磁盘约89%，日志、数据库和恢复材料持续增长。用户明确保持三份数据库备份及 LAST_BACKUP_DIR，暂不处理 MySQL logs、七天 binlog、Docker 镜像；第一批仅允许归档超过30天且已关闭的压缩文本日志。现有发布清单生成过早、使用绝对路径且遗漏隐藏 .env；后写入的发布状态和日志也不在清单中。

## Decision

既有发布工具在所有恢复包文件写完后生成包含隐藏文件的相对路径 SHA-256 清单，完整二次读取复验后才原子发布 SHA256SUMS。数据库转储完成与恢复包封存分开标识；封存前失败或中断的目录不产生完成清单。离线 verify-backup 拒绝遗漏、额外文件、路径穿越、链接及内容改变；校验成功不等于真实恢复演练。封存失败不自动回退已健康的新版本；旧包不自动重写。

日志离机工具复用已有应用轮转和压缩结果，默认只预览。archive 与 retire 分开：限定文件、计算指纹、gzip验证、通过显式 crypt remote 上传并解密读回校验、原子保存私有回执；退役前再次验证远端、源文件指纹、年龄和打开状态，逐文件删除。独立任务锁避免重入，关键状态变更持发布锁，网络上传及读回不占发布锁。失败保留该本地源文件，中断状态可重试。拒绝关闭内容加密的 crypt 配置，移除 RCLONE_* 环境覆盖，敏感配置和后端错误不输出。

后续只读核查确认生产已有 r2 remote、newapi-prod-backup 桶及2026-09-04的数据库备份；用户授权复用连接持续更新。[周期R2数据库备份](2026-10-22-continuous-r2-database-backup.md)承接独立定时备份，并在同桶encrypted前缀增加crypt、在Mac独立保管恢复材料。本文日志archive/retire尚未执行，数据库备份上线不自动授权日志退役；PITR和完整数据库恢复演练仍未完成。

## Alternatives considered

- 只修复 shell 隐藏文件通配：改动少，但无法覆盖后来写入的部署日志和状态，不采用。
- 本地只留一份数据库备份或清理binlog/镜像：能较快腾空间，但用户明确保留原策略，不采用。
- 全程持发布锁上传：状态简单，但网络延迟会长期阻塞发布；改为任务锁及短时状态锁，退役时重新核验源文件。
- 直接叠加 logrotate 或上传后立即删除：前者与现有轮转重复，后者缺少可恢复状态及读回证据；均不采用。

## Consequences

完整包校验可在搬迁后发现遗漏和篡改，日志退役具有可复验回执；代价是完整二次读取、上传和读回的I/O及带宽。上传单并发且设置网络超时；远端可用性与解密凭据独立保管是实际恢复前提。清单不能替代 MySQL 恢复和账务验证。第一批候选约3.6GiB，实际释放量还受持续写入及文件变动影响，不承诺20GiB。归档仍保持30天硬下限，不启用生产timer；R2目的地及独立凭据保管由后续周期备份流程落实；本文日志归档、数据库恢复及PITR验证尚未完成。运维工具独立安装，无应用版本或应用Release。
