# Agent Note: 源站磁盘维护与旧应用镜像保留

Status: implemented

## Problem

源站 96 GiB 系统盘已用 91%，仅余约 8.2 GiB。MySQL 约38 GiB，其中使用记录表约26 GiB；完整部署备份约14 GiB，文本日志约8.9 GiB，Docker 镜像73个。服务器已有每日备份保留和无损日志压缩，但最近两次部署发生在每日维护之后；镜像没有保留规则。

## Decision

复用服务器已有 `newapi-backup-retain.py`（保留最近三份完整备份并保护当前回滚备份）和 `newapi-log-archive.py`（只压缩关闭且一天未更新的日志，不删除历史），通过 systemd 覆盖改为每小时检查。独立[镜像维护](../../../../scripts/server-storage/image-retain.py)只处理指定 new-api 仓库、超过30天的镜像，保护全部容器引用、发布状态、当前 Compose 与保留备份引用；默认预览，执行时共用发布锁且不使用强制删除。每日镜像任务避开每小时备份检查的计划时间，异常停止并由 journal 留证。

影响范围为 root 运维脚本与 systemd；不改变页面、路由、鉴权、业务数据库或运行中的应用版本。功能地图现有运维入口有 SSH 和流量监控，没有磁盘维护。活跃笔记检索无同主题记录；日志并发轮转笔记只涉及应用 writer，不归并。

## Alternatives considered

- 删除数据库历史记录可以释放更大空间，但会改变用户查询和账单审计，并且 InnoDB 删除行不直接归还表文件空间；本次不采用。
- 全局 Docker prune 简单，但不能保护回滚镜像和其他项目；采用限定仓库、明确引用保护且无 force 的清理。
- 仅手动清理能暂时恢复空间，但更新仍会累积镜像；补上每日镜像维护，复用已有备份和日志工具。

## Verification

2026-10-17 北京时间完成六项 Python 回归，覆盖时间边界、全部引用保护、混合仓库标签、未知镜像、状态缺失、备份变量/符号链接、默认预览、非强制删除、锁竞争和失败即停；systemd 配置验证通过。线上默认预览发现41个候选，实际删除41个，再次预览为0；新任务 Result=success，脚本及三个配置的 SHA-256 与本地一致，两个 timer 均 enabled。

原维护任务校验最近三份备份后删除两份旧备份，共5666324657字节；无日志符合压缩条件，日志历史保持。执行镜像清理后系统盘使用率从91%降为81%，可用空间从8800378880字节增至18580074496字节，约净增9.1 GiB（期间仍有业务写入）。三容器启动时间均早于操作且重启计数为0，应用保持 main-135966d。现场结果与安装、回退路径见[运维说明](../../../../scripts/server-storage/README.md)。

外部HTTPS状态接口200且success=true，无凭据模型接口401；没有收费模型调用。`make verify-notes`和差异检查通过。应用与前端未改动，无需重建业务程序。

## Consequences

当前磁盘压力缓解，连续部署产生的额外备份和长期不用的应用镜像有保留规则。历史业务数据与压缩日志仍持续增长，维护不是无限容量。清理缓存镜像会增加以后回到旧版本时的拉取需求，且依赖远端仍保留旧镜像；多标签镜像可能被 Docker 拒绝。锁竞争或引用读取失败时任务停止，需要观察服务失败记录，不猜测可删除对象。没有应用变更，不发布新应用版本。
