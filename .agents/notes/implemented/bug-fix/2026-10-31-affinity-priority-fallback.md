# Agent Note: 亲和失败后的优先级回退

Status: implemented

## Problem

生产 2d4a3358d 的最近一万条日志抽样中，有 6 条请求在亲和渠道返回 500/502/503 后成功切换；相关 OpenAI/GLM 分组存在多档优先级。现有普通和容量选渠直接把实际尝试计数当作优先级索引，亲和尝试未访问普通优先级却消耗一个索引，首次回退跳过最高可用档。线上记录证明该路径在用，不足以证明每次跳过的渠道当时健康；用本地多档渠道回归确认算法缺陷。

## Decision

移植上游 fcc241cdf 的尝试次数与优先级索引分离原则。亲和选中后在请求 context 保存当前路由分组索引加一（零表示未命中）；普通选渠、容量候选和首选分组候选共享优先级计算，仅在该初始路由组扣除一次索引。实际 Retry、重试错误分类和既有组间预算保持不变。新组从自身最高档开始，不继承亲和偏移；候选探测不修改分组状态。

旧 auto 的亲和可能绑定后续组，却仍从第一组开始普通回退；因此偏移归属当前路由索引，而不是亲和渠道的实际分组名称。多模型路由在亲和标记前已经提交所选组，复用其索引。容量候选不提前消费或清除标记；切换后的不同索引天然不适用旧偏移。

## Existing notes audit

[首选分组回退](../../implemented/feature/2026-10-24-preferred-group-fallback.md)和[多模型分组范围](../../implemented/feature/2026-10-27-token-model-groups.md)部分重叠，保留全局预算、白名单与候选探测无副作用约束；[能力拒绝安全切换](../../implemented/bug-fix/2026-10-12-upstream-capability-failover.md)管理重试资格，本次不改变。容量诊断、缓存计费和健康指标笔记无关，不替代。

## Alternatives considered

- 直接减少 Retry 最少改代码，但会增加真实请求预算，并破坏外层循环终止条件。
- 照搬上游全局 offset/reset 覆盖两条路径最接近原补丁，但本地有只读容量候选和首选组分支；在候选读取时重置会使等待轮询结果不稳定。
- 分组限定的只读索引换算在各入口复用，新增一个 context 状态，但不会让新组的第二次尝试也被错误抵扣。

## Verification

- 普通、auto、首选分组、多模型分组 × 随机/容量 × 缓存开关的 16 组回归，修复前全部将首次回退选为第二档，修复后选择最高档，规则未命中行为不变。
- 跨组后偏移不泄漏，旧 auto 绑定后续组仍正确回到首组，容量探测不推进状态，白名单/失败排除继续生效，真实 Retry 不减少。相关 service 定向竞态检查通过。
- controller 真实 Distribute/Relay 与本地 HTTP 上游覆盖亲和 503 后最高档回退、容量选渠和零重试预算；核对最终渠道、单次扣费与失败退款。复用既有首选组集成场景，不调用生产上游。
- 上述 controller 集成定向 race、最终 `go test ./...`、后端构建和笔记校验通过。一次中间 controller 全包运行在既有 Epay 测试出现 SQLite 缺表；该测试单独复跑及最终全量均通过，没有修改支付代码。

## Consequences

恢复最高档可能改变故障后的供应商选择，但遵守已有管理员优先级；不改渠道权重、资格、计费、数据库或生产设置。没有生产故障注入，不声称改善比例已被线上验证。
