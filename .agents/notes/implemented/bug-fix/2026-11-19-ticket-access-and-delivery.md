# Agent Note: 工单权限撤销、成功额度与异步结果一致性

Status: implemented

## Problem

v1.40.1复审复现六项遗漏：降权处理人仍收到标题通知；无效申诉占用全天额度；读取权限可删除管理员附件；消息查询失败提前清未读；旧筛选及旧账号请求覆盖当前页面。原[工单决策](../../implemented/feature/2026-11-18-support-tickets.md)继续负责入口和基本状态机，本笔记修订创建额度及读写确认边界。检索命中的桌面反馈、模型图标、邀请分配笔记与本次决定无关，保留原归属。

## Decision

- 创建额度沿用普通每小时3次、申诉24小时1次，但在锁定用户行的创建事务内按成功持久化工单计数，包含已关闭工单，失败回滚不扣额度。复用现有表，不增加配额表；全局API限流继续约束无效请求，回复及上传仍用既有Redis/内存限流。
- 通知队列只携带工单ID，执行时读取当前工单和当前收件人；处理人需启用且角色至少管理员，否则转给有效Root。收件地址和偏好同时读新值。
- 附件删除在事务中先锁工单，拒绝关闭状态；普通/申诉用户仅可删本人上传的公开附件，管理员可删未关闭工单附件。物理文件只在数据库删除成功后移除。
- 消息读取和已读确认放入同一个锁定工单的事务；查询或确认失败回滚。正常回复/上传使用相同行锁，读完后到达的新活动保留未读。不引入浏览器送达回执。
- 管理员列表只应用当前请求序号的结果；通知请求同时核对账号、角色和请求代次，退出或切换使旧请求失效，并禁用跨账号共享GET请求结果。

## Alternatives considered

- 只把输入校验移到限流前，能修复空白标题，但数据库故障、事务回滚仍会占用全天额度；选择与持久化事务同一口径。
- Redis预占后失败退还可复用限流存储，但进程崩溃、退款失败及多请求同秒需要额外令牌协议；已有用户行锁及工单创建时间足够，不再维护两份成功配额。
- 查询成功后单独清未读改动较小，但会把查询之后的新消息一并清掉；选择同一事务行锁避免这个竞态。
- 仅AbortController取消旧请求不能保证共享Promise或已完成响应不写状态；请求代次作为结果提交门槛。

## Verification

六个复现均转为回归测试：有效收件人、降权/封禁后Root回退与重新指派；失败后重试、成功后仍限额、并发额度、消息写入回滚；附件角色/上传者/内部消息/关闭状态；三种详情读取失败保留未读及并发新消息；筛选、账号、退出与延迟管理员响应。

本地SQLite、MySQL 8.4及PostgreSQL 15通过数据库矩阵，Go相关包全量及工单竞态测试通过。Chrome挂载真实组件并控制响应顺序，验证旧响应不写当前状态；API模拟不替代服务端鉴权测试。浏览器用例接入共享发布前端构建门禁，沿用既有Chrome环境；数据库矩阵沿用MySQL 5.7/8.0和PostgreSQL 9.6 CI。

## Consequences

历史24小时内已成功创建的工单计入新配额，避免升级绕过；已关闭附件需管理员先重开才能删除。消息读取持有短事务行锁，长对话可能增加写入等待。成功准备响应不等于浏览器已收到；物理附件清理失败仍记录日志等待运维处理。
