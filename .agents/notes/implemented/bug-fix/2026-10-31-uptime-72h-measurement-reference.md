# Agent Note: Uptime 固定72小时并沿用最近有效性能值

Status: implemented

## Problem

用户要求“最近24个小时段可用率”展示72小时；测试补充的小时没有真实性能测量，首字延迟与缓存命中率显示空，要求使用最近一次有效值填充。现有24/72查询由性能图表选择器控制，状态条随之缩短；健康存储只有小时汇总，测试证据不携带当前模型的性能。

## Decision

模型详情的Uptime、广场分组健康和旧模型弹窗固定查询72小时，独立于性能/用量图表24/72选择，复用已有会话缓存去重。令牌请求健康窗口不变。

查询利用现有7天健康快照，为每个授权模型/分组范围生成独立的last_valid参考值（首字小时均值、完成小时均值、缓存小时命中率及来源小时）。历史时段只沿用当时或之前有效值，三个指标独立推进；不跨精确模型或越权分组、不用未来值倒填。实际汇总、样本数、请求/测试计数和Uptime口径不改，不落盘填充值。窗口外数据只作性能参考，不纳入当前窗口统计。

Uptime摘要、小时详情、模型行/卡片与性能图表在本指标缺失时展示参考值和“沿用最近有效值”来源时间；已有有效值含0保留，始终没有有效历史的指标仍未知。参考值来自最近有效小时，不能伪称最后一条请求的测量。正常请求健康视图仍使用原始测量。

## Alternatives considered

- 只将24小时标题改为72：数据仍只有24格，不能满足需求。
- 将历史值写进avg/计数：会污染均值、样本量与后续统计；单独提供显示参考。
- 使用其他模型的渠道测试延迟：对应模型性能不同，测试也不能产生有效缓存率；仅使用相同授权范围的实际测量。
- 只在浏览器72小时数组中向后补：不能覆盖窗口前已有值、摘要与批量卡片口径；后端按7天留存提供来源，前端决定显示。

- Go 健康聚合与 controller 回归通过，SQLite 实库覆盖24/72小时查询与批量摘要、窗口前来源、分指标独立推进、有效零值、禁止未来倒填、7天过期、模型/分组权限及原始统计不变。
- 39项相关前端顶层测试通过，覆盖72格、历史来源说明、零值优先、缺失/非法来源与图表单位；ESLint 和 Prettier 通过。
- Chrome 本地明确标识的 fixture 验证72格、24/72图表切换、1.14 s及95.63%补充值、来源时间、当前零值保留、无历史未知与390px下每行24格。未用fixture替代生产指标验收。

- 主站（含生图子应用及5页预渲染）、独立文档站和 Go 服务端构建通过，程序报告 v1.7.0；笔记门禁与 diff 检查通过。

## Consequences

查询读取范围从展示窗口扩大至7天留存，仍为一次有界聚合查询。历史参考不代表当前实测；超过留存范围无来源则不补。API新增可选参考字段，旧客户端继续读取原字段。
