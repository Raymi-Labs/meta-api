# Agent Note: Uptime 按对应渠道测试补充并恢复历史成功证据

Status: implemented

## Problem

生产截图 gpt-6-astra / OpenAI 福利组 07:00 小时有一次真实成功，仍呈灰色。只读核查发现，该组渠道 1465、1561 当小时分别有4次和5次成功测试，但测试模型是 gpt-6.1-sol、gpt-5.6-sol；旧采集只归属被测模型，且上线前测试未进健康表。用户确认：按该模型对应上游渠道测试通过补充，允许测试其他模型，并补最近72小时已有成功证据。

## Decision

实时测试复用真实请求执行/响应校验，按渠道当前配置的全部精确模型与分组记录上游测试证据。仍排除本地预检、用户令牌测试、auto和未配置关系；不改变自动测试频率、不额外调用供应商。

主节点启动后台兼容任务，固定启动时的72小时窗口，分小时读取 LogDB 中渠道测试的消费成功记录（type=consume、token_id=0、token_name/content=模型测试），以 channel_id 关联主库 Ability，而非日志中的管理员分组。每个尚无成功测试证据的分组/模型/小时补一个真实成功证据；确定性ID加冲突忽略，重复启动/并行执行/失败重试不重复计数。实时失败仍保留；不存在成功日志不推断失败或成功。普通健康查询继续只读聚合表，不在每次页面访问扫描日志。

历史归属使用当前配置，不能还原渠道历史改组。已删除配置不补；只代表对应上游曾测通，不声称当前模型被直接测试。历史每小时最多补一条证据，不冒充完整测试调用计数。现有不足30次、每桶最多一个补充样本、真实请求加权、权限和24/72小时窗口不变。

## Alternatives considered

- 不足30次直接按百分比着色：无法说明上游是否测通，也会使无证据时段变绿；不采用。
- 自动逐个测试所有模型：能得到模型直接证据，但增加调用量、成本和调度负担，不符合已确认的渠道口径。
- 只等待新采集：历史已有成功证据仍灰，无法解决截图；补最近72小时。
- 每次请求健康接口扫描日志：扩大接口开销，跨主库/日志库连接困难；后台按小时补聚合证据。

## Consequences
