# Agent Note: K3 冲突用量的结算与快照一致性

Status: implemented

## Problem

61b49b2的用量兼容引入两处边界回归：标准缓存计数为null而别名为80时，流式先复制别名、后处理未清除，非流式却保留未知，两种模式在隔离结算中分别扣48和120；流式快照按prompt_tokens判断总量相同，结算却可采用input_tokens，导致总量变化后仍恢复旧缓存。

## Existing capabilities and impact

- [用量字段保真](2026-09-29-kimi-usage-field-preservation.md)部分重叠：保留标准计数优先、明确零优先、未知不造数及原始冲突字段不覆盖。
- [流式快照](2026-09-29-kimi-stream-usage-evidence.md)部分重叠：继续保留同总量细项，只收紧“两套总量必须一致”的恢复条件。
- [真实验收](../testing/2026-09-29-kimi-live-acceptance.md)与本轮修复独立；不把计费合成回归当成动态工具、视频或三协议上线验收。
- 复用原生Chat的K3归一、handler、日志及隔离数据库回归，不修改DTO公共语义、价格配置、数据库结构或其他模型处理路径。

## Decision

- K3结算中的缓存/思考计数按与来源诊断相同的选择规则重新赋值；unknown、missing、invalid不沿用通用解析器预先复制的别名。内部默认0不写回未知的对外字段。
- K3非流式在本地估算前复用流式已有的总量归一，避免两种模式对input_tokens/output_tokens采取不同来源；不改全局归一函数或原始响应中既有字段。
- 只有当前块和前块各自存在明确、合法、无冲突的对应总量且相等时才允许恢复。两套总量冲突、任一已给出的总量为null/非法，均不能建立可继承的快照。
- 计数不得超过任一明确报告的对应总量；冲突样本不静默选择较大总量放行较大的缓存/思考计数。
- 两项维度独立：输入总量冲突不抹掉有一致输出总量支撑的思考计数，反之亦然。
- K3的负数输入/输出/总token数在通用归一前按无效上游响应处理，沿用失败路径，不使新增的非流式别名归一把负数带入结算。

## Alternatives considered

- **修改共享normalizeOpenAIUsage全局优先级**：可以一处统一所有模型，但可能改变其他供应商既有计费；限定到K3并复用原有总量规则。
- **仅在最后把缓存数清零**：能遮住本次扣费差异，但会丢掉合法计数，也不修复对外SSE已错误恢复旧缓存的问题；同时修复来源选择和恢复条件。
- **总量冲突时把较大的数视为正确并恢复历史值**：兼容范围更宽，但没有证据证明历史细项适用于新的累计总量；不据此猜测。

## Verification

- 正式回归在业务修改前复现null/别名模式不一致与冲突总量恢复；修复后两项通过。之前审查目录保留的原始复现用例也通过Go overlay重跑通过，不修改它们的预期。
- 新增handler矩阵覆盖6种计数证据×2种渠道×JSON/SSE×强制格式化开关，共48个子用例；另有12组快照边界、总量变化的完整handler链路、新鲜计数上界和负数总量拒绝检查。
- 隔离SQLite结算扩展至14种用量形状×流式/非流式：钱包、令牌、消费日志一致。原null冲突用例均扣120内部quota；真实缓存80的正常样例仍扣48；管理员unknown/invalid没有伪造value=0，用户日志不泄露诊断。
- `go test -p 2 -timeout 120s ./... -count=1`全仓通过；Kimi、流式及相关失败退款的定向race重复2次通过；`go build -p 2 ./...`通过。测试使用Go 1.25.1、GOMAXPROCS=2、GOPROXY=off。
- 初次验证仅在本地工作分支。2026-10-17 按最新远端主线整合后，全仓 Go 测试、Kimi/Claude/公共转发相关竞态与后端编译重新通过；后端入口使用临时前端占位资源验证，真实前端与镜像由发布工作流构建。补丁不包含生图/电商改动，未调用收费模型、未操作生产配置或历史余额。

## Consequences

供应商冲突计数会从此前不一致的折扣行为改为一致的保守处理，不自动追改历史余额。上游总量本身矛盾仍需供应商修复；本轮阻止不可信的跨块继承，不声称可以还原真实token数。

不改变共享DTO或其他模型的计费入口；原始冲突总量和未知字段保留，计数诊断与内部结算采用同一依据。只有无冲突、对应总量相等的快照继续复用缓存/思考细项。SQLite验证不是生产MySQL/PostgreSQL部署验收；已确认的客户动态工具、视频和协议兼容问题仍独立待修。
