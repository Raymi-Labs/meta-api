# Agent Note: 个人总览对调用量大的账号返回 503

Status: implemented

## Problem

2026-11-08 用户反馈个人总览弹出「Request failed with status code 503」。只读查看线上容器日志（v1.27.0，容器 19:14 启动）：
- 账号 1（根管理员）打开页面时，活跃日历 `/api/data/self/activity` 连续 4 次返回 503，每次 1.6–2.4 秒。
- 本月用量 `/api/data/self/month` 成功两次，分别用了 13.9 秒和 9.9 秒；慢查询日志显示 `user_id = 1` 的查询光是拿到第一行就要 3–11 秒。另有一次 4.8 秒的 503，原因未能确认。
- 同一 IP 的另一个账号（7352）三项都正常，耗时 0.23 秒。

容器启动后约 47 分钟内，全站 3,201 条消费日志中有 825 条属于账号 1（约每天 2.5 万条），主要来自令牌「yifei的grok」、站点自动翻译所用的「系统翻译 qwen-mt-flash」和「模型测试」。日历逐条扫描近 365 天的留存日志，25 万条上限按设计直接失败、不返回部分数据，所以这个账号每次打开日历都会失败。本月用量同样逐条扫描，越到月底越慢，会超过 20 秒超时或 100 万条上限；它还和管理员看板共用进程内 2 个名额，名额满时也立即返回 503。三个接口失败时都不写服务器日志，只能从耗时推断原因。

本地用 30 万条消费记录复现：旧版日历每次都在 0.23 秒时返回 503，本月用量和令牌概况正常。

## Decision

- **日历历史读每小时汇总**：开启数据看板汇总（`DataExportEnabled`，默认开、线上开）时，日历的历史部分按小时读 `quota_data`（用户 + 时间有索引，一年最多 8,760 个小时行），今天和还没落库的最近一段仍读留存日志。`quota_data` 只由 `RecordConsumeLog` 写入，任务补差和退款走 `RecordTaskBillingLog`，不会进入汇总，所以统计的仍是同一批调用。
  - 汇总每 `DataExportInterval` 分钟落库一次，所以分界点取「已结束满一个落库间隔加 1 分钟的整点」，且不超过包含本地零点的那个整点（`userActivityHourlySplit`）。分界点之后逐条读日志，按实际时间归日，因此今天始终实时准确。
  - 每个小时按开始时刻所在的本地日期归日：整点时区与逐条统计完全一致，半小时时区（如 +5:30）零点前后最多有 30 分钟算到相邻一天。
  - 用汇总时返回 `source: "settlement_hourly_v1"`，前端两个来源都接受。关闭汇总时仍整段逐条扫描（`retained_settlement_logs_v1`），上限和失败行为不变。
  - 25 万条上限现在只作用于逐条读取的那一段。
- **本月用量按天缓存**：按用户本地日逐日扫描、逐日求和。每个已结束的日子在本地零点后 10 分钟才进入缓存，避免零点前打上时间戳、零点后才写入的日志被漏掉。缓存记录的是「本月截至某日的累计计数」，存在 Redis（没有 Redis 时用进程内存），键为用户 ID、时区和月份，不含账号名。每扫完一天就保存一次，所以首次打开时即使某次请求超时，下次也能接着算。以后每次打开只实时扫描今天（零点后 10 分钟内还包括昨天）。
  - 汇总使用同一累加器，逐日求和后再计算缓存率和单价；测试确认与整月一次扫描的结果完全相同。新增 `addDashboardUsageCounters`，有测试保证累加覆盖全部 13 个计数。
  - 活跃天数改为按天判断「这一天是否有计入调用次数的记录」，与原来按记录实际时间归日一致。
  - 每天单独累加，也避开了原来整月共用一个「模型 × 小时」分组上限的问题。
- **名额分开并允许排队**：本月用量不再占用管理员看板的 2 个名额，改用独立的 4 个；本月用量和日历在名额满时都先排队最多 3 秒，仍满才返回繁忙。管理员看板保持原样。
- **记录失败原因**：本月用量、令牌概况和日历失败时写一条警告日志，包含用户 ID 和具体错误，返回内容不变。

## Alternatives considered

- 给 `logs` 加 `(user_id, type, created_at)` 联合索引：查询会快很多，但线上日志表很大，程序启动时的自动迁移会同步建索引，部署期间服务不可用，需要单独安排；而且月底仍要逐条处理几十万条记录。本次不改表结构。
- 只放宽日历上限或延长超时：这个账号一年有数百万条记录，放宽多少都会在 8 秒内跑不完，还会占住数据库。
- 新增按天汇总表并在计费时实时写入：最彻底，但要改计费写入路径、做历史回填和保留期迁移，范围过大。现有每小时汇总已经覆盖同一批调用，足够支撑日历。
- 本月用量也改读每小时汇总：汇总表没有退款，任务补差也不在其中，金额会和原口径不一致，所以本月用量继续读留存日志，只把已结束的日子缓存起来。
- 原日历决策曾明确不回退到 `quota_data`，顾虑在于采集开关、异步落库和补差口径。本次逐项处理：关闭采集时仍逐条扫描；未落库的时段由分界点交给日志；补差和退款本来就不写入汇总。

## Consequences

收益：大账号的日历从必定失败变为毫秒级返回；本月用量首次打开扫描当月已过去的日子，以后只扫描今天；个人总览不再因为管理员看板正在统计而报繁忙；以后出错能直接从日志看到原因。

代价与限制：
- 日历历史依赖每小时汇总：汇总开启之前的时段、进程崩溃时尚未落库的计数不会出现在历史里；如果汇总曾被关闭，对应时段为空。
- 已缓存的日子不会再重算：管理员事后删除某天的日志，本月用量要到下个月才不再计入（键按月份，32 天后过期）。
- 账号 1 的大部分调用来自共享令牌、系统翻译和模型测试，个人统计会显示这些调用；这属于账号用途问题，本次不处理。
- 未加索引，单日扫描的耗时仍取决于数据库的查询计划；按线上 8 天约 10–14 秒推算，冷启动时一天约 1–2 秒。
