# Agent Note: 企业令牌的稳定性优先路由与独立报价

Status: rejected — 2026-11-07 用户决定不做托管方案与独立售价：路由方案让产品多出一套与分组并行的概念；企业价格改用现有用户组专属倍率，多模型用现有分组多选，智能路由对所有令牌按原顺序生效。见[撤回记录](../../implemented/simplification/2026-11-07-withdraw-route-plans.md)

## Problem

用户希望创建令牌后，调用同一模型时自动选择当前稳定且性价比高的分组，并为企业客户保留报价和服务溢价空间。现有 Auto 可以故障回退，但分组同时承载路由范围和销售倍率，动态换组会影响客户费用；按最低分组倍率选路既不能证明最低采购成本，也不能保证稳定交付。

本轮只提出设计，不实现、不更改线上令牌、渠道或价格，不发布应用版本。源码核对基线为公司 main 的 ae7a76425；未读取生产配置、实时流量或采购合同，文中示例和参数均不代表当前实测或服务承诺。

## Proposal

增加可选的托管路由方案：**先满足模型、权限、服务质量和容量约束，再在合格线路间优化预计总成本；企业客户按独立、可审计的价格表结算。** 令牌关联方案，客户端继续填写明确的模型 ID。首期只在同模型、等价能力的已核验线路之间切换，不自动把一个模型换成另一个模型。

### 产品入口与方案归属

创建令牌先选择「手动选择分组」或「智能路由」。手动沿用现有字段；智能选择已授权服务方案，企业方案默认稳定优先。用户只需要看到模型范围、服务等级、输入/输出/缓存等报价、额度及预算。线路池、熔断阈值和利润信息由管理员管理。

第一期只开放一个「企业稳定优先」方案，后续基于实测再开放「均衡」「经济」档位，避免先增加无法说明效果的开关。普通用户只能选择获授权的方案，不能自行修改加价或折扣。企业合同归属于客户账户，令牌引用合同或方案版本；管理员可以为不同项目绑定不同报价。明确报价有效期、变价通知和续约规则。

建议将方案策略与价格分别版本化：策略决定候选范围、质量门槛、总尝试/时限预算和应急线路；价格决定销售分项价格及适用期限。令牌原有总额度、模型限制、IP 等控制继续生效。方案引用、服务端解析与缓存失效需要同批实现，旧客户端省略字段不清除新方案。

### 路由顺序与稳定性口径

1. **资格过滤**：取账户、令牌、方案、模型和渠道许可的交集；核对真实上游模型/版本、协议、工具调用、结构化输出、上下文长度，以及客户约定的地区和数据处理范围。标称同名或分组名叫“企业级”不足以证明等价和质量。能力未知时不进入严格企业池；模型降级必须独立授权。
2. **健康和容量过滤**：按真实供应商故障域、渠道、映射后模型、接口及流式类型观察；必要时按上下文长度/任务类型分层。最近约 1 分钟用于突发异常，5–15 分钟用于趋势，24 小时用于基线，均为待校准参数。连续错误、429、首字/完成时间尾延迟、断流、无效协议终态及当前容量共同判断。为稀疏组合设置分层回退和基数上限，避免无限维度。
3. **合格线路间优化成本**：先满足该模型/工作负载的质量门槛，再比较输入、预期输出、缓存读写、长上下文阶梯、采购时段价格、切换丢缓存及失败重试的预计成本。输出量与缓存命中是估计，保存预测版本与区间；销售倍率不作为采购成本。健康相近时向便宜线路倾斜，但保留容量余量和合格备用线路，不能把全部流量推给最低价渠道。
4. **有界执行与恢复**：复用亲和和原子容量准入；健康亲和线路在允许成本区间内保持会话，故障才切换。以请求开始时确定的总截止时间约束选渠、排队和所有重试，同时设总真实尝试上限；跨组或 VM 容量拒绝不能无限续期。供应商明确执行前拒绝与执行结果不明分开记录。候选选择不增加重试资格。
5. **失败边界**：已有业务输出、工具副作用、previous_response_id 等会话绑定不能通用重放。沿用各协议已有输出保护与已证明安全的例外，不从 HTTP 200 或“还没看到文字”推断可重试。流式中断应明确失败，不将第二条线路的答案拼接为同一条成功回复；异步任务不在首期覆盖范围。

线路健康和客户体验使用两个账本口径：每次尝试都记录结果，不能让重试后的成功抹去前一线路故障；一次逻辑请求另记最终交付、端到端首字/完成时间和重试次数。只把有证据的上游故障用于上游惩罚，本地无余额/权限/输入错误不算上游故障；客户端断开和原因不明单列，不能从客户体验报表消失。业务正确性、模型真实性不能由 HTTP 成功率代替，需要供应商准入与代表性任务验证。

少量样本的 100% 不代表可靠。采用最小样本量、置信下界或保守先验，样本不足和数据过期保持 unknown；具体阈值由流量基线确定，不能把 20/20 成功等同于 99.9% 能力。新线路通过合成探测和隔离验收后低比例引入，严格企业流量默认不承担未经验证的探索。熔断恢复采用限量半开，连续恢复后逐步加流，并设冷却、最小驻留/切换收益阈值，防止抖动。

后台周期性维护内存/Redis 快照，主请求只做有界读取和原子准入，不逐次扫描消费日志或同步查询供应商财务接口。多实例共享健康状态、半开配额与容量；共享后端异常沿用既有准入保护。指标失效时只可使用方案预先允许的、最近已验证的保守备用策略，不能将未知线路当健康或越权。没有合格线路时返回可解释失败；放宽质量门槛或超过应急采购预算须由方案事先规定并记录，不临时暗改。

### 企业售价、采购成本与应急预算

企业固定的是**每模型、每计费项的合同单价**，实际账单仍随输入、输出、缓存、图像等真实用量变化。不能承诺每次请求固定金额。客户看到同一价表，后台换到较贵线路不会临时提高本次客户单价；若合同允许动态加价，需另设明确的封顶与事先选择，首期不采用。

分别保存：销售价快照与版本、实际路由组/渠道/上游模型、每次 attempt 的预计采购成本及后续核实成本。请求接入时锁定销售规则，在所有重试中保持；预扣、补扣、结算、退款使用同一快照和稳定结算 ID。正常完成的一次逻辑请求只结算一次销售用量；失败/取消/部分交付按明确且经过测试的产品规则处理，不能将多次上游尝试全部重复出售。采购侧则必须收集失败尝试可能发生的费用。

报价应从保守成本预算反推：

`目标单价 =（正常采购成本 + 预计故障切换成本 + 支付/汇兑成本 + 服务保障预算）÷（1 − 目标毛利率）`

这是报价模型，不是已核实利润。净到账折扣、赠送额度、退款、采购手续费等与既有 cash 账本保持统一定义，不能重复扣费用。例：同一模型、同一用量组合的综合成本预算 7 元，目标毛利率 30%，示例售价 10 元；若应急调用实际成本升至 12 元，该次会亏损，应由预留保障预算覆盖。**不能为守住每单利润而暗中拒绝合同已经包含的备用线路。** 在合同容量及保障范围内优先履约，超出范围按预先约定限流/排队/报价处理。

企业可谈「按量价＋月度服务费或最低消费承诺」：服务费对应真实的备用容量、监控告警、对账和响应支持，量大通过承诺用量换取阶梯折扣。容量预留需供应商确实提供或平台自行留余量，静态优先级不能包装成供应商保证。未知成本线路先人工设置带有效期的保守成本上界，超过期限停止成本优化资格，不填零。

为避免“便宜优先”耗尽应急成本，策略明确普通预算、应急预算与最大负载。管理员查看客户/方案维度的净收入、全部尝试成本、备用命中、估算覆盖率和预算消耗；报价页、令牌页、模型目录、测试及使用日志应共同使用销售价契约，管理员另见实际线路成本。

### 可承诺范围与第一期交付

自动路由能减少单线路故障的影响，无法保证绝对稳定。两个分组可能共用同一个供应商、账号池、区域、入口或支付余额；备份至少要核实故障域独立性，且演练主线路退出后的剩余容量。站点自身 DNS、入口反代、应用、数据库、Redis、网络和计费依赖仍可能是单点，必须纳入端到端故障演练。

先定义并测量内部 SLO，再谈外部 SLA：明确适用模型/协议/负载、逻辑请求最终有效交付率、P95 首字/完成时间、流中断率、测量边界、排除项、统计窗口、承诺吞吐及补偿方式。99.9% 仅可作为候选目标，不能从历史成功率或路由算法直接承诺；请求成功率也不能直接换算为每月停机分钟数。

分阶段建议：

1. **观测与影子决策**：补每次尝试事件、供应商故障域、采购价和预测成本；只记录推荐候选及理由，不改变调度。对照现有用户体验与完整成本，明确未知数据比例。
2. **企业试点**：只接少数明确模型/协议、已验证的两个独立供应来源；独立销售价表和管理员授权令牌，同时上线预扣/结算一致性。先隔离故障演练，再限量真实调用；无自动跨模型或图片/视频任务扩展。
3. **扩大与商业化**：满足预先约定的完整业务周期、负载与故障演练验收后开放更多模型；基于数据确定档位、价格、容量和 SLA。实现、正式版本制品、生产部署、真实客户验收分别报告。

## Alternatives considered

- 继续配置现有 AutoGroups 顺序：可立即使用现有回退，改动和风险最小；适合作为短期人工管理方式，但不能响应近期质量差异，企业销售价格仍随实际组变化。
- 按分组 24 小时成功率过滤，再取最低倍率：实现最简单、能利用现有界面数据；小时汇总掩盖突发和组内重试，分组内不同模型/渠道差异很大，倍率又是销售口径，因此不能作为企业调度核心。
- 用成功率、延迟、价格做单一加权分数：便于排序和调参；足够便宜的劣质线路可能用低价抵消质量罚分。选择先执行硬性资格/质量约束，再在合格集合优化成本。
- 把企业方案直接做成一个固定倍率分组：能较快形成稳定售价，并让多个渠道在同组内回退；可用于最小人工试点，但不足以表达客户合同版本、不同模型分项售价、跨组采购选择和全部尝试成本。正式实现采用方案/售价上下文，底层仍复用现有渠道池。
- 对每个请求同时请求两家并取最快：可能改善尾延迟；会增加采购成本、容量压力、数据发送范围与重复副作用，取消也不保证免收费。首期不采用，可在将来限定无副作用请求并设预算后单独设计。

## Acceptance criteria

- 新旧令牌创建、编辑、旧客户端省略字段、撤权、方案停用和缓存更新行为明确；目录、测试、实际调用的模型/组/渠道权限交集一致。方案编辑只允许管理员，客户日志不暴露采购价或其他租户信息。
- 构造低价不健康、高价健康、低样本 100%、陈旧数据、同供应商多分组、冷启动、价格缺失及上游满载，验证无越权和错误兜底；同一时刻多实例半开、容量与重试预算受控。
- 验证首尝失败后成功分别进入尝试指标与逻辑请求指标，P95 不由均值假造；取消/未知/本地拒绝归因、非流式/流式终态、工具调用和会话绑定均有端到端验证。
- 以高低价格线路切换、跨时段/合同变价、部分用量、全部失败、超时结果未知、并发退款与结算重放验证销售快照；销售一次结算、采购多尝试计成本，账目可追溯且未知成本不填零。
- Redis/统计后端故障、网关重启、主供应来源退出、代理故障、共享配额耗尽和客户重试风暴经过隔离演练；测量额外调度延迟、队列和容量余量，给出真实可用率与成本对照后再扩大。
- 运行相关 Go/前端、并发及故障注入测试；新增持久字段与结算路径须验证 SQLite、MySQL、PostgreSQL，生产同引擎/排序规则验收不能由 SQLite 替代。同步功能地图和相关 implemented 笔记，再按已有流程发布；生产仍走受保护入口。

## Risks

采购价与上游实际扣费可能不同，未知输出/缓存和失败收费使单次利润不可保证；必须持续核账。短窗口与小样本会误判，过度切换会损失缓存，过度集中会诱发限流；需要影子评估和限量放开。独立报价改动影响预扣、重试、退款、日志与目录，是跨模块计费工程，不能仅改创建页开关。

两个渠道不必然是两个故障域，备用容量也不自动存在；全站基础设施故障无法由供应商路由修复。流式已经输出后无法通用无缝恢复，不能以重试承诺绝对稳定。当前未审计线上供应商组合、真实采购成本或客户目标负载，报价数值、阈值、SLA 和时间安排都需后续数据确定。
