# Agent Note: 上游账户按到账资金分摊现金收益

Status: proposed

## Problem

用户要求在账户管理展示上游账户带来的实际收益，并选择“按真实到账资金分摊，计算现金利润”。本站 quota 扣费、OpenRouter credits 支出和真实收付款是三个不同的计量对象，不能简单相减后称为现金利润。

当前生产只读核对发现：OpenRouter 渠道存在多个渠道共用调用密钥；历史成功订单中有缺少实付金额/币种的记录；兑换码既有管理员发放，也有钱包购买。已有字段不足以重建每次消费的完整现金来源。本提案保留完整路线图；首阶段已按 [现金账本与工作台](../../implemented/feature/2026-11-03-upstream-cash-ledger-v1.md) 落地，生产部署单独验收。

## Proposal

在现有账户管理内增加“收益”视图，先支持 OpenRouter，再让其他上游适配相同的资金与成本契约。保留原有余额和消费明细。主指标采用**现金贡献利润**，表示已分摊净到账收入减对应上游现金成本及已录入的直接费用；不是当期现金流，也不是包含所有公司开支的净利润。

### 现有能力及复用范围

| 链路 | 已有能力 | 缺口与设计处理 |
| --- | --- | --- |
| 页面 → 路由 | `UpstreamAccounts`、管理员 `/api/upstream_accounts`、`controller/upstream_account.go` | 复用账户和管理员权限；收益查询、账单导入和映射编辑仍需新增并审计 |
| 上游数据 | `model/openrouter_account.go` 的 credits/activity；已有加密账户凭据与快照 | credits 是购入额度，activity 是消耗 credits；缺少真实购款、手续费、汇率凭据和持久日账 |
| 本站扣费 | `controller/channel_usage.go`、`model/channel_usage.go`、`model/log.go`；日志按渠道/时段聚合 | quota 不是现金；日志可清理、分库，不能作为唯一资金账本或跨库事务依据 |
| 在线收款 | `model/topup.go`：PaidMoney/PaidCurrency、PresentmentMoney/Currency；`model/payment_record.go` 联合订单显示 | provider 回调金额不保证银行净结算；缺少手续费、实际结算状态、提现/结算汇率与现金流水证据 |
| 权益来源 | `model/redemption.go` funding_source、钱包转赠；`model/subscription_issuance.go`、`model/subscription.go` | 权益发放与现金来源不是一一对应，需保留资金成本随转移/退款的血缘 |
| 退款/风险 | `model/payment_risk_case.go`、权益回收与任务退款日志 | 权益回收不等于现金已退款；消费退款和收款退款分别冲销，不重复扣减 |

`tiered_cost_usd` 是本站销售计费中间值，不是供应商账单成本。当前渠道配置、当前汇率和当前套餐价格均不能回算历史现金。

### 页面与口径

- 顶部：账户、时间范围、原币/折合人民币、UTC 结算日、最近同步和核实进度；默认最近 7 个完整 UTC 日。今天单独标记“待结算”，不与已核实区间混算。
- 四个主指标：分摊净到账收入、上游现金成本、现金贡献利润、利润率。利润率分母为同范围分摊净到账收入；零收入时显示破折号。
- 趋势：每日分摊净收入与上游现金成本、利润；可从某日进入来源明细。日/账户/模型维度必须使用同一时段、币种、归属与核实状态。
- 明细：账户/模型/渠道的收入、成本、利润、核实状态、分摊方法与覆盖率。渠道共享密钥时只能显示有依据的分摊估算，不能标记精确实测。
- “待核对”：缺少收款手续费/币种、旧余额来源、未绑定密钥、站外用量、未匹配请求、待支付退款、BYOK 外部账单等；每项有影响范围和补录入口。
- “现金流”单列客户实际到账和上游实际付款；尚未消耗的预付款保留余额，不一次计作成本。充值发生日和消费归属日分别展示。
- 缺失数据不补零。只展示双方范围匹配的已核实部分利润；不能核实的全量利润显示“待补齐”，同时列已知收入和成本，避免隐藏已知支出。估算结果单独切换，不能混入已核实总额。覆盖率同时给出请求数、扣费额度和上游费用的可核实占比，不能只给一个模糊百分比。

### 收入分摊：资金批次与固定规则

1. 每笔确认到账生成不可变资金批次：订单/支付事件 ID、原币实收、支付手续费、净到账、实际发放权益、成交/结算时间、汇率及证据来源。已收款未结算可显示“待结算”，不得冒充已到账。相同支付事件及订阅在 top_ups 的镜像记录必须去重。
2. 钱包按资金批次先入先出（FIFO）分摊。选择 FIFO 是为了让每次分摊可追溯到明确收款；这是收益分析规则，不改变用户实际扣费或额度优先级。示例：实收 100 元、支付费 2 元、发放 120 单位，消费 12 单位分摊净收入 9.8 元，余额保留 88.2 元现金基础。政策与分母一经入账即快照，尾差留在批次最后一次分摊。
3. 明确无偿的赠送/签到/奖励按零现金基础；管理员兑换码不能一概视为免费，可能是站外出售，需关联实际收款，否则标记来源未知。钱包购买兑换码、商品令牌、转赠等继承原资金批次和剩余现金基础，不新增收款、不重复收入；转赠过期返还同一基础。付费兑换套餐同样保留来源。
4. 旧余额建立“待核实期初”批次，不能按零成本或当前售价补齐；仅在付款、赠送、退款、转移和消费记录完整且余额闭合时回放确认。手工确认需凭证、操作人、原因和不可覆盖的修订记录。
5. 定额不重置套餐按快照权益分摊；重置/不限量订阅按服务期划分净到账预算，期内按实际使用的计费额度权重分摊到渠道。开放期只能暂估，期末封账；无使用预算单列未归属订阅收入，不强行归给某个上游。续费、叠加、重置、提前取消必须按权益事件快照切段，不能用当前 plan 覆盖历史。套餐到期未用收入的归属单列，不虚增渠道收益。
6. 消费撤销关联原分摊并返还原资金基础；支付退款/拒付用独立资金负向事件，区分未消耗余额回收与已确认收入冲减。退款重试幂等，已支付手续费是否退还以实际凭证为准，不能因额度回收推断现金已退。

### 成本与渠道归属

[企业托管路由与独立报价](../architecture/2026-11-05-managed-token-routing-and-pricing.md)提案将复用本篇逐次成本和核账边界；运行时预计成本不作为已核实现金利润，合同销售价另行版本化。

- 新增账户与渠道密钥指纹的有效期映射；管理密钥不等于推理密钥。读取官方 keys 元数据取得 hash，并用 `activity?api_key_hash=...` 核对作用域，服务端保存映射，浏览器不接收密钥明文。共享密钥、账号重复录入、跨账户重复绑定均需检测。同一 key 在其他应用使用时无法自动判定全部本站成本，差额进入“未归属成本”。
- 先按账户/密钥/UTC 日/上游模型对账。模型使用调用时的真实 upstream model 与供应商标识，禁止拿当前 model_mapping 回填历史。切换渠道、轮换密钥和删除渠道保留历史映射。
- 精确渠道成本需要逐次上游 attempt ID / generation ID 与实际供应商费用；先核对 relay 是否能稳定采集，再设计持久采集与异步核账。一次本站请求的重试和失败但上游收费都要计成本；不能只统计最后成功渠道。缺少精确费用时仅允许显式估算；不得按请求数粗分不同模型/缓存/长短输入的成本。
- activity 保存最后 30 个完整 UTC 日的日账，并滚动重拉覆盖迟到调整；日账写入有稳定复合键和版本，重新同步不累计加钱。超过公开窗口的历史需账单导入；当天只展示待结算。
- OpenRouter 充值现金批次记录购入 credits、实付原币、充值手续费、实际汇率和到账日期，消费 credits 按批次现金基础转为成本。当前 credits/activity 不含这些支付凭证，提供受审计的账单导入/补录；不能用 total_credits 当实付款。BYOK 外部推理费用必须单独接入对应供应商账单，避免重复计 OpenRouter 服务费。
- 原币永远保留；折合人民币采用每笔实际结算/购款汇率，未知时允许显式人工估算并保留版本。充值手续费包含在上游批次现金基础，客户支付手续费已扣入净收入，不再在利润中扣第二次。
- 推荐把服务器、人工等间接开支放到可选费用分摊页；未录入时页面明确成本范围，不能把现金贡献利润命名为公司净利润。

### 数据与执行架构

建议主库新增资金批次/事件、消费分摊、上游购款批次、费用与冲销事件、有效期映射；上游日账与对账结果可同库持久化。金额用定点或 decimal，原始金额与归一化金额分开，跨 SQLite/MySQL/PostgreSQL 使用 ORM，不依赖 JSON 专属运算。所有外部/账单事件以稳定来源 ID 幂等处理；修订追加冲销与替代版本，不覆盖已封账结果。

复用现有账单、账户 CRUD 和渠道统计入口，但不能只靠定时扫描会删除的 logs 构建资金账。先以旁路账本采集确认支付、权益变化和计费事件，建立稳定结算 ID 与重放点；对现有 Redis/批量额度落库路径明确持久事件边界及对账补偿方案，不能假称已经有跨库原子性。影子核账不影响推理；事件缺失、跨库延迟、待补偿时相应利润保持未核实。完成账本闭合后再开放已核实指标。

只向管理员开放财务查询；账单导入、期初确认、改映射使用独立写权限和审计记录。未来 API 明确返回金额是否已知、核实状态、覆盖范围、UTC 区间、原币、汇率版本、同步时间及来源引用，不用 null/0 隐式混用状态。详情避免泄露用户隐私、支付凭据和调用密钥。

### 分阶段落地

1. 已完成 activity 日期兼容与设计。首阶段实现资金批次、净到账及购款凭证、密钥归属、持久日账、三页工作台和完整范围的账户收益；上游采用 UTC 日加权平均，详见首阶段笔记。以下更完整血缘、精确逐次成本与封账仍为 proposed。
2. 补齐资金来源与上游购款录入、映射及持久日账，先显示现金流与待核对项；对现有数据只做可解释的历史回放。
3. 影子账本通过支付/权益/消费/退款闭合后，开放账户级已核实现金贡献利润；仅完整范围可计算。
4. 补齐逐次上游成本与订阅封账后，开放精确渠道/模型利润；缺少数据时保持估算标识。每阶段独立评审、测试和发布，正式上线另走受保护入口。

## Alternatives considered

- 本站 quota 折 USD 减 activity：可以立即出图，但赠送、充值折扣、手续费、汇率及套餐会导致伪利润，不符合用户现金口径。
- 全站充值按当日调用比例分配：实现简单、可快速看到趋势，但把未消费的预付款和不同日期、不同来源的用户消费混在一起，不能核实单个上游收益。
- 钱包移动加权平均：平滑且聚合成本低，但原支付退款和跨用户转移仍需批次血缘；本版优先 FIFO 的逐笔可解释性，政策写入版本，不在运行中任意切换。
- 独立重写财务系统：可隔离业务，但复制已有支付、权限和权益处理容易重复记账；扩展既有事件来源与账户入口，单独持久分析账本。

## Acceptance criteria

- 示例可从净到账到账户利润逐笔复算；每个资金批次的已分摊、余额、转移、退款/冲减合计守恒，不重复确认支付镜像订单。
- 覆盖充值折扣、赠送、站外售码、钱包转赠、令牌商品、期初未知、套餐续费/重置/到期、部分退款、拒付、无手续费凭证、多币种与尾差。
- 同一 key 多渠道、轮换 key、外部使用、模型映射、失败重试收费、BYOK、跨 UTC 日、迟到调整及重复同步均不漏算或重复计费。
- 主/日志数据库分离、批量额度更新、多实例并发、事件重放与日志清理后账本可闭合；MySQL 同生产 schema 的迁移演练及 SQLite/PostgreSQL 兼容检查齐全。
- 看板汇总、趋势、明细及导出在同一筛选下相等；分页不影响总额。未知/估算/已核实、空数据、同步失败和权限边界有完整用户流程验收。
- 每阶段明确已实现、估算及未具备的能力；发布、附件验证与生产部署分开报告。

## Risks

历史证据可能永久缺失，不能承诺历史全量精确；共享密钥可能包含站外调用，账户总成本不能自动全部归属本站；实际结算凭据、退款状态和购款汇率需要补录或额外接口。旁路账本与实时余额的最终一致性必须用可复查的差异队列和封账条件控制，不能靠“后台稍后同步”直接把利润标为准确。
