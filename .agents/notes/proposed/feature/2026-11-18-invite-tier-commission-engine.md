## Problem

运营方给出了一份内部推广返利结算规则（内部文件，不在仓库、界面或注释中复述原文与风控上限表），要求把现有“一级/二级固定比例”的邀请返佣改为按推广者档位分配：普通、晋级档 A/B、宣传专员、部门成员、宣传部长六档，一级比例、二级比例与注册奖励随档位变化；二级比例同时取决于二级收款人身份和一级用户档位；部门成员业务由所属部长提取团队分成；首次达标充值给专员/部长额外奖金；每笔推广支出受固定返利池比例约束；二级按被邀请人每月有限基数计算。

现状只能表达“全站统一的一级比例 + 二级比例”，无法区分档位、无法表达部门关系与上游切断、无法限制二级月基数，也没有晋级/降档考核。同时用户余额与台账金额大量使用 32 位 `int`，单个大额推广账户累计后存在溢出风险。

## Existing capabilities and impact

- 入池：[台账与结算](../../../../model/invite_commission.go) 在支付事务内调用 `enqueueInviteCommissionWithDB`，按实付金额折算 `base_quota`，一级取 `InviterRechargeCommissionRate`、二级取 `InviterRechargeSecondLevelCommissionRate`；排除自邀与成环；`(topup_trade_no, inviter_user_id)` 唯一键配合 `OnConflict DoNothing` 保证幂等。入口来自 `model/topup.go` 三处与 `model/subscription.go` 一处，兑换码不入池。
- 结算与冲回：同文件的 worker 路径（`service/invite_commission_settlement_task.go`）按 `next_retry_at` 结算到 `aff_quota`，支付撤销时 `reverseInviteCommissionsByTradeNoTx` 先扣 `aff_quota` 再扣钱包；时效与账单拆到 [结算账单笔记](2026-11-18-invite-commission-statements.md)。
- 绑定与注册奖励：`model/invite_binding.go` 在注册事务内按 `InviteBindingSettings` 决定是否绑定，并一次性发放 `QuotaForInviter`/`QuotaForInvitee`。
- 配置：`common/invite_binding.go` 的 atomic 配置 + `model/option.go` / `controller/option.go` 的校验模式可复用；`GetOptions` 会隐藏以 Key/Secret/Token 结尾的键，新键命名避开这些后缀。
- 统计与界面：`model/user.go` 的邀请汇总/明细 SQL 只认识 level 1/2；前端 `InviteCommissionModal`、`InvitePromotionModal`、`WithdrawalModal`、管理员 `UserInviteRelationsSheet` 展示现有口径。
- 已有笔记：[及时到账](../../implemented/feature/2026-10-31-invite-realtime-settlement.md) 拥有 pending 台账、唤醒/补偿 worker 与金额快照决策，本提案扩展而不推翻其事务与锁顺序；[邀请推广](../../implemented/feature/2026-10-22-invite-promotion.md) 拥有推广素材与点击统计，不受影响。风控与身份另见 [推广者风控笔记](2026-11-18-invite-promoter-risk-identity.md)。

## Proposal

### 档位与配置

- 新增 `InviteTierSettings`（JSON，atomic 存储）：总开关 `enabled`、返利池比例、六档一级比例、二级矩阵（收款人身份 × 一级档位，成员额外带部长位）、部门团队分成比例、达标奖金比例与金额门槛、二级月基数（元）、晋级人数门槛、各档注册奖励（以站内展示单位计）与最低提现额（分）。默认值取内部规则，但仓库只存配置默认值，不写说明性表格；二级容量一律由“池比例 − 一级比例 − 奖金预留”推导，不单独存表。
- 保存时逐组合校验：一级 + 奖金预留 + 二级（含部长位）≤ 池比例；成员一级 + 团队分成 ≤ 池比例；比例均在 [0, 1]。校验失败拒绝保存并记录管理员日志（复用 `RecordLogWithAdminInfo`）。
- `enabled=false` 时完全沿用旧比例与旧注册奖励；开关只影响开启后入池的支付，已存在的 pending 台账按原快照结算。

### 档位判定

- 新增推广者档案表（每用户最多一行）：人工档位（专员/成员/部长）、生效月份、所属部长、上游切断标记与时间、管理员覆盖档位及截止时间、提现冻结标记。
- 新增被邀请人资格表（每个被邀请人一行）：首次成为“有效用户”的时间、月份、当时的直接上级与来源支付。它同时驱动晋级人数、注册奖励与成员 30 日无新增检测；来源支付被撤销时资格失效，可重新获得。
- 业绩档：当月档位 = max(上月邀请成功数对应档, 本月实时邀请成功数对应档)，实现“达标当月起享受 → 次月考核 → 第三个月起降档”。人数按直接下级、资格月份统计，带 `(inviter_user_id, qualified_month)` 索引。
- 宣传专员：审核通过当月及次月享受；之后每月按上月业绩续期，上月未达 B 门槛则降为上月业绩档；保级门槛可配，0 表示长期有效。管理员可撤销。
- 部门成员：B 档及以上申请、审核通过当月生效，签约即永久切断原奖励链上游；主动退出次月生效，连续 30 日无新增邀请成功由每日任务移出；退出后回到宣传专员档，下游绑定不变。部长直接申请，审核通过即为顶级节点并永久切断上游。部长与成员的绑定不形成邀请链。
- 管理员覆盖档位优先于以上判定，到期自动失效；所有人工变更写管理日志。

### 单笔分配（支付事务内一次计算并快照）

1. 被邀请人 C 的本笔支付须满足有效消费“三选二”（判定时点与风控排除见风控笔记）；不满足且无法事后补足的直接不入池。
2. 一级 X 按其档位取一级比例（level 1）。X 为成员时，所属部长按团队分成比例取 level 4，X 无二级。
3. X 为专员或部长、本笔达到达标金额且 C 尚未领过达标奖金时，X 另得 level 3 奖金；“每个被邀请人只触发一次”用可空唯一键列在数据库层保证，奖金被撤销时释放唯一键，允许下一笔达标充值重新触发。
4. X 保留上游（未切断且非成员/部长）时存在二级位：容量 = 池比例 − X 一级比例 − 本笔奖金预留。二级收款人 Y 取矩阵值；Y 为成员时成员位归 Y（level 2）、部长位归 Y 的部长（level 5），两者合计不超过容量；Y 为部长时合并值全部归 Y，不另计团队分成。
5. 二级与部长位共用被邀请人当月基数：用 `(invitee_user_id, month)` 计数行加锁占用，超出部分不产生二级收益；撤销时释放已占用基数。
6. 注册奖励改为被邀请人首次成为有效用户时生成 level 6 台账，金额取 X 当时档位；开关开启后注册事务不再一次性发放 `QuotaForInviter`（被邀请人自己的奖励不变）。
7. 每行台账快照：收款人档位、规则版本（`amount_version=2`）、结算周期、账单到期时间；二级空缺或容量未用完的部分不写台账，自然留在平台。
8. 唯一索引改为 `(topup_trade_no, inviter_user_id, commission_level)`，删除旧的两列唯一索引，`OnConflict` 列同步修改，保证部长同时拿 level 4/5 或同一人多角色时不互相吞掉。

### 金额宽度

新表金额一律 `int64` + `type:bigint`。`users.quota/transferable_quota/used_quota/aff_quota/aff_history`、台账金额列、日上限计数、提现额度列扩到 bigint：MySQL/PostgreSQL 依赖 GORM 迁移器在类型不一致时自动改列，SQLite 列类型亲和天然容纳 64 位整数，跳过改列避免重建大表。Go 字段改 `int64` 的调用面较大，按编译错误逐处改写并保留现有日志格式。

### 开放决策

1. 档位来源：普通/A/B 自动考核，专员/成员/部长人工审核，管理员可带期限覆盖。➡️ 采用。
2. 降档公式：当月档位 = max(上月业绩档, 本月实时业绩档)。➡️ 采用。
3. 专员保级：按规则每月考核，上月未达 B 门槛降为上月业绩档；门槛可配，0 为长期有效。➡️ 按规则考核。
4. 上游切断：签约成员或成为部长后永久切断，退出部门不恢复。➡️ 永久切断。
5. 比例配置：JSON 配置并在保存时校验所有组合不超过池比例。➡️ 采用。

## Alternatives considered

- **在现有两个比例选项上叠加档位倍数** — 改动最小、迁移最少；但二级比例同时依赖收款人与一级档位、成员还要拆出部长位，倍数无法表达矩阵，也无法保证每种组合不超池，放弃。
- **结算时按收款人当时档位重算金额** — 档位变化可即时反映到未结算台账；但同一笔支付的金额会随考核结果漂移，冲回、对账与异议都无法复现，且与已实现的“支付时金额快照”决策冲突，放弃，改为支付时快照。
- **用 Redis 计数维护二级月基数与达标奖金去重** — 性能好；但计数必须与台账同事务提交/回滚，Redis 无法与三种数据库事务原子，失败补偿复杂，放弃，改用数据库计数行与可空唯一键。
- **把用户金额列改成 decimal** — 精度直观；但现有额度全部是整数语义，decimal 会改变大量扣费/统计代码与索引行为，bigint 已有先例（`PulsePaidQuota`、发票金额），选 bigint。

## Acceptance criteria

- 开关关闭时，现有返佣、注册奖励、汇总接口与前端行为逐项不变（现有测试全部通过）。
- 开关开启时，内部规则中的七个计算示例与二级对照组合均有表驱动测试：一级、达标奖金、团队分成、二级成员位/部长位、二级空缺、月基数截断、首次达标唯一、撤销释放基数与奖金唯一键。
- 配置保存拒绝任一组合超池或比例越界，错误信息不泄露容量表；管理员日志记录前后值。
- 档位判定覆盖：首月达标即生效、次月考核、第三月降档、B 降 A、专员保级/降档、成员主动退出次月生效、30 日无新增移出、上游永久切断、管理员覆盖到期。
- SQLite / MySQL / PostgreSQL 三库迁移通过：新表、索引替换、旧库 int 列扩宽后可写入超过 2^31 的值；并发重复支付回调不重复入池，`-race` 通过。

## Risks

- 扩宽 `users` 金额列在大表 MySQL 上是锁表 DDL，需在低峰执行并提前备份；回滚只需旧版本继续读写 bigint（GORM 读取到 int 字段在 64 位平台不丢失，超过 2^31 的值才会受影响）。
- 档位判定依赖资格表；历史用户没有资格记录，开启后历史下级不计入晋级人数，也不补发注册奖励（与“无台账历史不补发”一致），需在发布说明告知运营。
- 部门、专员审核与管理员覆盖属于人工流程，误操作会改变后续入池金额；只影响开启后、变更后的新支付，已入池台账不重算。
- 唯一索引替换在旧库存在重复数据时会失败；迁移前先检查重复并在日志中给出可执行的清理提示，不自动删除数据。
