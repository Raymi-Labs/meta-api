# Agent Note: VM2API 实时容量接入渠道准入与有界等待

Status: proposed

## Problem

VM2API 的 Claude 池容量随账号健康和额度变化。中转目前只读取渠道静态 max_concurrency，无法据此变化调整派发；瞬时超额可能变成用户最终失败。目标是复用现有渠道准入、亲和与有界等待，减少可避免的容量拒绝，不承诺任意并发都成功或任意会话零等待。

源码核对基线：Raymi-Labs/meta-api main，397a9aa1e2bd441fbc8abaa86955e472c317a8cc。VM2API 接口基线为 hotsu32/vm2api 的 feat/channel-capacity，8dae99a19ce96f08e9f685f8c7628891eb1d0f4c；该接口尚未部署生产。

## Existing capability review

- middleware/channel_concurrency.go 已有 Redis Lua 原子 Lease/RPM、续期、释放、进程内单实例模式和压力排序；不新建信号量服务。当前非正并发值表示无限制，动态零容量必须有独立拒绝状态。
- controller/channel_concurrency_relay.go 已有满载换渠道、全部满时有界等待、客户端取消、亲和优先等待。默认总等待 3000ms、亲和等待 2000ms；全局开关默认关闭。现有队列是轮询竞争，不是严格 FIFO，队列人数上限是进程本地指标。
- controller/relay.go 已在每次尝试结束释放 Lease；service/channel_retry.go、channel_rate_limit_cooldown.go 和 channel_model_circuit.go 管理重试、429 冷却、故障熔断。容量错误需先分类，不能直接走所有普通故障副作用。
- 后台已有渠道编辑的 max_concurrency 与 /api/channel_concurrency/stats，但只显示正占用渠道；前端把非正上限回退为默认值，不能直接用于显示动态零容量。

## Proposal

### 1. 范围与配置

只给显式启用的单 Key Claude VM2API 渠道增加能力源 vm2api；其他渠道和全局默认保持原行为。沿用 channel.setting JSON，建议增加 upstream_capacity.enabled、overflow_policy（reroute/wait）、max_wait_ms，不增加数据库列或新服务。启用要求原渠道并发控制开启，不允许静默绕过。

第一版仅支持一个配置渠道代表同一个上游 Base URL + 调用 Key；多 Key 轮换渠道不允许启用。同一上游 Key 的重复渠道配置应检测并拒绝启用，避免按 channel_id 重复放大额度。外部其他 Key 共享 VM 账号的占用可由快照反映，但不宣称跨 Key 的精确联合调度。

### 2. 容量读取

新增小型 service 适配器，读取 GET /v1/channel/capacity?model=实际上游模型，以已有渠道调用 Key 鉴权，不接触管理 Key。复用渠道代理与受控 HTTP 客户端；固定同源路径、不跟随携带凭据的跨源重定向，不允许任意探测 URL。正确处理 Base URL 带 /v1 的情况。

模型解析复用并核对 ResolveChannelUpstreamModel 与最终请求映射一致。缓存按渠道、配置版本、实际模型区分；Key/Base URL/模型映射变化立即失效。只刷新启用且近期活跃的模型，刷新合并、有限超时、限制响应体大小、拒绝未知 schema/非法数值/未来或过期时间。遵守 max_age_ms；每个 Key 汇总查询不超过 VM2API 的 10次/秒限制，不按用户请求逐个查询。

多实例时复用已有 Redis 共享快照和短刷新锁，限制旧响应覆盖新状态；无 Redis 仅承诺单实例。Redis 开启但故障时不私自退回各实例独立放行。

### 3. 准入口径

候选派发上限 = min(中转原静态安全上限, VM effective_admission_limit)。多个模型共用同一渠道的 Lease 集合，不能每个模型各放一份额度；每次原子申请都使用当前请求模型的有效限制。不同模型的资格可能不同，已有其他模型占用过高时允许保守阻塞，不声称模型间容量可简单相加。

available_now 已扣除 VM 侧占用，只作为即时可用性与排序信号：为零时先等待刷新或换渠道，不再减中转在途数，也不能把它当成渠道总并发上限。原子 Lease 只保证中转自身的动态上限，不能把快照变成上游预留；更新间隙、外部占用与会话资格仍可能造成竞争拒绝，由 VM 最终门禁裁决并走下面的短时过载处理。

动态零、未知与静态继承值 0 分开表达。已知容量为零不派发；过期、超时、503、partial 且无可用容量均临时不可准入，不沿用过期高值或回退默认100。partial 且有已知容量只使用保守的已知部分。容量下降不取消既有流，恢复后重新准入。静态安全上限仍会限制后续扩容，后台明确展示该限制。

普通选渠、亲和选渠、候选排序与所有可触达该 Claude 渠道的转发路径共用该准入，不只替换 ResolveChannelMaxConcurrency 一个函数；该函数当前既无模型参数，也不能区分未知和零。

### 4. 排队与分流

- reroute：满载时立即尝试权限范围内其他渠道；该策略对目标渠道不额外做亲和等待。其他渠道也无容量时，仍受现有总等待预算约束，不无限重试。
- wait：优先在目标 VM 渠道有界等候，建议该渠道先设30秒，保留全局等待人数保护；到期后在剩余请求预算内尝试其他合法渠道，或给出明确超时。不是修改全站默认3秒。

一个请求共用总截止时间与重试预算，不能每轮重试重置30秒。队列中不持有执行 Lease，派发后才占用；取消/断开立即退出。等待满、超时仍可能最终失败，不能承诺20个请求全部成功。流式复用现有保活，但心跳不等于模型输出；非流式核对客户端和反向代理超时。保留原会话标识、请求体、cache_control 和权限/分组规则。

### 5. VM 容量错误单独处理

仅对启用渠道精确识别 channel_capacity_busy、account_pool_exhausted、channel_capacity_unavailable；兼容原静态门禁 api_key_concurrency_limit。核对 Claude/OpenAI 适配后的结构化 code 不丢失，优先于泛化429/503分类。

释放本轮 Lease，合并触发快照刷新，遵守 Retry-After；按策略在共同截止时间内排队/分流，既有 attempts 记录保留原因，不把一次满载自动作为用户最终错误。容量暂时忙不永久排除渠道、不永久改写亲和、不套用通用默认一分钟429冷却、不触发错误的鉴权停用或模型熔断。真正401/403、未知429/503、真实额度故障仍按既有规则处理。

仅在未交付业务内容且确认可以安全重放时重试。已有 Claude ping-only 证据与业务输出区别须复用/窄化扩展，不为所有 Written 响应放开重试。不得增加已输出内容后的重复回答、跨渠道拼接或重复扣费。循环受尝试/时间上限控制，不做无界 RetryNextTry。

### 6. 后台与观测

复用管理员渠道编辑和并发统计入口，增加启用开关、过载策略、等待预算及只读状态：静态上限、动态总容量、VM可用数、中转在途数、状态质量、快照年龄、刷新错误、排队人数/等待耗时/竞争拒绝/最终超时。零容量和空闲的启用渠道也可见，前端不得把0显示成默认100。权限保持管理员，普通用户不暴露上游账号与拓扑，所有日志不含调用 Key。

单独统计中转排队、VM内部等待（有证据才报）、上游首字和用户首字；SSE心跳不算首字。区分一次请求与多次attempt，不用混合成功/失败样本证明体验改善。

### 实施顺序

1. 后端容量客户端、缓存和显式配置校验，mock VM 接口覆盖正常/零/未知/过期/查询限流。
2. 接入共享准入、排序和两种过载策略，完成错误分类与取消/释放/账务回归。
3. 管理端编辑与状态展示、相关i18n/能力地图/文档更新，桌面移动验收。
4. 隔离环境联调两端补丁；中转先具备新协议处理，再部署 VM 接口，最后启用指定渠道及 VM Key 动态门禁。各次生产部署另行授权，不自动修改线上配置。

## Alternatives considered

- 只配静态渠道并发4：可立即复用排队，但账号drain/停用后容量下降或扩容不能自动跟随，不满足实时目标；可作为部署前的临时保护，不作为本次最终方案。
- 定时把快照写回渠道max_concurrency：改动表面小，但零的继承语义会放大流量，覆盖人工安全上限，且频繁持久化不能表达未知/过期；选择独立运行时容量源。
- 新建分布式预留协议和严格FIFO队列：可提供更强排队和预约语义，但现有VM接口没有租约能力，会扩大两端改动；首版复用原Lease与有界轮询，明确不承诺零竞争与严格公平。

## Acceptance criteria

- 容量4的mock上游、20个并发请求：中转共享Lease不超过4，其余排队或合法分流；等待预算充足且mock正常释放时全部拿到完整回答，无重复计费。测试覆盖两中转实例共用Redis。
- 4→3→2→0→2→4、partial、快照过期、服务重启、Redis失败；零绝不变无限放行，旧流不被切断、恢复可继续，无过期高值、无立即重试风暴。
- 多模型共享渠道不各放一份额度；映射查询正确；重复上游Key/多Key配置拒绝启用；其他Key外部占用变化引发的竞争拒绝得到有界处理，不能声称完全消除竞争。
- 覆盖普通/亲和/指定渠道、reroute/wait、无其他渠道、队列满、总截止时间、客户端取消、正常/异常流结束、无业务内容可重试、已交付内容不可重放；Lease/计费预留各释放或结算一次。
- 容量忙不触发长期冷却/停用，其他鉴权、额度、真实故障策略不回归；开关关闭时原行为不变。
- 管理员保存/读取/复制渠道一致，权限与脱敏正确，零/未知/空闲状态显示一致，桌面移动端可用；相关Go竞态/前端检查和make verify-notes通过。公网真实小额验收另列，禁止对真实账号做20请求压测。

## Risks

快照不是预留，VM接口目前也不是多副本全局计数；中转无法单靠消费它保证任意会话没有等待。轮询可能存在短时空闲和队列饥饿，需通过等待p95/超时证据决定是否后续引入唤醒或公平队列。缓存优先的更长等待会增加用户首字时间，速度优先换渠道会损失缓存局部性；后台明确呈现取舍，不声称两者同时最优。跨多个Key/重复渠道的统一池资源标识与租约不在第一版。
