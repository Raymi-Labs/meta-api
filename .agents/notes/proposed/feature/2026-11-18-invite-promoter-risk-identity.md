## Problem

内部推广规则把“有效消费”作为一切返点、奖金与晋级人数的前提：单笔充值不低于 1 元、注册满 7 日、有真实 API 调用消耗，三项满足任意两项。推广者须完成实名才能领取并提现返佣；同一支付账户、同一实名主体或同一设备指纹下的第二个及以后账号不产生返点与奖金并进入风控审核；推广者用返利余额、提现或兑换所得再次充值不计入任何人的返佣基数。规则还要求注册后 30 日内经双方确认可改绑一次、禁止直接或间接成环，并对自养号、集中注册、上级清退与违规给出冻结、扣回、降档等处置。

项目目前没有实名、改绑、设备指纹与支付账户标识；有效性只看“支付成功”，无法排除小额刷单与返利循环充值。

## Existing capabilities and impact

- 入池前提：[台账与结算](../../../../model/invite_commission.go) 只排除自邀、二级成环（C→B→A 中 A=C）和兑换码来源；[分配引擎笔记](2026-11-18-invite-tier-commission-engine.md) 在此基础上增加有效消费与档位分配。
- 用户数据：`model/user.go` 有 `created_at`、`register_ip`（带索引）、`used_quota`、`inviter_id`；`model/invite_binding.go` 只在注册事务内决定一次绑定，没有改绑。
- 加密：`common/crypto.go` 提供按用途派生密钥的 `EncryptSensitiveData/DecryptSensitiveData`（AES-GCM）与 `GenerateHMAC`，可用于实名信息加密存储和身份号/指纹的去重哈希。
- 支付：`model/topup.go` 记录实付金额、币种与支付方式；钱包内部购买（`PaymentMethodWallet`）不经 `EnqueueInviteCommission*`。各支付渠道当前回调里没有被持久化的付款账户标识。
- 管理面：管理员用户邀请关系页（`UserInviteRelationsSheet`）可扩展风控标记与审核入口；冻结、扣回与欠款的资金动作复用 [结算账单笔记](2026-11-18-invite-commission-statements.md)。已实现的 [邀请推广](../../implemented/feature/2026-10-22-invite-promotion.md) 只统计点击，不存访客标识，本提案不改变其隐私边界。

## Proposal

### 有效消费判定

- 条件：本笔实付不低于配置金额（默认 1 元）、注册时间满 7 日（按支付时刻判定）、`used_quota > 0`（真实调用消耗）。满足两项即有效。
- 判定时点：支付时满足两项直接入池；只差一项且该项会随时间满足（注册满 7 日、后续产生调用）时，台账以“待判定”入池，`next_retry_at` 设为注册满 7 日的时刻，到期重判，仍不满足则跳过并写原因。
- 首次成为有效用户时写入被邀请人资格记录（见引擎笔记），驱动晋级人数与注册奖励。

### 返利循环排除

- 推广者在获得过返佣后，其本人充值中不超过“累计已划转/兑换入钱包的返佣额度”的部分不计入任何人的返佣基数；用一个累计计数（已转入额度、已被抵扣额度）在入池事务中加锁扣减，超出部分照常计入。提现所得属于站外资金，无法在站内追溯，按同一累计计数近似处理。

### 实名

- 推广者实名：用户提交姓名与证件号，管理员审核；姓名与证件号用 `EncryptSensitiveData` 加密存储，另存证件号 HMAC 用于“同一实名主体”去重；界面只显示脱敏值，管理员解密查看需单独权限并写审计日志。
- 未实名推广者的返佣照常入池，但结算时挂起（保持 pending 并延后重试），实名通过后继续结算；提现要求实名姓名与收款账户姓名一致。
- 被邀请人实名为可选开关，默认关闭；开启后被邀请人未实名的支付视为不满足有效消费。

### 关联账号风控

- 设备指纹：前端在注册与支付时提交浏览器指纹，服务端只存 HMAC 值；支付账户标识仅在渠道回调提供时以 HMAC 存储。
- 同一实名 HMAC、支付账户 HMAC 或设备指纹 HMAC 下的第二个及以后被邀请账号，其台账以风控原因跳过，并生成风控审核单；3 日内同一 IP 段集中注册且金额一致的团队自动冻结推广者提现、待人工审核。
- 处置：冻结提现与结算、扣回指定周期返佣（走欠款路径）、强制降档、清退（其下级邀请关系转为无上级，即平台公共池）。上级违规扣除其名下当月返佣、团队降档，不影响下级用户自身权益。所有处置写管理日志并可撤销。

### 改绑与成环

- 注册后 30 日内，被邀请人发起改绑、新上级确认后生效，每个用户限一次；改绑只影响之后的支付，已入池台账不迁移。新上级不能是自己的直接或间接下级（沿邀请链向上检查到深度上限），也不能是已切断上游的成员/部长链路之外的非法节点。

### 开放决策

1. 实名方式：用户提交、管理员审核、加密存储，暂不接第三方实名接口。➡️ 采用。
2. 真实 API 消耗口径：`used_quota > 0`。➡️ 采用。
3. 判定时点：注册满 7 日按支付时刻判定；只差可补足条件时到期重判。➡️ 采用。
4. 关联标识：浏览器指纹哈希；支付账户标识只在渠道提供时采集。➡️ 采用。
5. 实名范围：强制推广者收款实名，被邀请人实名默认关闭为可选开关。➡️ 采用。

## Alternatives considered

- **接入第三方实名核验接口** — 自动化程度高、可防伪造证件；但需要额外供应商合同、费用与个人信息出境评估，且规则只要求“完成实名认证”，先用人工审核满足合规，接口留作后续替换实现。
- **用注册 IP 代替设备指纹做关联** — 无需前端改动，已有 `register_ip` 索引；但同一出口 IP 下的正常用户（校园网、企业网）会被误伤，单独使用误判率过高，改为只在“集中注册”组合规则中参考 IP 段。
- **有效消费只在支付时判定一次** — 实现简单；但规则允许“注册满 7 日 + 有调用”这类事后满足的组合，只判一次会让新用户的首笔小额充值永远无法生效，改为可到期重判。
- **明文存储实名信息并靠数据库权限保护** — 查询方便；但仓库与备份泄露时直接暴露身份信息，且项目已有按用途派生密钥的加密工具，选择加密存储加 HMAC 去重。

## Acceptance criteria

- 三选二判定表驱动测试覆盖八种组合；“待判定”台账到期重判，满足则结算、不满足以原因跳过。
- 返利循环排除：推广者用转入钱包的返佣再充值，不产生上级返佣；超出部分照常入池；并发支付不重复扣减累计计数。
- 实名信息数据库中为密文，接口只返回脱敏值；管理员解密有审计日志；未实名推广者的台账挂起、实名后结算；提现姓名不一致被拒绝。
- 关联账号：同一实名/支付账户/指纹的第二个被邀请账号不产生返点并生成审核单；冻结后提现与结算被阻止，解冻后恢复。
- 改绑：30 日内仅一次、需新上级确认、成环被拒绝、已入池台账不迁移。三库迁移与 `-race` 测试通过。

## Risks

- 实名与指纹属于个人信息，必须在隐私政策中说明用途与保存期限；笔记、日志和测试数据不得出现真实身份信息。
- 浏览器指纹可被伪造或因浏览器升级变化，只能作为辅助信号，自动处置仅限“跳过返点 + 生成审核单”，冻结和清退需要人工确认。
- 返利循环排除按累计额近似，无法识别通过站外转手再充值的资金，可能漏判；也可能误伤推广者本人的正常充值，需在账单中显示被排除的基数。
- 人工审核量会随推广规模增长，审核积压时返佣延后；需要后台列表支持筛选与批量处理。

## 已确认的集中注册处理

2026-11-19 用户确认：默认只记录风险、人工冻结。不在缺少网段定义和成团人数阈值时自动冻结。
