# Agent Note: 企业工作空间、成员额度与申请审批

Status: proposed

## Problem

企业需要统一购买和管理模型调用额度，由企业管理员给员工分配额度及可用模型；员工独立登录、创建自己的令牌，余额不足时申请追加。当前用户钱包、令牌和平台管理员权限不能表达企业归属、企业内部授权和审批。

本轮仅交付设计，不实现业务功能、不调整生产数据、不发布应用版本。以下是推荐默认方案，产品细节可在实施前调整。源码核对基线为 `323067c41`；2026-11-12 评审修订时在 `f28f22f8a` 复核计费链路，并按产品结论调整了预留规则、首期范围、违规费、发票与返佣；同日确定入口与界面（管理员独立后台、员工留在控制台、创建令牌时选付款方）和邀请初始额度，并把调用范围改为全部类型分两批开放，确定首期由平台开通企业、对公转账入账、审批不设金额上限、模型范围默认继承并随平台新增自动开放。目标客户是外部合作企业，平台内部团队作为首家灰度企业。

## Proposal

### 目标与现有能力

新增企业工作空间，复用现有登录、令牌管理、模型目录、路由、计价和结算框架。企业持有独立钱包；成员分配额度是企业内部的预算划拨，不进入个人钱包。企业管理员是企业内部角色，不授予平台管理员权限。

| 已核对链路 | 当前能力 | 扩展边界 |
| --- | --- | --- |
| `web/src/pages/Enterprise/index.jsx` → `/enterprise` | 公开介绍与咨询入口；既有笔记明确不承诺团队权限 | 保留公开页，新增 `/console/enterprise` 工作台 |
| 用户页 → `router/api-router.go` → `middleware/auth.go` → `model/user.go` | 用户身份、平台角色、个人钱包、用户分组 | 增加组织及成员关系，不把企业管理员写进 User.Role |
| 令牌页/编辑弹窗 → `/api/token` → `controller/token.go` → `model/token.go` | 按 UserId 列表、创建与编辑；令牌额度、模型和渠道限制、分组与周期包 | 保留现有个人令牌；企业令牌增加不可变归属和企业策略收窄 |
| `TokenAuth` → `service/token_routing.go` → 路由/计价 | 保存与运行时分组权限、模型限制、有序回退 | 加企业/成员权限交集，所有回退仍受约束 |
| `service/billing_session.go` → `service/funding_source.go` → 钱包/订阅模型 | 预扣、结算、退款；钱包、订阅、token-only 分支 | 增加 EnterpriseFunding，并覆盖预留扩容、退款判定、重试与恢复，不能只增加工厂分支 |
| 本人日志/统计与管理员全站接口 | 本人和平台全站两级视图 | 新增企业范围查询，日志、导出、汇总按相同企业条件过滤 |

用户 Group 继续承担可用分组/倍率职责，不能兼作租户标识。沿用现有分组和用户组专属倍率机制，为企业解析独立计费上下文，不修改员工个人 Group，也不恢复已否决的托管路由和独立售价体系。做法：每家企业配置一个计费用户组，企业令牌在 `TokenAuth` 写入请求上下文时以该组覆盖用户组，同一企业的成员价格一致，合同价落在该组的专属倍率上。绕过请求上下文直接读取用户分组的调用点（`middleware/distributor.go`、控制器中的充值、令牌、渠道测试，`service/quota_notice.go` 等）实施时检索列出并逐一核对。

### 身份、角色和工作空间

同一登录账号可拥有个人空间和企业成员身份。数据模型允许加入多个企业；首期一个账号只能加入一家企业，多企业后续开放。界面不做空间切换：企业成员创建令牌时选择付款方，默认企业、可选个人，创建后不可更改；令牌列表和使用日志每行标出付款方并可按其筛选。每枚令牌仅属于一个付款方；个人令牌不会因加入企业自动迁移。

| 角色 | 权限 |
| --- | --- |
| 平台管理员 | 开通、冻结企业及平台侧支持，操作留审计；不把企业管理接口开放给普通平台用户 |
| 企业所有者 Owner | 企业资料、充值、管理员任免、所有权转移、全企业成员/预算/策略/账单；企业始终保留一名有效 Owner |
| 企业管理员 Admin | 邀请及停用普通成员、分配回收额度、设置成员模型、审批申请、查看企业用量；不能自行增加企业资产、转移所有权或提升角色 |
| 员工 Member | 查看本人企业额度与消费、管理本人企业令牌、发起和撤销本人待审批申请 |

所有者也受自身成员预算与模型策略限制；普通管理员不能审批本人申请、增加本人额度或放宽本人模型范围，由 Owner 操作。Owner 自己的预算调整作为直接管理操作留痕。首期财务/只读审计角色暂缓。

首期企业只能由平台开通，不开放自助创建：计费用户组和合同价逐家配置，开通时指定 Owner。管理员的分配与审批不设单笔金额上限，总额受 U 约束，并禁止自批自增。

邀请绑定已验证邮箱，令牌只存摘要、有有效期、一次性消费；`users.email` 在数据库层没有唯一约束，OAuth 账号也可能没有邮箱，所以成员关系以登录后接受邀请的用户 ID 为准，邮箱一致只作为接受时的校验；通过普通注册/登录加入，不由管理员分发共享密码。邀请有效期 7 天，可填初始额度；未接受邀请不占用预算，接受时在同一事务内从 U 划拨，U 不足时成员照常加入、额度为 0 并提示邀请人。停用先阻止新请求，再等待在途结算，最后回收剩余额度；重新加入建立新成员代次，旧令牌不复活。成员离开不删除历史账单。最后一名 Owner 不允许直接退出。

### 企业余额与成员额度

推荐首期采用预付费、实额划拨：分配给员工的钱立即从企业未分配额度划出，减少先到先得造成的额度争抢；每次请求只锁成员预算行，不锁企业钱包行，企业内并发不会集中在同一行。金额沿用内部整数 quota，页面沿用现有币种换算，不用浮点金额记账。

定义：U 为未分配额度，A_i 为成员可用额度，R_i 为成员在途预留，S 为企业累计净消费。无异常调账时，净入账金额 = U + ΣA_i + ΣR_i + S。

- 充值：U 增加。平台确认到账才入账，回调按订单幂等。首期只走对公转账：平台核对到账后在企业管理后台录入金额与转账凭证号，同一企业内凭证号唯一，重复录入拒绝；自助充值随后复用现有支付通道，订单必须固定 `payer_type=enterprise` 和 `enterprise_id`，不能根据支付人当前空间决定收款账户。企业入账走独立入口，不调用邀请返佣入队，不产生返佣。发票由企业负责人以本人账号走现有发票申请（公司抬头、银行转账录入），首期不改发票代码；发票记录归属企业留到自助充值阶段。
- 分配 x：U 减 x，A_i 加 x；回收仅限 A_i 为正的部分。分配和回收是内部划拨，不计入模型消费或收入。
- 请求预留 r：A_i 减 r，R_i 加 r；结算 c：R_i 减 r，A_i 加 r-c，S 加 c。失败按已确认真实用量结算，仅退未消费部分。c 大于 r 时 A_i 可以为负，守恒式不变；A_i 小于等于 0 时拒绝该成员新请求，后续分配先抵欠额。成员停用时 A_i 无论正负一并并入 U 并记流水；U 为负时禁止分配，下次入账先抵。
- 所有员工令牌共用 A_i；令牌可另设更小的安全上限，该上限与已用量记在企业账本，和成员预算在同一事务内检查；企业令牌不使用令牌表的剩余额度字段，因为现有令牌额度与资金来源分两步提交，失败只记日志。增加令牌数量不会增加成员预算。
- 内容安全违规费从触发成员的 A_i 扣除，流水记录成员与请求，企业管理员可见，不扣个人钱包。现有违规费经 `PostConsumeQuota` 扣个人钱包，企业分支单独实现。“令牌不限额”只表示不额外设置令牌上限。
- 首期手动分配、手动回收，默认不设月度清零、不自动结转；周期预算在后续独立增加，避免把企业资产和每月消费上限混为一谈。
- 个人钱包、个人套餐、可售令牌额度均不作为企业令牌备用资金；企业余额不足不自动扣员工个人钱，个人消费也不扣企业钱包。
- 首期不提供成员间转账、个人钱包互转或员工提现；企业退款由平台受控处理，先核对未分配余额和在途，不凭审批生成资产。

示例：企业到账 10,000，给甲分配 2,000、乙分配 1,000，则未分配余额 7,000。甲的两枚令牌分别消费 300 和 200 后，甲剩余 1,500，企业净消费 500。甲申请追加 800 并批准后，甲为 2,300，企业未分配为 6,200，企业资产不会因审批增加。

### 模型、功能和请求权限

实际模型范围 = 平台给企业开放范围 ∩ 企业策略 ∩ 成员策略 ∩ 令牌限制。成员和令牌可继承上层或进一步收窄；显式空集合表示全部禁止，必须区别于继承。企业策略默认继承平台给该企业开放的全部模型，平台新增模型自动可用；管理员可改为指定清单，改后新增模型不再自动加入。成员默认继承企业范围，管理员可对个别成员收窄。支出由成员预算约束。

首期只做企业级和成员级模型白名单；IP、并发、有效期复用令牌已有字段。按聊天、图片、音频、视频等能力授权，以及最大输出、RPM、策略模板放到第二期，避免第一版实现通用策略语言。型号别名与实际路由模型需规范化校验；模型列表隐藏无权项不能替代服务端鉴权。

模型目录、令牌创建编辑、调用鉴权、自动回退、网页体验临时令牌、桌面入口均使用同一付款方上下文。未适配企业资金和权限的入口应明确禁止企业模式，不能默默退到个人付款。机制上默认拒绝：`TokenAuth` 识别企业令牌后只放行白名单路由，其余返回明确错误；`PostConsumeQuota`、`taskAdjustFunding`、`SettleBilling` 的无会话回退等按用户 ID 扣个人钱包的兜底分支，遇到企业来源改为报错。测试枚举全部 relay 路由，断言每条路由要么在白名单、要么拒绝企业令牌，新增路由默认不放行。首期不启用企业 token-only/可售/周期包模式。

调用范围的目标是全部类型，分两批开放。第一批随企业资金来源上线：文本、生图、语音、向量与重排，它们已经通过 BillingSession 预留并经 `SettleBilling` 结算。第二批逐项改造后开放：网页体验区（`controller/playground.go` 的临时令牌与 `controller/image_playground.go` 的系统令牌都按用户归属，需要带上付款方）、视频与音乐等异步任务（提交走 BillingSession，但 `taskAdjustFunding` 把退款和差额记到个人钱包）、Midjourney（`relay/mjproxy_handler.go` 直接调用 `PostConsumeQuota`，`controller/midjourney.go` 的失败退款进个人钱包）、实时语音（`PreWssConsumeQuota` 与 `PostWssConsumeQuota` 在会话中直接扣个人钱包）。改造方向是把这些入口接到同一资金来源接口，而不是逐处加企业分支。未开放的入口对企业令牌返回“暂不支持企业额度”。

收紧模型或停用成员后，新请求立即受新策略约束；写入时递增策略版本，鉴权不能只依赖可能过期的缓存：令牌整枚缓存在 Redis，停用成员或收紧策略时主动删除相关令牌缓存，并在每次请求比对策略版本。已接受的请求保留原付款方与定价快照完成结算；紧急中断尽力取消，但不承诺取消已产生的上游成本。

### 申请与审批闭环

员工从额度卡、额度不足提示进入申请，填写追加金额、用途；页面同时显示可用额、在途额及待审批申请，避免把暂时预留误报为额度耗尽。

状态：pending → approved / rejected / cancelled / expired。已批准金额作为审批结果保存，可以少于申请金额，并记录原因；pending 的成员可撤销。默认同一成员同类申请仅一个待办，待办有效期建议 7 天。模型扩权申请后续复用审批框架，但与额度账务分开。

审批页面显示当前预算、近期开销、申请原因、企业可分配余额。批准时在同一数据库事务中核对审批权限、申请状态、成员有效性和 U，完成状态变更、划拨与审计。余额不足时保持 pending，返回明确原因；多人同时审批只能成功一次。企业冻结或成员离开会使待办失效。

首期不建站内消息（仓库没有通用的私有消息设施）：审批中心显示待办数量，并复用现有邮件发送通知申请人和审批人。通知失败不撤销审批，只发给对应企业授权人员。私有站内消息与事务 outbox 放到第二期，不能直接将现有全站公告当作私有审批通知。

额度归零不直接永久禁用企业令牌；返回可识别的 `enterprise_quota_exhausted`，审批后下一次请求即可恢复，仍保留手动封禁/过期状态。另区分模型禁止、企业冻结、在途占用、单次预留不足、预算为负。复核现有连续额度失败自动禁用逻辑，企业分支必须适配。

### 页面和数据可见范围

入口与布局：企业管理员使用独立后台，自带顶栏（企业名、未分配余额、返回控制台）和侧栏，沿用现有组件与主题，不另做一套视觉；`web/src/components/layout/PageLayout.jsx` 对 `/console` 路径默认渲染控制台侧栏，企业后台路径需要例外。入口是控制台侧栏新增的“企业”分组，位于“控制台”与“个人中心”之间，仅企业成员可见：员工只有“我的额度”，管理员另有带待办数量的“企业工作台”。顶栏余额旁显示企业额度；公开页 `/enterprise` 对已加入企业的用户增加进入工作台的按钮；邀请与审批邮件直达对应页面。

企业后台五页：总览（未分配、成员可用、在途、净消费、待办、成员消费）、成员（邀请、分配、回收、停用、成员模型）、审批、用量（账单与导出）、设置（企业资料、企业级模型、余额提醒、操作记录）。平台管理员在“管理员”分组新增“企业管理”：企业开通与冻结、入账与调账、计费用户组、待对账预留。

员工留在现有控制台：“我的额度”一页含额度卡、申请入口、获准模型和我的申请；令牌与消费沿用令牌管理和使用日志，按付款方标注。顶栏同时显示企业额度与个人余额。

复用现有令牌表格、日志表格、模型选择器和统计图，增加付款方筛选参数与按付款方隔离的缓存键。企业管理员可看成员消费金额、模型、时间和令牌名称/掩码，可撤销令牌，但不能读取成员明文 Key、个人账单或默认查看提示词/响应内容。

账单以结算记录为准，消费减退款为净消费，分配不计消费；统计显示截止时间及未知/待结算状态。列表、导出、卡片统一企业/成员/模型/时段条件，时间按企业配置时区展示，底层 UTC 存储。审计至少包括角色、额度、模型、审批和停用的操作者、时间、前后值、原因及请求标识。

### 建议数据与接口

| 数据 | 关键职责 |
| --- | --- |
| enterprises | 企业状态、Owner、计费分组/策略引用、时区、版本 |
| enterprise_members | 企业与用户关联、角色、状态、成员代次；有效关系唯一约束 |
| enterprise_invitations | 邮箱绑定、摘要、有效期、消费状态 |
| enterprise_wallets / member_budgets | 未分配、成员可用和预留余额，令牌上限及已用量；条件更新/事务锁与版本 |
| enterprise_ledger / reservations | 充值、划拨、预留、结算、退款、调账；请求/事件唯一键与状态机 |
| enterprise_policies | 企业/成员模型和能力策略；结构化列及 TEXT JSON 配置 |
| enterprise_quota_requests | 申请金额、批准金额、审批人、原因与状态版本 |
| enterprise_audit_events | 不可静默修改的操作记录；私有消息与 outbox 第二期再加 |

Token 增加 enterprise_id 和 membership_id（个人为空/兼容默认值），创建后不可直接改归属。请求、任务、消费/退款日志保存企业、成员代次、资金来源、预留 ID、原始定价快照；不能靠当前用户归属反推历史账单。账单以主库企业流水为准；日志只增加企业列用于明细下钻，按事件 ID 去重，写入遗漏由流水对账补齐，不能假设跨库事务。`logs` 是大表，生产 MySQL 增加带索引的列须单独评估 DDL。

建议新增 `/api/enterprises/:id/{members,invitations,budgets,policies,quota-requests,usage,audit}`，批准与撤销使用明确动作接口和幂等键。登录身份 + 企业成员中间件 + 操作权限校验共同保护接口，不复用只检查平台 Admin 的接口。每次按对象 ID 访问都带企业条件，包括导出、任务结果下载、声音/文件等资源；越权对象返回一致的不可访问响应。

### 计费可靠性与兼容迁移

复用 FundingSource 概念，新增企业的持久预留/结算状态机。成员预算与令牌上限同在企业账本，在同一事务内检查和更新；状态机参照 `model/pulse_funding.go` 的绝对目标值与行锁写法；数据库条件更新防止多节点并发超分配。锁顺序固定，使用 GORM 事务并分别验证 SQLite、MySQL、PostgreSQL；缓存仅加速，不作为余额真相。所有 JSON 编解码使用 common 包。

企业成员预算沿用个人钱包的预留与结算规则（同步聊天用有界首笔预留，其他类型用各自现有的预扣），成员有额度时体验与普通用户一致：按现有预估建立预留，可用额不足本次预留则拒绝；结算按真实用量多退少补，超出预留的部分直接计入成员预算并允许其为负，为负后拒绝新请求。每个企业请求都建立按 request_id 的持久预留，不使用无预留的信任旁路。单成员最大欠额约为其并发在途请求的真实费用与预留之差，可用令牌并发上限收窄。第一批开放的各调用类型逐项验证预留与结算，流式、工具轮次、阶梯与缓存价格同样逐项验证。不能截断真实账单或转扣个人。

重试共用一个逻辑请求预留；结算/退款有唯一事件键，服务重启后可恢复。现有个人预留在进程崩溃后停留在 reserved、不按超时退款；企业预算小，卡住的预留等于长期冻结，因此企业预留自带回收任务：超时未终结的预留转待对账并告警，由平台后台处理，不自动退款。结果不明不能仅凭超时退款，先查询上游或转待对账。结算和退款不可重复生效；角色撤销/成员停用不能阻断原已受理请求的最终结算。

灰度采用新增表、可空/兼容默认字段和功能开关。旧用户、令牌、钱包、套餐保持原解释；开启前验证所有旧入口，企业流量不可进入未适配分支。生产上线仍走受保护发布入口，先备份/预检、后切换；回退前停用企业新请求并处理在途，不直接让旧程序继续接受企业令牌。应用功能实施后再按功能版本发布，本提案不改变 VERSION。

### 分期建议

1. 首期闭环：平台开通企业并配置计费用户组、Owner/Admin/Member、邀请和停用、平台确认入账、手动分配回收、企业级与成员级模型白名单、企业令牌、第一批调用类型（文本、生图、语音、向量与重排）、申请审批（待办数量加邮件）、基本账单和审计、平台侧企业管理。一个账号一家企业。所有暴露入口都要完成企业隔离；未开放的调用类型明确拒绝。内部团队在此阶段灰度。
2. 对外开放前：第二批调用类型，即网页体验区、视频与音乐等异步任务、Midjourney、实时语音，含退款归属与崩溃恢复。
3. 管理增强：多企业、按能力/最大输出/RPM 的策略与模板、站内消息与 outbox、低水位自动补额、部门/项目、日/月预算与时区周期账本、预算模板、自助在线充值及企业发票归属、批量操作、邮件告警、模型扩权申请。
4. 大客户能力：企业 SSO、SCIM、域名验证、部门管理员、多级审批、服务账号、财务/审计角色、账单成本中心、合同后付费。后付费需要独立授信规则，不复用预付费语义。

### 首期实施顺序

按功能开关分步合入，每步默认关闭、可独立回退：

1. 企业、成员、邀请表与接口，不接触计费；验证越权和保留最后一名 Owner。
2. 企业钱包、成员预算、流水、平台入账、分配回收；验证三库并发下守恒。
3. 令牌归属字段、`TokenAuth` 企业上下文与计费用户组、路由白名单、模型权限交集；验证路由枚举和停用即时生效。
4. EnterpriseFunding、预留状态机、结算退款、回收任务、兜底分支报错、违规费；验证重试幂等、崩溃恢复、个人钱包零变动。
5. 日志与用量的企业范围查询和导出。
6. 申请审批与邮件通知；验证并发审批只成功一次。
7. 前端：企业独立后台、控制台内的员工页与付款方选择、平台侧企业管理。
8. 第二批调用类型逐项接入同一资金来源接口：网页体验区、异步任务、Midjourney、实时语音。

内部团队作为首家企业在第 7 步后灰度；第 8 步完成后再开放外部企业。

## Alternatives considered

- 管理员给普通用户钱包直接充值：现有功能复用最多，但资金混入个人资产，离职回收、企业隔离、共享审批与审计都无法准确表达，因此不采用。
- 企业共用管理员账号和一枚令牌：接入最快，但员工无独立身份、权限与责任归属，不能支持本需求。
- 企业钱包加成员消费上限、允许总上限超过钱包：适合弹性预算且资金利用率高，但某员工可能提前用尽其他人的预算。首期优先采用实额划拨；后续可作为明确的共享预算模式。
- 独立企业版部署和代码分支：隔离直观，适合私有化交付，但会重复维护计费与权限。当前推荐同应用组织隔离；私有化作为后续部署选择，不复制产品实现。
- 企业严格准入预留（本提案初稿）：无可信计费上界即拒绝，超出部分待平台人工对账，超支控制最严。但多数客户端不传输出上限，成员有额度也会被拒，且每笔超出都需人工调账；2026-11-12 产品决定改为沿用个人钱包规则。后续可作为按企业开启的严格模式。
- 超出部分由企业不可分配的安全垫自动补扣、成员预算不为负：成员额度更直观，平台也不会因单个成员超出而垫付。但多一套安全垫配置和补扣流水；产品选择与个人钱包一致的规则，暂不采用。
- 顶栏空间切换（本提案初稿）：切到企业后整个控制台只显示企业数据，边界直观。但控制台要维护两套视图，成员容易找不到另一空间的令牌；2026-11-12 产品决定改为创建令牌时选付款方。
- 企业功能全部放进现有控制台侧栏：改动最少，但企业管理员多为非技术角色，五个管理页会夹在不相干的菜单之间。全部独立一套则令牌和日志要做两遍。选择管理员独立后台、员工留在控制台。
- 只开放同步文本协议（本提案初稿）：交付范围最小，但外部企业需要生图、视频等全部能力；改为全部类型分两批开放，未改造的入口先拒绝。
- 自助创建企业并在线充值：获客路径最短，但每家企业的价格要单独配置，在线订单还要处理付款人与企业的归属；首期由平台开通、对公转账入账，自助充值留到管理增强阶段。
- 管理员审批设单笔上限、超出由 Owner 审批：多一层控制，但可批总额本来就不超过未分配余额，首期不设。
- 平台新增模型默认不对企业开放、由管理员显式加入（本提案初稿）：企业不会在不知情时用上高价模型，但每次上新都要逐家勾选；成员预算已经限制支出，2026-11-12 产品决定默认自动开放，需要管控的企业改用指定清单。

## Acceptance criteria

- 完整流程：开通→邀请→分配→授权模型→员工发令牌→真实结算→额度不足→申请→批准→继续调用；甲乙多枚令牌、企业总览与账单金额一致。
- 两个企业与个人空间之间，修改 URL、请求体、令牌 ID、任务/导出 ID 均不能跨域；按付款方筛选无缓存数据串漏，企业管理员不获平台能力。
- 枚举全部 relay 路由，企业令牌只能进入白名单路由；任何企业请求（含违规费、失败退款、重试）都不改变成员个人钱包。
- 成员预算结算超出后为负并拒绝新请求，分配后先抵欠额；企业入账不产生返佣记录。
- 新旧令牌模型权限、自动分组回退、别名、网页体验/桌面和直接 API 均受同一企业策略；未适配协议明确拒绝。
- 第二批开放后，企业令牌的异步任务失败退款、Midjourney 扣费与退款、实时语音扣费、网页体验区请求都记到成员预算，个人钱包零变动。
- 邀请初始额度在接受时到账且只到账一次；令牌付款方创建后不可更改。
- 平台新增模型后，继承范围的企业与成员无需操作即可调用；已改为指定清单的企业不受影响。
- 重复充值回调、并发分配/回收、双人审批、自批申请、请求重试/中断、重复结算/退款、进程重启、日志库故障及通知故障保持账务守恒与可恢复。
- 停用成员后旧令牌新请求拒绝，在途按原企业结算；重加成员、改角色、降权限、企业冻结不能复活旧权限或抹除历史。
- 余额不足、在途占用和预留不足分别展示，批准不解除手动封禁；无明文 Key 或请求正文进入企业普通审计视图。
- 分页/筛选/时区/导出与汇总一致；SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 的事务、唯一约束和迁移均须验证。主库/日志库分离及多节点缓存失效需专门演练。
- 保留既有个人钱包、订阅、可售令牌和路由回归；未全部通过前不宣称支持企业模式。

## Risks

主要工作量在跨入口授权、账务原子性及在途恢复，而非成员 CRUD。组织隔离遗漏可能暴露跨企业数据，当前多个显式计费类型分支必须逐项审计；第二批入口各自绕过 BillingSession，改造量取决于能否统一到资金来源接口；完成前不能对外部企业开放。

实额划拨提高额度保障，但管理员需主动回收闲置预算。沿用个人钱包规则意味着成员预算可短暂为负；全企业额度耗尽时企业总余额也可能为负，由下次入账抵扣，与个人钱包透支同一性质。预算接近用尽时，大输出上限请求可能因单次预留不足被拒，页面需区分展示，不偷偷改写请求。以下关联面尚未逐项核对，实施前各需结论：上游现金账本归属、个人用量统计与看板、额度不足提醒对象、按用户或用户组的限流。对公入账依赖人工核对，录错金额只能走调账并留痕；入账量变大后需要自助充值替代。
